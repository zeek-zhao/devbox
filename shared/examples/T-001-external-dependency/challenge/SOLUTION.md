# T-001-external-dependency · faded 挑战档参考答案

> 与上层 [WALKTHROUGH.md](../WALKTHROUGH.md) 对应：本文件只给答案骨架，
> 逐行判读以 WALKTHROUGH 为准（challenge 不进 run.sh 断言）。

1. **两个 200 里藏着一个 401**：API 域名上的两次请求（jobs / logs）都 200/302 成功，
   令牌没问题；401 只出现在跟随 302 之后的**第二次请求**。两者唯一差异变量是
   「收件方从 API 换成了 blob」——对照实验见 WALKTHROUGH §3 检查 3 与 §4 判读 2。
2. 同事的两个结论都错：
   - 「令牌过期」：同一令牌在 chain① 返回 200，过期/无效应全链路 401；排除。
   - 「改 db 用例」：日志真因是 `TLS handshake timeout`（外部镜像源）→ 依赖拉不下来
     → `service "toolbox" is not running` → 用例全红，因果链上用例代码根本不在场。
     按 docs/73 §9：环境故障只取证，不动用例代码，更不让 AI 去「修」。
3. 不是同一种故障，互斥判定：
   - **401** = 请求方式错（凭证误带到 blob）→ 修脚本（去掉第二次请求的 Authorization
     头），立刻可验证；
   - **503/5xx** = 依赖本体不可用 → 脚本再对也没用，留证（时间点 + 响应体）+ 等恢复 +
     必要时重试，**不改代码**；
   - 两条路都不该走的是「改用例/加超时重试」——用例是被伪装的受害者（S-06 同型：
     环境问题被误读为代码问题）。
4. `bash run.sh` 七步全绿（RUN-PASS：7/7，退出 0）；其中 step 7 的 mode=down/up
   对照就是第 3 问判定规则的实验依据。
