## 🔢 Bump (版本升级)

### 什么是 Bump?

**Bump** 是指自动升级项目版本号的过程。它是语义化版本管理的核心操作。

### 版本号格式

遵循 [语义化版本 (Semantic Versioning)](https://semver.org/lang/zh-CN/) 规范：

```
MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]

例如: 1.2.3-alpha.0+build.123
     │ │ │   │            │
     │ │ │   │            └─ 构建元数据
     │ │ │   └─ 预发布版本
     │ │ └─ 修订号 (PATCH)
     │ └─ 次版本号 (MINOR)
     └─ 主版本号 (MAJOR)
```

### Bump 类型

| Bump 类型 | 说明 | 触发条件 | 示例 |
|-----------|------|----------|------|
| **Major** | 主版本升级 | 包含 `BREAKING CHANGE` | 1.2.3 → 2.0.0 |
| **Minor** | 次版本升级 | 包含 `feat:` commits | 1.2.3 → 1.3.0 |
| **Patch** | 修订版本升级 | 包含 `fix:` 或 `perf:` | 1.2.3 → 1.2.4 |

### 执行过程

```bash
npm run release
```

**步骤**:
1. 分析 git commits (从上次 tag 到 HEAD)
2. 确定 bump 类型 (major/minor/patch)
3. 计算新版本号
4. 更新文件中的版本号

**更新的文件** (由 `.versionrc.js` 中 `bumpFiles` 配置):
- `package.json` → `"version": "0.0.1"`
- `package-lock.json` → `"version": "0.0.1"`

### 手动指定 Bump 类型

```bash
# 强制 patch 升级
npm run release:patch    # 0.0.1 → 0.0.2

# 强制 minor 升级
npm run release:minor    # 0.0.1 → 0.1.0

# 强制 major 升级
npm run release:major    # 0.0.1 → 1.0.0

# 指定确切版本
npm run release -- --release-as 2.5.0
```

### 预发布版本

```bash
# Alpha 版本
npm run release -- --prerelease alpha
# 0.0.1 → 0.0.2-alpha.0

# Beta 版本
npm run release -- --prerelease beta
# 0.0.1 → 0.0.2-beta.0

# RC (Release Candidate) 版本
npm run release -- --prerelease rc
# 0.0.1 → 0.0.2-rc.0
```

## 📋 Changelog (变更日志)

### 什么是 Changelog?

**Changelog** (`CHANGELOG.md`) 是记录项目所有重要变更的文档，帮助用户和开发者了解每个版本的更新内容。

### 生成原理

```
Git Commits → 分析解析 → 分类整理 → Markdown 格式 → CHANGELOG.md
```

1. **读取 Commits**: 从上次 tag 到当前 HEAD 的所有提交
2. **解析内容**: 提取 type, scope, subject, body, footer
3. **分类整理**: 按 commit type 分组
4. **格式化输出**: 生成 markdown 格式的文档

### Changelog 结构

```markdown
# Changelog

## [0.1.0](https://github.com/xxx/compare/v0.0.1...v0.1.0) (2025-11-11)

### ✨ Features | 新功能
* **scope1**: 功能描述 ([commit-hash](link))
* 功能描述2 ([commit-hash](link))

### 🐛 Bug Fixes | Bug 修复
* **scope2**: 修复描述 ([commit-hash](link))

### 📝 Breaking Changes
* **重大变更说明**

## [0.0.1](https://github.com/xxx/compare/v0.0.0...v0.0.1) (2025-11-10)
...
```

### 配置 Changelog

在 `.versionrc.js` 中配置:

```javascript
module.exports = {
  types: [
    // 会在 CHANGELOG 中显示
    { type: "feat", section: "✨ Features | 新功能" },
    { type: "fix", section: "🐛 Bug Fixes | Bug 修复" },
    
    // 不在 CHANGELOG 中显示
    { type: "chore", hidden: true },
    { type: "docs", hidden: true }
  ]
}
```

### Changelog 的作用

- ✅ **用户视角**: 了解新版本有什么变化
- ✅ **开发者视角**: 追溯历史变更
- ✅ **项目管理**: 版本发布说明
- ✅ **自动化**: CI/CD 自动生成发布说明

## 💬 Commit (提交规范)

### 什么是 Conventional Commits?

**Conventional Commits** 是一种规范化的 commit 消息格式，使 commit 历史更易读、更结构化。

### 完整格式

```
<type>(<scope>): <subject>
<空行>
<body>
<空行>
<footer>
```

### 各部分说明

#### 1. Type (类型) - 必填

表明提交的类别：

| Type | 说明 | Bump | 示例 |
|------|------|------|------|
| `feat` | 新功能 | minor | `feat: 添加用户登录` |
| `fix` | Bug修复 | patch | `fix: 修复登录错误` |
| `docs` | 文档 | - | `docs: 更新README` |
| `style` | 格式 | - | `style: 格式化代码` |
| `refactor` | 重构 | - | `refactor: 重构API` |
| `perf` | 性能 | patch | `perf: 优化查询` |
| `test` | 测试 | - | `test: 添加单元测试` |
| `build` | 构建 | - | `build: 更新依赖` |
| `ci` | CI/CD | - | `ci: 添加Actions` |
| `chore` | 杂项 | - | `chore: 更新配置` |
| `revert` | 回退 | - | `revert: 回退xxx` |

#### 2. Scope (范围) - 可选

表明影响的范围，用括号包裹：

```bash
feat(auth): 添加OAuth登录
fix(ui): 修复按钮样式
docs(api): 更新API文档
```

#### 3. Subject (主题) - 必填

简短的描述性说明：

- ✅ 使用祈使句，现在时："添加"而非"已添加"
- ✅ 不要首字母大写
- ✅ 结尾不加句号
- ✅ 限制在 50 字符以内

```bash
# ✅ 好的例子
feat: 添加用户登录功能

# ❌ 不好的例子
feat: 已添加了用户登录功能。
```

#### 4. Body (正文) - 可选

详细的描述信息：

```bash
git commit -m "feat: 添加用户认证功能

- 支持邮箱和手机号登录
- 集成 OAuth 第三方登录
- 添加 JWT token 验证
- 实现记住登录状态"
```

#### 5. Footer (脚注) - 可选

包含以下信息：

**Breaking Changes (破坏性变更)**:
```bash
git commit -m "feat: 重构用户API

BREAKING CHANGE: 
- API路径从 /user 改为 /api/v2/users
- 响应格式从数组改为对象"
```

**关联 Issue**:
```bash
git commit -m "fix: 修复登录bug

Closes #123
Fixes #456, #789"
```

### 破坏性变更标记

**方式一**: 在 type 后加 `!`
```bash
feat!: 重构API接口
```

**方式二**: 在 footer 中使用 `BREAKING CHANGE:`
```bash
feat: 重构API

BREAKING CHANGE: API完全重构
```

两种方式都会触发 **major** 版本升级。

### 实际示例

**简单提交**:
```bash
git commit -m "feat: 添加用户注册功能"
git commit -m "fix: 修复表单验证错误"
```

**带 scope**:
```bash
git commit -m "feat(auth): 添加邮箱验证"
git commit -m "fix(ui): 修复按钮对齐问题"
```

**完整提交**:
```bash
git commit -m "feat(api): 重构用户认证API

重构说明:
- 使用 JWT 替代 Session
- 添加刷新 token 机制
- 支持多设备登录

BREAKING CHANGE: 
旧的 session 认证方式已废弃，需要迁移到新的 JWT 认证。

Closes #123"
```

## 🏷️ Tag (版本标签)

### 什么是 Git Tag?

**Git Tag** 是指向特定 commit 的引用，用于标记重要的版本节点。

### Tag 类型

#### 1. 轻量标签 (Lightweight Tag)
```bash
git tag v1.0.0
```
只是一个指向 commit 的指针。

#### 2. 附注标签 (Annotated Tag) - 推荐
```bash
git tag -a v1.0.0 -m "Release version 1.0.0"
```
包含标签者信息、日期、消息等元数据。

**standard-version 使用附注标签**。

### Standard-Version 创建的 Tag

```bash
npm run release
# ✔ tagging release v0.0.1
```

等同于执行:
```bash
git tag -a v0.0.1 -m "chore(release): 0.0.1"
```

### Tag 命名规范

```
v<major>.<minor>.<patch>[-prerelease]

示例:
v1.0.0        # 正式版本
v1.0.0-alpha.0  # Alpha 版本
v1.0.0-beta.1   # Beta 版本
v1.0.0-rc.0     # Release Candidate
```

### Tag 常用操作

**查看所有 tags**:
```bash
git tag
# 输出:
# v0.0.0
# v0.0.1
# v1.0.0
```

**查看 tag 详情**:
```bash
git show v0.0.1
# 显示 tag 信息和对应的 commit
```

**查看某个 tag 的代码**:
```bash
git checkout v0.0.1
```

**删除本地 tag**:
```bash
git tag -d v0.0.1
```

**推送 tag 到远程**:
```bash
# 推送单个 tag
git push origin v0.0.1

# 推送所有 tags
git push --tags

# 推送代码和 tags (推荐)
git push --follow-tags origin master
```

**删除远程 tag**:
```bash
git push origin :refs/tags/v0.0.1
# 或
git push origin --delete v0.0.1
```

### Tag 在版本管理中的作用

- ✅ **版本锚点**: 标记每个发布版本
- ✅ **回滚基准**: 快速回到某个版本
- ✅ **发布管理**: GitHub Releases 基于 tags
- ✅ **依赖管理**: npm 包发布关联 tag
- ✅ **CHANGELOG**: 计算两个版本间的差异

## 🔄 完整工作流程

### 标准开发流程

```
1. 开发功能
   ↓
2. 创建符合规范的 Commit
   git commit -m "feat: 添加新功能"
   ↓
3. 执行 standard-version
   npm run release
   ↓
4. 自动执行:
   - Bump: 升级版本号
   - Changelog: 更新 CHANGELOG.md
   - Commit: 创建 release commit
   - Tag: 创建版本 tag
   ↓
5. 推送到远程
   git push --follow-tags origin master
   ↓
6. (可选) 发布到 npm
   npm publish
```

### Standard-Version 详细执行步骤

当执行 `npm run release` 时：

```
📖 Step 1: Read Git History
   - 读取从上次 tag 到 HEAD 的所有 commits
   - 解析 commit 消息格式

📊 Step 2: Determine Version Bump
   - 分析 commit types
   - 检查是否有 BREAKING CHANGE
   - 确定 bump 类型 (major/minor/patch)

🔢 Step 3: Bump Version
   - 计算新版本号: 0.0.0 → 0.0.1
   - 更新 package.json
   - 更新 package-lock.json
   ✔ bumping version from 0.0.0 to 0.0.1

📝 Step 4: Generate Changelog
   - 分析 commits 并分类
   - 生成/更新 CHANGELOG.md
   - 添加版本对比链接
   ✔ outputting changes to CHANGELOG.md

💾 Step 5: Git Commit
   - 暂存修改的文件
   - 创建 release commit
   - commit message: "chore(release): 0.0.1"
   ✔ committing package.json and CHANGELOG.md

🏷️ Step 6: Create Git Tag
   - 创建附注标签
   - tag name: v0.0.1
   ✔ tagging release v0.0.1

✅ Step 7: Done
   ℹ Run `git push --follow-tags origin master` to publish
```

### 输出示例

```bash
$ npm run release

> standard-version

✔ bumping version in package.json from 0.0.0 to 0.0.1
✔ bumping version in package-lock.json from 0.0.0 to 0.0.1
✔ created CHANGELOG.md
✔ outputting changes to CHANGELOG.md
✔ committing package-lock.json and package.json and CHANGELOG.md
✔ tagging release v0.0.1
ℹ Run `git push --follow-tags origin master && npm publish` to publish
```

### 推送流程

```bash
# 1. 推送代码和 tags
git push --follow-tags origin master

# 2. (可选) 发布 npm 包
npm publish

# 3. (可选) 创建 GitHub Release
# GitHub 会自动检测到新 tag 并可创建 Release
```

## 🎓 总结

| 概念 | 作用 | 何时发生 | 产物 |
|------|------|----------|------|
| **Bump** | 升级版本号 | 执行 `npm run release` | `package.json` 版本更新 |
| **Changelog** | 生成变更日志 | 执行 `npm run release` | `CHANGELOG.md` 文件 |
| **Commit** | 规范化提交 | 开发者 `git commit` | Git commit history |
| **Tag** | 标记版本 | 执行 `npm run release` | Git tag (如 `v0.0.1`) |

**它们的关系**:
```
规范的 Commits → 触发 Bump → 生成 Changelog → 创建 Tag
     ↓              ↓            ↓              ↓
 开发阶段        版本升级      文档生成       版本标记
```

**核心价值**:
- 🤖 **自动化**: 减少手动操作和错误
- 📚 **标准化**: 统一团队协作规范
- 📖 **可追溯**: 清晰的版本历史
- 🚀 **高效**: 快速发布新版本
