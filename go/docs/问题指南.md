## 并发（goroutine 泄漏 / channel 死锁）

> 来源：类型 ②——可复现实验（下文 NumGoroutine 对照与 deadlock 报错均为
> `devbox-go:latest` 容器实测，Go 版本真本 `images/versions.env` `${GO_VERSION}`）；
> 类型 ①——素材池 `S-06` 作旁证（CI 一片红未必是并发 bug，先确认镜像/通路）、
> `S-01`（并发类用例失败也要先排除 TAG 变量名不一致这类环境故障）。

### 典型现象

- `runtime.NumGoroutine()` 只涨不跌（或压测后不回落）——泄漏的 goroutine 卡在
  无接收者的 channel 收发或永不返回的阻塞调用上。实测对照（完整代码见
  [实践指南.md](实践指南.md) §3 反例）：

  ```
  before: 1
  after: 2
  ```

  程序仍以 0 退出——**泄漏不会自己报错**，这是它最难发现的原因；
- 进程突然终止，stderr 出现（实测）：

  ```
  fatal error: all goroutines are asleep - deadlock!
  ```

  与 goroutine 堆栈 `goroutine 1 [chan send]:`，退出码 2——这是**全局死锁**
  （所有 goroutine 都阻塞）；若只死锁部分 goroutine 而 main 还活着，Go 运行时
  不报错，表现为「任务悄悄不做了」；
- 向已关闭的 channel 发送 → `panic: send on closed channel`；对 nil channel
  收发则永久阻塞（既不 panic 也不报错）；
- （`S-06` 旁证）CI 上并发用例 FAIL，但 stderr 是 docker 报错（
  `manifest unknown`）而非任何 Go 诊断——程序根本没被执行过，别按并发 bug 排。

### 先做的三个检查

1. 现象属于哪一类：报 `fatal error: ... deadlock!` 是全局死锁（运行时替你抓了）；
   静默不退出/计数不落是泄漏（要自己抓）——两类排查入口不同；
2. 每个 channel 是否有明确的「所有者」：谁创建、谁关闭、接收方是谁——
   泄漏几乎总是缺一个角色（发送方在、接收方没了）；
3. 通路与环境先排除：`TAG=latest scripts/run-example.sh go L0-hello` 先绿，
   CI 与本地 `TAG`/`IMAGE_TAG` 值一致（`S-01`：两名不一致曾让 6 个用例 job
   全红而本地假绿）。

### 定位命令 / 工具

```bash
# 泄漏对照：在 main 出口与可疑点各打一次 goroutine 计数
docker run --rm -v "$PWD":/exp -w /exp \
  "ghcr.io/zeek-zhao/devbox-go:${TAG:-latest}" go run leak.go   # NumGoroutine 对照，实测见上

# 竞态与死锁现场：带 -race 构建跑同一程序
docker run --rm -v "$PWD":/exp -w /exp \
  "ghcr.io/zeek-zhao/devbox-go:${TAG:-latest}" \
  bash -c 'go build -race -o /tmp/prog main.go && /tmp/prog'

# 基准用例：健康的关闭/退出范式
TAG=latest scripts/run-example.sh go L3-001-worker-pool-shutdown
TAG=latest scripts/run-example.sh go L1-028-channels-select-close
```

堆栈细读、pprof goroutine 剖析等工具细节见 [工具指南.md](工具指南.md)。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| NumGoroutine 不回落 | 发送方阻塞在无缓冲 channel 且无接收者 | 计数对照实验（实测见上）；`kill -QUIT` 或 pprof 看 goroutine 堆栈卡在哪一行 |
| `all goroutines are asleep - deadlock!` | 所有 goroutine 都在等对方（实测：`ch <- 1` 无接收方，`goroutine 1 [chan send]`） | 读报错里的 goroutine 堆栈，找互相等待的收发点 |
| `panic: send on closed channel` | 多处 close 或接收方越权 close | 只允许发送方（所有者）close；`comma-ok`/`range` 判收 |
| 卡在 nil channel | channel 变量未初始化就收发 | `make` 前置检查；select 里刻意用 nil channel 禁用分支是合法用法，别误伤 |
| 静默丢任务、退出即丢 | main 不等 worker 就 return（`KP-GO-L1-27` 反面） | 对照 `L3-001-worker-pool-shutdown`：close 任务源 → WaitGroup 等待 → 优雅退出 |
| CI 红但 stderr 是 docker 报错 | 镜像/环境问题，不是并发 bug（`S-06`） | 先跑 `L0-hello` 通路；按 [问题指南.md](问题指南.md) 同目录 G2 的环境排查路径走 |

### 修复与预防

修复：给每个 channel 定唯一所有者并保证「发送方有接收方、等待方有退出路径」；
泄漏点用 `context` 取消 + `select` 包住阻塞收发，让 goroutine 能被通知退出。
预防落成可执行判据：

- 并发代码进 CI 必须带 `-race`（`L3-002-race-detector` 的 `go build -race` 基准）；
- 服务型代码在测试里断言 goroutine 计数回落（NumGoroutine 对照，本节实测即最小
  版本），`L3-001-worker-pool-shutdown` 的「所有 worker 退出且 WaitGroup 完成」
  是现成模板。

**反例（可执行）：全局死锁**

- 错误做法：

  ```go
  package main

  func main() {
      ch := make(chan int)
      ch <- 1 // 无接收方，主 goroutine 永久阻塞
  }
  ```

- 复现命令（实测）：

  ```bash
  docker run --rm -v "$PWD":/exp -w /exp \
    "ghcr.io/zeek-zhao/devbox-go:${TAG:-latest}" go run deadlock.go
  ```

- 后果（实测输出，退出码 2）：

  ```
  fatal error: all goroutines are asleep - deadlock!

  goroutine 1 [chan send]:
  main.main()
      /exp/deadlock.go:5 +0x28
  ```

  运行时只救「全体都睡着」的情形：若再加一个正常工作的 goroutine 让 main
  不属于死锁集合，同样的阻塞就变成静默泄漏——所以死锁报错没了不等于问题没了。

## 构建与依赖（go.sum 校验 / module）

> 来源：类型 ②——可复现实验（下文 go.sum SECURITY ERROR 为 `devbox-go:latest`
> 容器实测，离线 file:// 代理构造，过程随节给出）；类型 ①——素材池 `S-01`
> （环境变量名不一致的「构建能过但 CI 全红」同型故障）、`S-02`/`KI-08`
> （依赖 `:latest` 类可变引用导致结果随时间漂移）、docs/20-开发发布增强.md §3.2
> R2/R5（go.mod/go.sum 与依赖清单口径）。

### 典型现象

- 构建中止并出现 `SECURITY ERROR`（实测，完整复现见反例）：

  ```
  verifying example.com/greet@v1.0.0: checksum mismatch
      downloaded: h1:yoWmtHwXoUaza1+nGyhmveCNSBjrJKcG92hq1mpB0jA=
      go.sum:     h1:AAAAwHwXoUaza1+nGyhmveCNSBjrJKcG92hq1mpB0jA=

  SECURITY ERROR
  This download does NOT match an earlier download recorded in go.sum.
  ```

  退出码 1——内容与 go.sum 记录不一致，Go 默认拒绝构建；
- 「本地能 build，CI 报依赖错误」——本地 GOMODCACHE 里已有缓存、CI 是干净
  环境（同型于素材池 `S-01` 的「各跑各的都正常，合到一处就红」）；
- 同一 commit 两次构建产物/行为不同——依赖了浮动版本或没提交 `go.sum`，
  与 `S-02`（`:latest` 可变标签互相覆盖）是同一类「引用了会漂移的东西」；
- 毕业项目场景直接红：`go/project` 强制禁用代理与自动工具链下载
  （`go/project/README.md`），引第三方依赖或依赖本地缓存都会被显式拒绝。

### 先做的三个检查

1. `go.sum` 在不在库里、和 `go.mod` 是否同步：`git status` 看 go.sum 是否漏提交；
2. 报错是「校验不一致」（SECURITY ERROR，有人改了内容或 go.sum）还是
   「下载不到」（网络/代理问题）——前者查内容，后者查 `GOPROXY`/网络；
3. 本地与 CI 的 Go 工具链与构建环境是否一致：`GOTOOLCHAIN`、`GOFLAGS`、
   `GOPROXY` 的值两边各打一次（镜像内版本以 `${GO_VERSION}` 为真本）。

### 定位命令 / 工具

```bash
# 依赖清单口径：当前模块用到哪些版本（docs/20 §3.2 R5 的推荐演示）
docker run --rm -v "$PWD":/exp -w /exp \
  "ghcr.io/zeek-zhao/devbox-go:${TAG:-latest}" go list -m all

# 校验基准：重建 go.sum（确认是 go.sum 陈旧还是内容被换）
docker run --rm -v "$PWD":/exp -w /exp \
  "ghcr.io/zeek-zhao/devbox-go:${TAG:-latest}" \
  bash -c 'go mod tidy && git diff --stat -- go.sum'

# 依赖图与版本选择：为什么拉进了这个版本
docker run --rm -v "$PWD":/exp -w /exp \
  "ghcr.io/zeek-zhao/devbox-go:${TAG:-latest}" go mod graph
```

module 机制与 `L2-001-local-module-replace` 的 replace 语义见
[开发指南.md](开发指南.md)；工具参数见 [工具指南.md](工具指南.md)。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| `SECURITY ERROR: checksum mismatch` | go.sum 与实际下载内容不一致（手改 go.sum、上游内容被换、镜像层缓存混入旧包） | 本节反例实测；恢复 go.sum 后重试，若仍红则上游内容真的变了，停下来查来源 |
| 本地绿 CI 红 | 本地命中 GOMODCACHE 缓存、CI 干净环境才走到校验/下载 | CI 里跑 `go clean -modcache` 后重试复现 |
| 两次构建结果不同 | 依赖浮动版本或 go.sum 未入库（`S-02` 同型：引用可变对象） | `go mod graph` 固定版本；commit 后 `git status` 确认 go.sum 已提交 |
| `module ... not found` / 代理 404 | GOPROXY 配置差异或私有模块地址写在代码里（公开仓纪律：不得有内网地址） | 对比两边 `go env GOPROXY GONOSUMDB GOSUMDB` |
| 毕业项目 build 直接失败 | `go/project` 显式禁代理/禁自动工具链，`GOFLAGS=-buildvcs=false` 被移除 | 读 `go/project/go.mod` 与 `build.sh`，按其约束改 |

### 修复与预防

修复：`go.sum` 陈旧→`go mod tidy` 重建并提交；内容被换→先查上游与缓存来源，
确认可信再更新校验和，**不许**为了变绿直接删校验行。
预防落成可执行判据：

- `go.mod`/`go.sum` 必须入库，依赖变更走 `go mod tidy` 一次成型（PR 里 diff
  只应出现这两处依赖文件）；
- 复现构建用固定版本引用：module 用精确版本（不用分支名/`latest`），镜像用
  `sha-<commit>` tag（`S-02`/`KI-08`）；
- CI 与本地共用同一 runner 与镜像层，环境变量名单一（`S-01`：`TAG` 是 runner
  读的名字，指南统一 `TAG=latest scripts/run-example.sh go <ID>`）。

**反例（可执行）：go.sum 校验失败（离线 file:// 代理构造）**

- 构造过程（不依赖外网）：本地目录起一个模块 `example.com/greet v1.0.0` 的
  file 代理（`@v/` 下放 `.mod`/`.info`/`.zip`），`go mod tidy` 生成含真实
  `h1:` 校验和的 go.sum；随后把 go.sum 中该行哈希首段改成 `AAAA`。
- 复现命令（实测）：

  ```bash
  docker run --rm -v /tmp/goexp:/exp -w /exp/sumdemo \
    -e GOFLAGS=-mod=mod -e GOSUMDB=off -e GOPROXY=file:///exp/proxy \
    "ghcr.io/zeek-zhao/devbox-go:${TAG:-latest}" go build -o demo .
  ```

- 后果（实测输出，退出码 1）：

  ```
  verifying example.com/greet@v1.0.0: checksum mismatch
      downloaded: h1:yoWmtHwXoUaza1+nGyhmveCNSBjrJKcG92hq1mpB0jA=
      go.sum:     h1:AAAAwHwXoUaza1+nGyhmveCNSBjrJKcG92hq1mpB0jA=

  SECURITY ERROR
  This download does NOT match an earlier download recorded in go.sum.
  The bits may have been replaced on the origin server, or an attacker may
  have intercepted the download attempt.
  ``

  恢复原始 go.sum 后同样命令即绿（`hello devbox`）——证明红只来自校验不一致，
  不是构建流程本身。
