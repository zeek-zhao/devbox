# Go 错误处理指南（G1 · 操作指南）

> 本文只有一个主要承诺：**按本仓库口径，把一段 Go 的错误处理写对**的操作步骤。
> 每一步落到具体用例 ID，命令契约统一为 `TAG=latest scripts/run-example.sh go <ID>`
> （见 [工程参考](工程参考.md) §5）。症状 → 命令 → 判据 → 修复的排查动作在
> [排查手册](排查手册.md)，本文不复述。语法基础归 [知识点清单](知识点清单.md) §1。

## 1. 适用边界（什么时候用 / 什么时候别用）

**用**：你在 `go/examples/` 下写用例、或写带失败路径的业务代码，需要决定
「失败怎么表达、怎么传播、怎么报告」。本仓库只用标准库（`errors` / `fmt.Errorf` /
`errors.Is|As|Unwrap|Join` / `context` / `defer`），无第三方错误处理库；
gofmt / `go vet` 门禁见 [工程参考](工程参考.md) §3。

**别用**：error 接口与 goroutine/channel 语法学习（归 [知识点清单](知识点清单.md) §1，
用例 `L1-027-goroutines`、`L1-028-channels-select-close`）；正在排查一个已发生的
故障时直接去 [排查手册](排查手册.md) 按症状查。

## 2. 最小动线：分类 → 创建 → 匹配 → 包装 → 容错 → 边界 → 报告

七步各自独立成节，按序做完一段错误处理代码就成形；每步给出「做与不做的差别」。

### 2.1 分类：类别 → 动作（E-001-error-taxonomy）

先定类别再写代码：VALIDATION（输入坏，拒绝）/ TRANSIENT（依赖抖动，重试）/
INTERNAL（自身 bug，快速失败）。类别用**自定义错误类型**表达，不用错误码字段——
类型是编译期概念，`errors.As` 沿包装链取类型，包装多少层都不丢类别；
`classify` 对每个错误给出唯一归类，保证同一错误在任何调用点解读一致。
验证：`TAG=latest scripts/run-example.sh go E-001-error-taxonomy`，
末行 `taxonomy types=3 VALIDATION=1 TRANSIENT=1 INTERNAL=1`。

### 2.2 创建：文本带上下文，类型表达语义（E-002-error-create）

`errors.New` 用于纯消息；`fmt.Errorf` 带现场数据（哪个端口、第几次尝试）；
结构化字段（越界的端口值、合法区间）用自定义类型携带。两条红线：
一是错误文本不许只有 `failed`，排查时要知道现场；二是**typed-nil 陷阱**——
成功路径返回具体类型的 nil 指针赋给 `error` 接口后 `err != nil` 恒真，
正确写法是成功路径直接 `return nil`。
验证：`TAG=latest scripts/run-example.sh go E-002-error-create`。

### 2.3 匹配与身份：`errors.Is` / `errors.As`（E-003-error-match、E-005-error-identity）

调用方判定错误只用两件工具：`errors.Is`（判哨兵值身份，沿 `Unwrap` 链）与
`errors.As`（取结构化字段，如 `*ParseError` 的 `Field` / `Line`）。
`==` 只在中间层从不包装时成立，加一层 `fmt.Errorf("...: %w", err)` 就失灵；
两条文本相同的 `errors.New` 身份不同，**按文本判定类别是反模式**（见 §2.10）。
领域规则归一类（如「逾期 ≥30 天即违约」）给错误类型实现自己的 `Is` 方法。
验证：`TAG=latest scripts/run-example.sh go E-003-error-match` 与
`TAG=latest scripts/run-example.sh go E-005-error-identity`。

### 2.4 包装与上下文：`%w` 保链，现场逐层叠加（E-004-error-wrap、E-006-error-context）

中间层传播错误用 `fmt.Errorf("commit log: %w", err)`——加了本层位置
（commit log）又保住根因身份；用 `%v` 会把错误「重造」一遍，
`errors.Is` 判定根因永远失败。需要的现场（主机、用户、步骤）在各自层追加，
不必一次凑齐；用户输入拼进错误文本要引号包裹，防换行/注入搅乱日志。
验证：`TAG=latest scripts/run-example.sh go E-004-error-wrap` 与
`TAG=latest scripts/run-example.sh go E-006-error-context`。

### 2.5 清理：defer 双错误共存（E-007-defer-cleanup）

`defer` 负责清理，但两条规矩：主错误优先返回，清理失败**可见但不覆盖**
主错误；`f.Close()` 的返回值不许随手丢——磁盘满时打印「成功」、数据没落盘。
错误路径提前 return 时清理仍要执行（defer 天然保证），步骤序列可验证。
验证：`TAG=latest scripts/run-example.sh go E-007-defer-cleanup`。

### 2.6 容错：重试 / 超时 / 并发聚合（E-010-retry-backoff、E-011-context-timeout、E-012-error-join）

- **重试**只对 TRANSIENT 类做：指数退避（10/20/40ms）加上限，非重试错误
  （配额超限、参数错）一次都不试，重试耗尽把「第几次失败」包进最终错误。
- **超时**用 `context`：`context.DeadlineExceeded`（预算到了，正常背压）与
  `context.Canceled`（调用方不要了，主动取消）用 `errors.Is` 分辨，
  重试策略因此不同；`context` 取消同时是防 goroutine 泄漏的第一手段
  （泄漏演练见 lab [T-001-goroutine-leak](../labs/T-001-goroutine-leak/WALKTHROUGH.md)）。
- **并发聚合**用 `errors.Join`：N 个分片全部跑完再汇总，成员身份逐个
  `errors.Is` 可判（失败集合里有没有限流），单错/空集退化正确。

验证：`TAG=latest scripts/run-example.sh go E-010-retry-backoff`、
`... E-011-context-timeout`、`... E-012-error-join`。

### 2.7 系统边界：退出码与快速失败（E-009-errno-boundary、E-014-fail-fast)

- 进程边界给**退出码协议**：参数错 2 / 领域失败 3 / 成功 0 / 未分类 70，
  标准库失败用 `errors.Is(err, fs.ErrNotExist)` 判定（稳定接口），
  不 `strings.Contains` 匹配错误文本，不 panic、不 `os.Exit(1)` 一刀切。
- 不变量破坏即快速失败：符号表缺条目就停，不带病运行；库函数不随手 panic
  穿透调用栈，panic 在进程边界 `recover` 转 error（`errors.Is` 可判
  `ErrInvariant`），谁破坏不变量谁的消息进错误链。

验证：`TAG=latest scripts/run-example.sh go E-009-errno-boundary`、
`... E-014-fail-fast`。

### 2.8 报告：只记一次，日志后身份仍在（E-008-error-reraise、E-013-error-observability)

中间层**不吞错**（`err = nil` 与「打日志后 return nil」都是假成功）、
也不抢着记日志——一条错误只在进程边界记一次，结构化字段
（level / msg / err / op）齐备；记完该重抛就重抛，`errors.Is` 判定
身份在日志之后仍然成立。
验证：`TAG=latest scripts/run-example.sh go E-008-error-reraise`、
`... E-013-error-observability`。

## 3. 惯用法与反模式对照表

| 场景 | 惯用法 | 反模式 | 对照用例 |
|---|---|---|---|
| 判定类别 | 自定义类型 + `errors.As` | `strings.Contains(err.Error(), ...)` | E-015 / E-005 |
| 传播 | `fmt.Errorf("ctx: %w", err)` | `%v` 重造错误 / 原样裸抛丢现场 | E-004 |
| 吞错 | 重抛或显式归类 | `err = nil`、log 后 return nil | E-008 |
| 匹配 | `errors.Is` / 自定义 `Is` | `==`（包装即断）/ 按文本 | E-003 / E-015 |
| 日志 | 边界记一次 | 每层都记、日志与返回值不一致 | E-013 |
| panic | 边界 recover 转 error | panic 当流程控制，调用方只得零值 | E-014 / E-015 |
| 成功路径 | `return nil` | 返回 typed-nil 具体指针 | E-002 |

## 4. 真实工作中的变体

- **HTTP 服务**：handler 里 recover panic 转 500（E-014 的边界规则），
  依赖抖动按 E-010 重试，`context` 取消要透传到下游（E-011），
  退出码协议换成 HTTP 状态码分流（E-009 的同构问题）。
- **批量任务**：分片失败用 `errors.Join` 全量聚合（E-012）再决定整批语义，
  而不是首错即停丢掉其余分片的失败信息。
- **毕业项目**（并发任务网关，`go/project/`）：worker pool 的关闭与
  错误聚合（[知识点清单](知识点清单.md) §3 L3 层）直接复用 §2.6 的三件套。

## 5. 评审清单（review 时逐条问）

1. 错误创建带现场了吗（哪个端口、第几次）？还是只有一句 `failed`？（E-002）
2. 中间层包装用 `%w` 还是 `%v`？判定方还能 `errors.Is` 到根因吗？（E-004）
3. 有没有 `== ErrXxx` 会被一层包装打破的判定？（E-003）
4. 有没有按错误**文本**分流的分支？（E-015 / E-005）
5. 清理失败的错误会覆盖主错误吗？`Close()` 返回值去哪了？（E-007）
6. 重试有没有分类（只重试 TRANSIENT）与退避上限？（E-010）
7. 超时与取消分得清吗？`context` 是否透传到底层调用？（E-011）
8. 并发失败是首错即停还是 `errors.Join` 全量聚合？（E-012）
9. 有没有吞错点（`err = nil`、log 后 return nil）？（E-008）
10. 一条错误在日志里出现几次？只在边界记一次了吗？（E-013）
11. 有没有 typed-nil 成功路径？（E-002）
