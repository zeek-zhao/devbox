# E-003-deadlock-retry —— 死锁检测、受害者归因与重试

## 主题映射

语言轨错误处理 E 段「可重试错误与重试预算」（`E-010-retry-backoff`）主题的 db 轨落地：
死锁 1213 是数据库替你检测并裁决的冲突——受害者整体回滚后重试即可成功，
这与不可重试的约束违反（E-002）正好构成一组对照。

## 现象

两个会话按相反顺序更新同一组行：A 先锁 id=1、3，B 先锁 id=2，随后 A 要 id=2、
B 要 id=1，形成环。InnoDB 立即检测死锁并回滚其中一个事务（受害者），
本例通过让 A 持有更多行锁控制裁决方向（权重重的 A 存活，B 成为受害者），
B 收到 `1213` 后整体回滚并重试，最终三个余额与「串行执行」一致。

## 复现命令

```bash
bash db/scripts/run-example.sh db E-003-deadlock-retry
# 或单独跑断言：
```

## 期望输出

与 expected.txt 逐行一致：`deadlock err=1213 victim=b retryable=yes`、
存活方 `a_committed=yes`、重试 `retry attempt=2 ok=yes`，
最终余额（ORDER BY id）`85 / 70 / 95`——没有丢失任何一笔更新（受害事务回滚后按同一业务重试，重试语义以实测为准）。

## 为什么这样处理

- 1213 是「可重试」错误：数据库已经把受害者整体回滚到事务起点，重试不会产生
  半套状态；但重试前必须先 `ROLLBACK`，在失效事务上继续跑只会连环报错。
- 受害者方向靠锁权重控制：A 多持一行再互等，InnoDB 回滚权重轻的 B，
  演示结果因此可复现；真实代码不能依赖受害者方向，只能依赖「1213 后重试」。
- 重试的是**整笔业务**（两条 UPDATE 重新执行），不是报错的那一条——
  事务的原子性边界就是重试的边界。

## 反例

- 捕获 1213 后不回滚直接重试——上一个事务已作废，后续语句全部报错。
- 对 1213 和 1205（锁等待超时）用同一策略但都不回滚——两者都需要先结束当前事务。
- 死了就加 `innodb_lock_wait_timeout` 或绕开检测——环还在，只是换个姿势挂。
