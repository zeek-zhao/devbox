## 所有权与借用（E0502 / E0382 一类编译错）

> 来源：类型 ②——可复现实验（下文 E0502 为 `devbox-rust:latest` 容器实测，
> 输出原样记录）；类型 ①——素材池 `S-06` 作旁证（CI 一片红未必是代码问题，
> 先确认镜像/通路）、`S-01`（用例失败先排除 TAG 变量名不一致这类环境故障）；
> docs/20-开发发布增强.md §3.3「语言特有坑：所有权/借用编译错误阅读」。

### 典型现象

- 编译期报 `error[E0502]: cannot borrow ... as mutable because it is also
  borrowed as immutable`（实测，完整输出见反例）——不可变借用存活期间又取
  可变借用。这是借用检查器**在编译期**拦下的数据竞争，退出码 1，不产生任何
  二进制；
- 编译期报 `error[E0382]: borrow of moved value`（见 `L1-001-string-move`）——
  值被 move 后仍使用；`Copy` 类型（`L1-002-copy-types`）没有此问题；
- 编译期报 `error[E0597]: ... does not live long enough`——借用超出了被借
  值的生命周期（`L1-006-return-lifetimes`、`L1-007-struct-lifetimes` 的考点）；
- 运行期 panic：`RefCell` 双重可变借用 `already borrowed: BorrowMutError`、
  解引用悬垂 `Rc` 后的意外行为（`L1-025-rc-refcell`）——**内部可变性把
  编译期检查推迟到了运行期**，现象从编译错变成 panic；
- （`S-06` 旁证）CI 上用例 FAIL，但 stderr 是 docker 报错（`manifest unknown`）
  而非任何 rustc 诊断——程序根本没被执行过，别按借用问题排。

### 先做的三个检查

1. 报错发生在编译期还是运行期：E0502/E0382/E0597 是编译期（改代码设计）；
   `BorrowMutError` panic 是运行期（改共享策略）——两类修法完全不同；
2. 通读报错的三个标注：`occurs here`（冲突点）、`borrowed here`（借用起点）、
   `later used here`（借用为何还活着）——三个位置连起来就是数据流；
   `rustc --explain E0502` 给教学级解释；
3. 通路与环境先排除：`TAG=latest scripts/run-example.sh rust L0-hello` 先绿，
   CI 与本地 `TAG`/`IMAGE_TAG` 值一致（`S-01`：两名不一致曾让 6 个用例 job
   全红而本地假绿）。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| `E0502 cannot borrow as mutable` | 不可变借用存活期与可变借用重叠（实测见反例） | 读三个标注位置；调整语句顺序或改 owned |
| `E0382 borrow of moved value` | 值被 move 后继续用；或函数按值收参 | `L1-001-string-move` 基准；需要保留就传 `&T` 或 `.clone()`（先想清为何 clone） |
| `E0597 does not live long enough` | 借用比被借值活得久（返回局部引用等） | `L1-006-return-lifetimes`；改返回 owned 或补生命周期标注 |
| 运行期 `BorrowMutError` | `RefCell` 双重可变借用（编译期查不出） | `L1-025-rc-refcell`；把冲突改成结构化（拆字段/改 `Mutex`） |
| 循环引用内存不释放 | `Rc` 环（强引用成环） | `L1-044-weak-cycle`：环上改用 `Weak` |
| CI 红但 stderr 是 docker 报错 | 镜像/环境问题，不是代码问题（`S-06`） | 先跑 `L0-hello` 通路再谈代码 |

### 修复与预防

修复：按报错的三个标注改数据流——要么缩短不可变借用的存活期（提前结束使用），
要么把「可变」操作挪到借用结束后，要么改为 owned 传递；内部可变性场景
（`RefCell`/`Mutex`）把「可能 panic」换成「结构上不可能同时借用」。
预防落成可执行判据：

- 新代码过 `cargo clippy`（`L2-008-clippy-warnings`），不必要的 clone 会被点名；
- 禁止「到处 clone 让编译闭嘴」：评审清单第 4 条（见
  [实践指南.md](实践指南.md) §5）把「用 clone 糊弄借用错」列为打回项；
- 内部可变性只允许有理由地引入，并在用例 README 里说明为何编译期检查不够。

**反例（可执行）：借用冲突（E0502，实测）**

- 错误做法与复现命令：见 [实践指南.md](实践指南.md) §3 反例（同一实验，
  不重复贴码）——`rustc borrow.rs` 退出码 1，报
  `error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable`，
  并给出 `immutable borrow occurs here` / `mutable borrow occurs here` /
  `immutable borrow later used here` 三个标注。
- 后果：编译不过，没有二进制可跑——这是**特性不是缺陷**：同一行为在无
  借用检查的语言里是运行期悬垂指针。把 `v.push(4)` 挪到 `println!` 之后
  即绿（`L1-005-borrow-scope` 的作用域语义）。

## 依赖与 feature（cargo build 冲突 / 离线构建失败）

> 来源：类型 ②——可复现实验（下文 cyclic feature dependency 与 offline
> `no matching package` 均为 `devbox-rust:latest` 容器实测，离线构造，输出原样
> 记录）；类型 ①——素材池 `S-02`/`KI-08`（依赖 `:latest` 类可变引用导致结果
> 漂移）、`S-01`（环境口径不一致的同型故障）；docs/20-开发发布增强.md §3.3
> R2/R3/R4（Cargo.lock 入库、release profile、feature 兼容责任）。

### 典型现象

- `cargo build` 报 `error: cyclic feature dependency: feature `fast` depends on
  itself`（实测，完整输出见反例）——feature 声明自引用或成环，构建直接中止，
  退出码 101；
- 干净环境/`--offline` 下报 `error: no matching package named `...` found`、
  `location searched: crates.io index`（实测）——依赖清单里写了第三方 crate，
  但本地缓存与 vendor 里都没有，离线模式直接失败；
- 「本地能 build，CI 报依赖错误」——本地命中 `~/.cargo` 缓存，CI 是干净环境
  （同型于素材池 `S-01` 的「各跑各的都正常，合到一处就红」）；
- 同一 commit 两次构建依赖树不同——没提交 `Cargo.lock`，或依赖用了浮动版本，
  与 `S-02`（`:latest` 可变标签互相覆盖）同型：引用了会漂移的东西；
- feature unification：`cargo tree` 里的 feature 集合随依赖树变化，同一 crate
  在不同 workspace 里编出的行为不同（docs/20 §3.3 语言特有坑）。

### 先做的三个检查

1. 报错是「feature 声明错误」（cyclic/unknown feature，改 `Cargo.toml`）还是
   「依赖解析失败」（no matching package，查缓存/vendor/网络）——两类入口不同；
2. `Cargo.lock` 在不在库里、feature 声明有没有自引用/环：
   `git status` 看 lock 是否漏提交；`grep -A3 '\[features\]' Cargo.toml`；
3. 本地与 CI 的 cargo 环境是否一致：`cargo --version`、`CARGO_HOME`、
   是否存在 `.cargo/config.toml`（本轨道工具链 `${RUST_TOOLCHAIN}`，
   真本 `images/versions.env`）。

### 定位命令 / 工具

```bash
# 依赖树与 feature 来源：谁把某个 feature 拉进来的
docker run --rm -v "$PWD":/exp -w /exp \
  "ghcr.io/zeek-zhao/devbox-rust:${TAG:-latest}" cargo tree --format "{p} {f}"

# 干净环境复现：临时 CARGO_HOME 隔离本机缓存，看依赖解析是否还成立
docker run --rm -v "$PWD":/exp -w /exp \
  "ghcr.io/zeek-zhao/devbox-rust:${TAG:-latest}" \
  bash -c 'export CARGO_HOME=/tmp/empty-cargo && cargo build --offline'

# 基准用例：feature 健康范式与离线构建范式
TAG=latest scripts/run-example.sh rust L2-006-cargo-features
TAG=latest scripts/run-example.sh rust L2-009-offline-build
```

工具参数见 [工具指南.md](工具指南.md)；workspace/别名等工程配置见
[开发指南.md](开发指南.md)。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| `cyclic feature dependency` | feature 自引用或成环（实测：`fast = ["fast"]`） | 读反例；修正 `[features]` 声明后重试 |
| `no matching package ... offline` | 依赖不在本地缓存且未 vendor（实测：`serde = "1"` 无缓存 + `--offline`） | 反例实测；`cargo vendor` 或去掉依赖 |
| 本地绿 CI 红 | 本地命中 CARGO_HOME 缓存、CI 干净环境才解析失败 | 临时 CARGO_HOME 隔离复现（见定位命令） |
| 依赖树两次构建不同 | `Cargo.lock` 未入库或用浮动版本（`S-02` 同型） | `git status`；`cargo tree` 两次对比 |
| `the package ... does not have a feature named ...` | 命令行/依赖声明里写了不存在的 feature 名 | `grep '\[features\]' -A5 Cargo.toml` 对照 |
| 毕业项目 build 失败 | `rust/project` 仅标准库且有自检（`--self-check`），引依赖破坏确定性 | 读 `rust/project/README.md`，按其约束改 |

### 修复与预防

修复：feature 成环→改 `[features]` 声明，让 feature 只依赖其他 feature 的
「能力」而不自指；离线解析失败→`cargo vendor` 提交 vendor 目录并配
`.cargo/config.toml` 指向它，或回归本轨道默认（仅标准库）。
预防落成可执行判据：

- `Cargo.toml` 与 `Cargo.lock` 必须入库（docs/20 §3.3 R2：锁文件必须入库），
  依赖变更走一次 `cargo build` 让 lock 同步，PR diff 只应出现这两处；
- 可复现场景一律 `--offline` + vendor（`L2-009-offline-build` 基准），
  不依赖外网与镜像层缓存状态；
- feature 命名与组合在 `Cargo.toml` 注释里写明语义（`L2-006-cargo-features`
  的 `diagnostics` 是范例），评审时按此表核对互斥/叠加关系。

**反例（可执行）：feature 循环依赖与离线解析失败（两项实测）**

- 错误做法 1（feature 自引用）：`Cargo.toml` 写 `fast = ["fast"]`。
- 复现命令（实测）：

  ```bash
  docker run --rm -v /tmp/rustexp:/exp -w /exp/featdemo \
    "ghcr.io/zeek-zhao/devbox-rust:${TAG:-latest}" cargo build --offline
  ```

- 后果（实测输出，退出码 101）：

  ```
  error: cyclic feature dependency: feature `fast` depends on itself
  ```

- 错误做法 2（依赖未 vendor 就离线构建）：`Cargo.toml` 加 `serde = "1"`，
  干净缓存下 `cargo build --offline`。
- 复现命令（实测）：

  ```bash
  docker run --rm -v /tmp/rustexp:/exp -w /exp/offdemo \
    "ghcr.io/zeek-zhao/devbox-rust:${TAG:-latest}" cargo build --offline
  ```


- 后果（实测输出，退出码 101）：

  ```
  error: no matching package named `serde` found
  location searched: crates.io index
  required by package `offdemo v0.1.0 (/exp/offdemo)`
  note: offline mode (via `--offline`) can sometimes cause surprising resolution failures
  help: if this error is too confusing you may wish to retry without `--offline`
  ```

  两项修正声明/vendor 后即绿——红只来自声明与清单不一致，不是工具链问题。
