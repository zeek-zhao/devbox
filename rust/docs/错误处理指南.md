# Rust 错误处理指南（G1 · 操作指南）

> 本文只有一个主要承诺：**按本仓库口径，把一段 Rust 代码的错误处理写对**的操作步骤。
> 每一步落到具体用例 ID，命令契约统一为 `TAG=latest scripts/run-example.sh rust <ID>`
> （见 [工程参考](工程参考.md) §5）。症状 → 命令 → 判据 → 修复的排查动作在
> [排查手册](排查手册.md)，本文不复述。

## 1. 适用边界（什么时候用 / 什么时候别用）

**用**：你在 `rust/examples/` 下写用例、或在毕业项目（文本索引）里写业务代码，
需要决定「失败怎么表达、怎么传播、怎么报告」。本仓库只用 Rust 标准库
（`std::error::Error` / `Result` / `Box<dyn Error>`），不引入任何错误处理 crate——
thiserror/anyhow 属于第三方依赖，容器离线不可用（见 [知识点清单](知识点清单.md) §5）。

**别用**：语法学习（`Result`/`Option` 的基本操作归 [知识点清单](知识点清单.md) §2，
用例 `L1-008-option-values`、`L1-009-result-propagation`）；正在排查一个已发生的
故障时直接去 [排查手册](排查手册.md) 按症状查。

## 2. 最小动线：分类 → 表达 → 传播 → 批量 → 容错 → 报告 → 治理

### 2.1 先分类：每个失败点回答「调用方能否有意义地处理」

操作：对每个可能失败的点二选一——外部输入/环境问题（可恢复）用 `Result`；
破坏不变量的状态（不可恢复）用 `panic`/`assert!`。判据：两类失败各跑一次，
可恢复分支回退后继续执行，不可恢复分支终止。
演练用例：`E-001-error-taxonomy`（运行 `TAG=latest scripts/run-example.sh rust E-001-error-taxonomy`，
末行判据 `taxonomy: recoverable=Result, unrecoverable=panic`）。
决策表在 [排查手册](排查手册.md) §2.1。

### 2.2 表达：具体枚举优先，From 转换次之，装箱兜底

操作按序尝试：

1. 调用方需要按类别分支 → 定义具体错误枚举，为一个主要来源实现 `From`，调用点直接 `?`；
   不需要自动转换的调用点用 `map_err` 显式转（选型规则见 [排查手册](排查手册.md) §2.4）。
   演练：`E-004-from-vs-map-err`，判据 `question-mark is From::from: true`。
2. 多种异构来源汇到一个处理边界、又不值得为每种来源建枚举 → `Box<dyn Error>`，
   需要针对性恢复时 `downcast_ref::<T>()` 分流（边界取舍见 [排查手册](排查手册.md) §2.5）。
   演练：`E-005-box-dyn-error`，判据 `heterogeneous errors handled at one boundary: 2`。

### 2.3 传播：`?` 逐层附加语境，保留 source 链

操作：每跨一层业务边界，给 `Err` 包一层「这个层在做什么」的语境（本仓库无
`anyhow::Context`，用自写的 context 包装或在枚举变体里携带层级信息）；顶层报告时
沿 `source()` 链走到底打印根因。禁止吞掉 `source` 只留最外层一句话。
演练：`E-006-context-layering`，判据 `context stack depth: 3`。
source 链规范见 [排查手册](排查手册.md) §2.6。

### 2.4 批量：先选聚合还是短路，再写循环

操作：面向「使用者一次要修完所有问题」的输入（配置、数据导入）→ 聚合，
一次报出全部失败（行号 + 各自原因）；面向「下游只在乎是否可继续」的链路 → 短路。
迭代器里的四种写法语义不同：`collect` 全收、`try_fold` 短路、
`filter_map(Result::ok)` 静默丢错（排障阶段禁用）、`fold` 分区计数。
对照见 [排查手册](排查手册.md) §2.7/§2.9。演练：`E-007-error-aggregation`
（判据 `aggregated: 3 ok, 2 failed`）、`E-009-iterator-error-flow`
（判据 `partition: 3 ok, 1 err`）、`E-010-fail-fast-validation`
（判据 `invalid batch rejected before any side effect: ...`——先整批校验，拒绝发生在任何副作用之前）。

### 2.5 容错：重试与降级都先分类

操作：

1. 重试：错误先分 Transient/Permanent 两类，只有瞬时错误重试，指数退避（1ms、2ms、4ms……）
   加次数上限；永久错误立即上抛。演练：`E-008-retry-backoff`，判据
   `policy: retry transient with exponential backoff, fail fast on permanent`。
2. 降级：主源 → 备用源 → 默认值的链条上，每条结果携带来源标签（via primary/replica/default），
   默认值不许伪装成真值；std 惯用法 `unwrap_or_else`（惰性构造默认值）。
   演练：`E-013-graceful-degradation`，判据 `query \`gone\` -> 0 via default`。

参数口径见 [排查手册](排查手册.md) §2.8/§2.13。

### 2.6 报告：同一错误值，多个视图

操作：给用户/调用方的日志一行话（Display）；给排障的日志 Debug 结构 + 沿 `source`
链单独走一层根因；业务数据走 stdout、诊断走 stderr，诊断行带 `[WARN]`/`[ERROR]`
锚点，收尾一行 `metrics:` 计数。两份视图必须来自同一个错误值，不许手写两份文案。
演练：`E-011-error-display-reporting`（判据 `root cause walk: invalid digit found in string`）、
`E-012-error-observability`（判据 `metrics: processed=3 warned=1 failed=1`）。
分层口径见 [排查手册](排查手册.md) §2.11/§2.12。

### 2.7 治理： unwrap/expect 白名单 + 反模式自查

操作：`unwrap()` 只允许出现在测试与「不可能失败」的不变量处（且写注释说明）；
生产路径用 `expect("语境")` 或完整 `match`。提交前对照三大反模式自查：
`.ok()` 吞错、`Err(String)` stringly-typed、错误后继续跑（坏数据按 0 混入）。
演练：`E-003-unwrap-expect-hygiene`（判据 `unwrap-mode: exit=101`——unwrap panic 的退出码）、
`E-014-antipattern-catalog`（判据 `anti-1 swallowed: true (error cause destroyed by .ok())`）。
治理清单与反模式识别见 [排查手册](排查手册.md) §2.3/§2.14。

## 3. 惯用法与反模式对照表

| 场景 | 惯用法（本仓库口径） | 反模式（可复现后果） |
|---|---|---|
| 一次性错误类型 | 具体枚举 + `impl fmt::Display` + `impl Error`（`source()` 返回根因） | `Err(String)`：调用方只能 `starts_with` 匹配文本（`E-014` anti-2） |
| 错误转换 | 主要来源实现 `From`，调用点 `?`；零散来源 `map_err` | 每个调用点手写重复转换样板；或 `map_err(|e| e.to_string())` 销毁类型 |
| 上下文 | 逐层附加语境 + `source` 链走底 | 只 `.to_string()` 最外层，根因（哪个字段、什么输入）丢失 |
| 批量输入 | 聚合全部失败或整批 fail-fast | 边解析边执行，半批脏数据落库（`E-010` 对照形态） |
| 线程 | 子线程 `Err` 经 `JoinHandle`/通道回收；锁中毒先判定数据一致性再恢复 | 忽略 `join()` 返回值，错误静默消失（`E-015`） |
| 不可恢复 | `assert!`/`panic!` 表达不变量破坏 | 用 `Result` 把 bug 伪装成业务分支，真假失败混在一起（`E-001` 反例） |

## 4. 真实工作中的变体

- **错误类型随边界收敛**：库里层枚举细、应用层聚合粗——本仓库用 `Box<dyn Error>`
  模拟应用层聚合（`E-005`），真实服务里对应「库返回具体错误、main 只留日志边界」；
  本仓库无法演示进程级恢复策略（重启/熔断），容器内无真实流量，属
  [知识点清单](知识点清单.md) §5 不覆盖范围。
- **重试策略配置化**：`E-008` 把退避参数写死在演示里；真实工程由配置/环境变量下发。
  本仓库环境变量口径见 [工程参考](工程参考.md) §5，不引入配置框架。

## 5. 评审清单（review 时逐条问）

1. 每个失败点分类了吗？可恢复/不可恢复的出口对吗（`Result` vs panic）？
2. 错误类型能按类别分支吗（枚举变体，不是字符串文本）？
3. 跨层语境加了吗？`source()` 链走到根因了吗？
4. 批量路径选了聚合还是短路？选型理由说得出吗？
5. 有没有 `.ok()`、`unwrap`（测试外）、错误后继续跑？
6. stdout/stderr 分流了吗？失败计数有没有 `metrics:` 收尾？
7. 本条改动对应的演练用例跑绿了吗（`TAG=latest scripts/run-example.sh rust <ID>`）？
