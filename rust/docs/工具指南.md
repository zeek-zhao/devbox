# Rust 工具指南（G4）

> 「是否预装」全部在 `ghcr.io/zeek-zhao/devbox-rust` 镜像里实测过（2026-11-05，
> probe 命令见 §1 脚注），不是抄 README。版本一律引用 `images/versions.env` 变量名，
> 实测输出里的具体版本号不写进文档——以容器当场输出为准。

## 1. 工具全景表

| 工具 | 用途 | 本工程是否预装 | 版本来源 |
|---|---|---|---|
| cargo | 构建 / 测试 / 运行统一入口 | 是（`/usr/local/cargo/bin/cargo`） | 随 `${RUST_TOOLCHAIN}`（images/versions.env） |
| rustc | 编译器 | 是 | 随 `${RUST_TOOLCHAIN}` |
| rustfmt / cargo fmt | 格式化 | 是（rustup component 显式补装） | 随 `${RUST_TOOLCHAIN}` |
| clippy（cargo clippy / clippy-driver） | lint（CI 门禁的一部分） | 是（rustup component 显式补装） | 随 `${RUST_TOOLCHAIN}` |
| rustup | 工具链与组件管理 | 是 | 随镜像构建 |
| rust-gdb / rust-lldb | 调试器包装（底层 gdb / lldb 已装） | 是（`/usr/bin/gdb`、`/usr/bin/lldb` 实测在） | 随底座层 |
| rust-analyzer | LSP 语言服务器 | 否——`/usr/local/cargo/bin` 有 rustup 代理链接，但 minimal profile 未装该组件，运行报 `Unknown binary 'rust-analyzer'`（实测） | 需 `rustup component add rust-analyzer` |
| miri | UB / 未定义行为解释执行 | 否（同上：代理在、组件未装，实测报错） | 需 `rustup component add miri` |
| bacon / cargo-watch / sccache | 第三方效率工具 | 否（实测 `command -v` 无结果） | 需自装 |

复跑实测的 probe 命令：

```bash
docker run --rm "ghcr.io/zeek-zhao/devbox-rust:${TAG:-latest}" bash -lc \
  'cargo --version; rustc --version; rustfmt --version; cargo clippy --version;
   command -v gdb lldb; rustup component list --installed;
   command -v rust-analyzer && rust-analyzer --version 2>&1 | head -1'
```

## 2. 每工具一节

### 2.1 cargo（build / test / clippy）

- 装在哪：镜像内 `/usr/local/cargo`（rustup 安装，ENV 已固化 `RUSTUP_HOME`/
  `CARGO_HOME` 与 USTC 镜像源，勿在命令行覆盖）。
- 怎么调：容器内直接 `cargo ...`；宿主走 `bash rust/project/build.sh`
  （无 cargo 时自动落容器）。
- 常用参数速查：

```bash
cargo run --example <名>               # 跑 project/examples
cargo fmt --all -- --check             # 格式化检查（build.sh 第一步）
cargo clippy --offline --all-targets -- -D warnings   # lint，警告=错误（build.sh 门禁）
cargo test --offline --all-targets --all-features     # 全部测试
cargo build --release --offline        # 离线发布构建（Cargo.lock 锁定）
```

- 用例参考：lib+bin 工程结构见 L2-001-cargo-lib-bin，fmt 门禁见 L2-007-fmt-check，
  clippy 见 L2-008-clippy-warnings，离线构建见 L2-009-offline-build，
  std 基准见 L3-005-std-benchmark。

### 2.2 rustfmt / cargo fmt

- 怎么调：工程内 `cargo fmt --all -- --check`；全仓口径统一走
  `bash scripts/fmt.sh --lang rust`（`--check` 只查不改，CI 用它），格式化器只活在
  镜像里，宿主没有。
- 仓库根 `rustfmt.toml` 是格式规则真本，改它属门禁变更，走 T0 §3 的例外流程。

### 2.3 clippy

- 怎么调：`cargo clippy --offline --all-targets -- -D warnings`。
  `-D warnings` 把警告提级为错误，是 `build.sh` 的硬门禁。
- 单条规则豁免用 `#[allow(clippy::lint_name)]` 就地标注并写注释，不许全局放宽。

### 2.4 rust-gdb / rust-lldb

- 怎么调：`rust-gdb ./target/debug/app`（gdb）或 `rust-lldb ./target/debug/app`；
  底层 gdb、lldb 都在镜像里（实测 `/usr/bin/gdb`、`/usr/bin/lldb`）。
- 包装器会加载 Rust 的 pretty-printer，比裸 gdb/lldb 的变量显示可读。

### 2.5 rust-analyzer / miri（代理在、组件未装）

- 现象：`command -v rust-analyzer` 能找到文件，一跑就报
  `Unknown binary 'rust-analyzer' in official toolchain`——minimal profile 只装了
  rustc/cargo/rust-std + clippy/rustfmt，其余组件的 rustup 代理链接是空壳。
- 需要 LSP 就在容器内 `rustup component add rust-analyzer`；需要查 UB 就
  `rustup component add miri` 再 `cargo +nightly miri test`（miri 组件对 stable
  工具链不可用，实测报错）。装组件会联网，走镜像内 USTC 镜像源。

## 3. 选型对比

- 格式化器：不适用：无同类——rustfmt 是社区事实标准唯一格式化器。
- lint：rustc 内置 lint（预装、随编译器）对比 clippy（预装、rustc lint 的严格超集、
  进 build.sh 门禁）。工程门禁选 clippy：规则覆盖面大得多且版本随工具链走，CI 可重现。
- 调试器：rust-gdb 对比 rust-lldb，两者都预装，功能对等；Linux 容器内 gdb 栈回溯
  更稳，默认用 rust-gdb。

## 4. 常见误用

1. **在宿主机直接敲 cargo / rustfmt**：宿主（Windows 开发机、CI 构建机）没装 Rust
   工具链，必然 command not found。格式化器和被测代码一样只能活在镜像里；宿主入口是
   `bash scripts/fmt.sh --lang rust` 或 `bash rust/project/build.sh`（自动落容器）。
2. **把 rust-analyzer「能找到」当成「能用」**：`/usr/local/cargo/bin` 下的链接只是
   rustup 代理，minimal profile 未装组件，一跑就报 Unknown binary。先
   `rustup component list --installed` 确认，再按需 `rustup component add`。
3. **加依赖后仍用 `--offline` 构建报错**：`--offline` 依赖 Cargo.lock 已锁定且
   registry 缓存齐全；新增依赖要先联网 `cargo fetch`（走镜像内镜像源）更新 lock，
   提交 lock 一起进 git，再谈离线。
4. **clippy 警告「先攒着以后修」**：门禁是 `-D warnings`，一个警告就是红灯；
   局部豁免必须 `#[allow(...)]` 就地标注 + 注释理由，禁止整体降级或全局放宽。
