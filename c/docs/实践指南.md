# C 实践指南（G1）

> 回答「什么时候用 C 轨道的哪类用例、不用会怎样、怎么验证真的学会了」。
> 语法细节归 L1 用例（见 [知识点清单.md](知识点清单.md)），本篇只讲工程用法，不重复语法。
> 命令契约（规范 §4.3）：统一 `TAG=latest scripts/run-example.sh c <ID>`；
> 版本号只写 `images/versions.env` 的变量名（`${GCC_MAJOR}` / `${CLANG_MAJOR}`，版本引用契约 §4.4）。
> 注意：C 轨道复用 `devbox-cpp` 镜像层（同一套 gcc/clang 工具链，映射真本是 `images/lang-images.tsv`），
> 所以 c 的用例容器与 C++ 是同一个镜像——这不是写错。

## 1. 适用边界（什么时候用 / 什么时候别用）

**什么时候用本轨道**：你要在 devbox 体系里练 C 工程能力——L1 语言基础
（类型、指针、内存管理）、L2 构建与诊断（多文件构建、sanitizer、gdb）、
L3 数据结构与专题（内存池、位运算、序列化），共 78 个用例；终点是 `c/project`
的毕业项目。每一层都用「可观察判据」验收：用例跑通、输出与 `expected.txt`
逐行一致（见 [用例编写规范.md](用例编写规范.md)）。

**什么时候别用本指南**：

- 想学某个语言特性本身（指针运算规则、位域布局）——直接跑对应 L1 用例，
  指南不讲语法，读了也学不会；
- 想找某个具体报错的排查路径（越界、泄漏、未定义引用）——去
  [问题指南.md](问题指南.md)（G3，按问题域组织：内存与越界、构建与链接）；
- 想用 RAII、类、模板这类 C++ 设施——去 cpp 轨道；本轨道只覆盖 C
  （`${GCC_MAJOR}` 默认 `-std=c17` 一系的写法），把 C++ 写法混进 C 用例不会通过评审。

**反例（可执行）**

- 错误做法：把本指南当语法书，跳过用例直接背结论。
- 复现命令（语法考点的「正主」在清单与用例里，不在指南里）：

  ```bash
  grep '| L1-020-malloc-free' c/docs/知识点清单.md
  ```

  输出会指向用例 `L1-020-malloc-free`（考点行：动态分配、检查分配结果并释放）——
  内存管理知识点的载体是用例，不是本篇。
- 后果：只读不跑，等于没碰过编译器；malloc/free 的错误只有 sanitizer 和
  用例判据能教给你。正确动作是
  `TAG=latest scripts/run-example.sh c L1-020-malloc-free`。

## 2. 最小可运行示例（指向具体用例 ID）

入口是 `L0-hello`——L0 是通路验证层（`KI-05` 定案：L0 表示镜像与 runner
通路验证，不属于知识难度层级），它验证镜像能编译并运行 C，与任何知识点无关：

```bash
TAG=latest scripts/run-example.sh c L0-hello
# 实测输出：c/L0-hello                    PASS (0s)
```

通路没验证之前，不要碰 L2/L3 用例。

**反例（可执行）**

- 错误做法：不验通路，直接上依赖最重的用例。
- 复现命令（把 `TAG` 指向一个不存在的标签，模拟「镜像/tag 出问题」这一最常见
  环境故障）：

  ```bash
  TAG=nosuchtag scripts/run-example.sh c L2-006-asan-bounds
  ```

- 后果（实测）：runner 输出
  `c/L2-006-asan-bounds          FAIL (exit!=0, 2s)`，stderr 含
  `docker: Error response from daemon: manifest unknown.`，退出码非零。
  通路用例 1 秒就能把这类环境问题暴露出来；不验通路时，同样的错误会发生在
  你等得最久的那一步，且极易被误读成「代码有问题」（素材池 `S-06`）。

## 3. 惯用法与反模式对照表（含可复现反例）

| 惯用法 | 反模式 | 为什么 |
|---|---|---|
| 一律经 runner 跑用例 | 手写 `docker run` / `gcc` 复刻 runner 的行为 | CI 与本地共用 runner 真本（`scripts/run-example.sh`）；口径分裂会造成「本地假绿」——规范 §4.3 记录过 TAG 与 IMAGE_TAG 名字不一致导致 6 个用例 job 全红的真实事故 |
| 内存类代码一律带 `-g -fsanitize=address` 编译验证（`L2-006`/`L2-009`） | 裸 `gcc -O2` 编译完就算完 | 越界读在裸编译下完全静默（实测反例见下）；sanitizer 把它变成一行可定位的报告 |
| `malloc` 返回值判空、释放后置空指针（`L1-020`、`L1-023-double-free-guard`） | 不判空直接解引用、同一个指针 free 两次 | 分配可能失败；double free 是崩溃率最高的一类错误，`L1-023` 的置空写法让重复清理天然安全 |
| 头文件自带 include guard、自带全部声明（`L1-034-include-guard`、`L2-003-header-dependency`） | 依赖「调用方碰巧先包含了某个头」的包含顺序 | 相互包含与隐式声明问题都来自这个依赖；`L2-003` 用前置声明打断类型依赖是现成范例 |
| 多文件工程交给 make/CMake 管理依赖与链接顺序（`L2-001-multifile-build`、`L2-002-makefile-incremental`） | 手敲一长串 gcc 命令、漏链目标文件 | 手敲链不完就是 `undefined reference`（见问题指南 §构建与链接 实测）；构建系统还能管增量编译与头文件依赖 |
| 版本号只引用 `images/versions.env` 变量（`${GCC_MAJOR}`、`${CLANG_MAJOR}`） | 在文档/脚本里手写版本常量 | 升级时手写常量集体过期，且过不了 `scripts/check-version-truth.sh` |

**反例（可执行）：裸编译的越界读静默通过**

- 错误做法：越界读程序不开 sanitizer，`-O2` 编译运行，以为「能跑就是对的」。

  ```c
  #include <stdlib.h>
  #include <stdio.h>
  int main(void) {
      int *p = malloc(4 * sizeof(int));
      if (!p) return 1;
      printf("%d\n", p[7]);   /* 越界读：堆对象之后 16 字节 */
      free(p);
      return 0;
  }
  ```

- 复现命令（镜像 tag 经变量传入，容器真本为 `images/lang-images.tsv` 映射到
  `devbox-cpp` 层）：

  ```bash
  docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:${TAG:-latest}" bash -c \
    'printf "%s\n" "#include <stdlib.h>" "#include <stdio.h>" "int main(void) { int *p = malloc(16); if (!p) return 1; printf(\"%d\n\", p[7]); free(p); return 0; }" > /tmp/oob.c && gcc -std=c17 -O2 /tmp/oob.c -o /tmp/oob && /tmp/oob'
  ```

- 后果（实测）：输出 `0`，退出码 `0`——越界读无任何报错，脏数据直接进输出。
  同一程序加 `-fsanitize=address` 立即报
  `ERROR: AddressSanitizer: heap-buffer-overflow`（完整报告见问题指南
  §内存与越界）；现成基准用例 `L2-006-asan-bounds` 实测
  `TAG=latest scripts/run-example.sh c L2-006-asan-bounds` → `PASS (1s)`。

## 4. 真实工作中的变体

**变体 1：本地已自建镜像（`make images` 或 `scripts/build-images.sh`）**
runner 的 `TAG` 取值顺序是 `TAG` → `IMAGE_TAG` → `local`（真本
`scripts/run-example.sh`），本地调试自建镜像时不用传 `TAG`（默认 `local`），
或显式 `TAG=local scripts/run-example.sh c <ID>`。`local` 只是本地约定名，
不要写死进文档或 CI 配置。

**变体 2：需要可复现的构建结果**
`:latest` 随 `main` 变动（ROADMAP `KI-08`；历史 bug `#184`：并发 PR 互推
`:latest` 互相覆盖被测镜像）。复现某个历史结果时用 CI 每次构建都打的
`sha-<commit>` 标签：`TAG=sha-<commit-sha> scripts/run-example.sh c <ID>`。

**变体 3：整轨回归**
改动波及面大（升级编译器标准、动公共构建配置）时跑全轨 78 例，与 CI 的
`examples` job 同款入口：`TAG=latest scripts/run-example.sh c --all`。
内存类用例（`L2-006`/`L2-009`）也在这一步一起验，不要因为「本地单例跑过」
就跳过整轨。

**反例（可执行）**

- 错误做法：CI 一片红就当「用例代码坏了」去改代码，不先看报错发生在哪一层
  （素材池 `S-06`：镜像探测失败被误读为代码问题）。
- 复现命令（报错里根本没有 gcc/ld 的影子——镜像 pull 阶段就死了）：

  ```bash
  TAG=nosuchtag scripts/run-example.sh c L2-006-asan-bounds
  # 实测 stderr：Unable to find image 'ghcr.io/zeek-zhao/devbox-cpp:nosuchtag' locally
  #            docker: Error response from daemon: manifest unknown.
  ```

- 后果：对着一个根本没被执行过的二进制改代码，白烧一轮排查；正确动作是先看
  报错阶段（pull / 编译 / 运行），环境问题先修环境（见问题指南）。
