# C 用例编写规范

本规范面向 `c/examples/`。示例以 ISO C17 和 libc 为边界，使用仓库现有的 C/C++ 工具链；每个用例都应能独立编译、运行并得到可复现的判定结果。

## 1. 用例目录契约

每个用例目录恰好包含三个文件，各自承担唯一职责：

```text
c/examples/<ID>/
├── run.sh          # 编译并运行，只往 stdout 输出业务结果
├── expected.txt    # 逐行精确匹配的预期输出
└── README.md       # 考点、判据、易错边界及复现命令
```

不要把 `.c`、可执行文件、对象文件或临时构建目录留在用例目录。单文件源代码可以写在 `run.sh` 的临时 heredoc 中；多文件构建也应把生成的源码和产物放在 `${TMPDIR:-/tmp}` 下。统一 runner 是 `scripts/run-example.sh`，不要为单个用例另造比较流程。

编号用 `L1-...`、`L2-...`、`L3-...` 表示知识点难度；`L0-hello` 是通路验证层，`hello` 已在 KI-05 统一更名为 `L0-hello`。除该统一迁移外，已有目录名不可改。

## 2. `run.sh` 怎么写

1. 文件开头必须是 `#!/usr/bin/env bash` 和 `set -euo pipefail`，脚本必须可执行。
2. 使用 `gcc` 或 `clang` 编译，显式指定 `-std=c17`；常规用例可使用 `CC="${CC:-gcc}"` 并启用 `-Wall -Wextra -Werror`。不要依赖编译器默认标准或 GNU 扩展。
3. 编译与运行都在 `run.sh` 中完成。可执行文件、临时源码、日志和构建目录放到 `${TMPDIR:-/tmp}`；不要把生成物写入仓库。
4. stdout 仅保留业务结果。编译诊断、调试信息和进度写 stderr；失败必须以非零退出码报告，不能用 `|| true` 吞掉。
5. 一个用例需要多次编译、比较诊断或检查 sanitizers 时，脚本要明确验证每个预期条件；非预期编译/运行失败仍须使脚本失败。

示意的单文件编译方式：

```bash
CC="${CC:-gcc}"
OUT="${TMPDIR:-/tmp}/devbox-c-L1-001-types-sizes"
"$CC" -std=c17 -Wall -Wextra -Werror main.c -o "$OUT"
"$OUT"
```

用例源文件若通过 heredoc 生成，先将其写到临时目录，再把该临时源文件传给编译器。具体用哪个编译器和选项应服从该用例所验证的内容，例如 ASan、UBSan、GCC analyzer 或 `-O0`/`-O2` 对照。

## 3. `expected.txt` 匹配规则

实际 stdout 与 `expected.txt` 逐行精确比较；统一 runner 忽略行尾空白以及输出首尾的空行，但不忽略内部空行，也不替你排序、改写错误输出或归一化动态内容。文件应只包含预期业务输出，不带行尾空格。

更改期望值前先修正程序或测试判据，再运行用例核对实际输出。不要把当前错误输出直接更新成期望值。

## 4. 输出确定性：C 专属边界

- **不打印指针地址。** `%p` 的结果会受 ASLR、进程布局和实现影响。输出稳定的对象内容、相对偏移或布尔关系；指针相减仅在同一数组对象内有效，结果类型为 `ptrdiff_t`。
- **不把 `sizeof(struct)` 当成跨平台常数。** 成员间及尾部 padding 受 ABI、对齐和编译器影响。验证布局时检查成员偏移、对齐关系，或断言 `sizeof(struct) >=` 各成员大小之和；不要断言某个固定字节数。
- **浮点输出明确格式。** 使用固定小数位（例如 `printf("%.3f", value)`），容差判定也要给出固定阈值；不要依赖默认输出精度或打印耗时作为结果。
- **实现定义行为必须点名实现。** 例如通过 union 的非当前成员观察类型表示时，要在 README 写清“这里依赖 GCC/Clang 在本运行目标上的实现行为，不是 ISO C17 对所有实现的保证”，并把期望输出限定为当前工具链/目标。不要把它描述成通用语言保证。
- 集合或排序结果使用固定输入并显式排序；不输出地址、时间、随机数、主机信息、用户目录或绝对路径。
- 同一用例连续运行三次，stdout 必须逐字节一致。平台相关值不能伪装成普遍事实：要么断言平台无关的性质，要么明确限定实现和目标。

## 5. 内存用例的有效判据

进程退出码为 0 只说明程序正常结束，**不能单独证明没有泄漏、越界或释放后使用**。内存安全结论必须来自实际检查器或明确可验证的所有权/边界断言：

- 泄漏检测使用现有用例采用的 AddressSanitizer/LeakSanitizer（如 `-fsanitize=address` 配合 `ASAN_OPTIONS=detect_leaks=1`），或使用 `valgrind --error-exitcode=<非零值>`。脚本应检查工具的退出状态和预期诊断；若用例故意制造缺陷，应验证检查器确实报告缺陷，而不是把失败吞掉。
- 越界等错误使用对应 sanitizer，例如 AddressSanitizer；未定义行为用例使用 UBSan 并确认诊断。说明所测缺陷类别，不能把一种检查器的结果泛化成“所有内存安全都通过”。
- 纯粹展示 `malloc`/`free` 或统一清理路径的用例，应逐条覆盖成功和失败分支，确认每个拥有的分配恰好释放一次；README 说明可观察的资源判据。若声称通过运行时泄漏检查，就必须真的运行检查器。

仓库实例：`L2-009-leak-detection` 使用 ASan/LeakSanitizer 检查泄漏；`L2-006-asan-bounds` 检查堆越界；`L2-007-ubsan-overflow` 检查有符号溢出。

## 6. 加新用例的步骤

1. 先选对层级并查看同层最后一个序号，使用 `L<层级>-<三位序号>-<小写短横线名称>`；不要改已有 ID。`L0-hello/` 仅作通路验证参考，不是编号模板。
2. 参考最接近的现有 C 用例：普通单文件可参照 `c/examples/L1-001-types-sizes/`；多文件编译参照 `L2-001-multifile-build/`；泄漏检查参照 `L2-009-leak-detection/`；L3 算法参照对应专题用例。复制其目录结构和 runner 写法，不复制不相关的断言。
3. 编写 `run.sh`、`expected.txt` 和 `README.md` 三个文件。替换 ID、临时目录名、编译选项、考点说明和实际期望输出；README 写明判据、边界及可复现命令。
4. 实际编译运行并核对预期输出；需要额外检查时，让脚本对检查器报告、错误码或断言作明确判定。确认仓库没有生成文件，且三次 stdout 一致。
5. 在仓库根目录执行：

   ```bash
   bash scripts/run-example.sh c <ID>
   ```

   本轨道完整验收使用 `bash scripts/run-example.sh c --all`，覆盖表检查使用 `bash scripts/coverage-check.sh c --strict`。改动后还要按公共门禁运行 C 格式检查。

## 7. 常见错误清单

| 错误 | 为什么不可靠 | 对应真实用例 |
|---|---|---|
| 打印 `%p` 并把某次地址写进期望文件 | 地址随 ASLR 和进程布局变化 | `L1-005-pointer-arithmetic`、`L1-006-pointer-diff` |
| 把结构体 `sizeof` 写成固定数字 | padding、成员对齐和 ABI 会改变大小 | `L1-009-struct-layout`、`L1-010-struct-padding` |
| 将 union 类型双关结果说成 ISO C 保证 | 读取非当前成员的解释依赖实现 | `L1-013-union-type-punning` |
| 把变长数组当成任意长度都能安全分配 | 自动存储空间有限，支持情况和边界需谨慎处理 | `L1-025-vla-limits` |
| 仅凭退出码 0 宣称没有泄漏 | 普通退出不检测仍可达或遗失的分配 | `L1-022-memory-leak-pattern`、`L2-009-leak-detection` |
| 直接把 `realloc` 结果覆盖原指针 | 分配失败时原块仍有效，覆盖会丢失唯一所有权 | `L1-021-calloc-realloc` |
| 用 `a - b` 写 `qsort` 比较器 | 整数相减可能溢出，比较器应返回负/零/正关系 | `L1-027-stdlib-qsort` |
| 对有符号值随意移位或用未检查加法处理边界 | 可能触发未定义行为或溢出 | `L1-012-bitops`、`L3-016-overflow-safe-add` |

## 8. 现有工具链与平台边界

C 用例限定 ISO C17 与 libc，不以 POSIX API（例如 `pthread`、`mmap`、`epoll`）作为轨道契约。编译器工具链与 C++ 轨道共用；常规脚本通过 `gcc` 或兼容的 `clang` 进行显式 C17 编译。GCC analyzer、GDB、ASan/LeakSanitizer、UBSan 等用例依赖镜像中相应工具及运行时，不能把它们的存在说成 ISO C 标准保证。

L3 中 `L3-001-alignment` 的数值受当前 ABI 与编译器实现的对齐规则影响；`L3-011-endianness` 会报告当前机器字节序。应以用例实际断言为准，不可将本机观察推广到所有平台。当前 L3 清单没有 epoll、mmap 或 pthread 用例。
