## 内存与越界（越界访问、泄漏、重复释放）

> 来源：类型 ②——可复现实验（下文 ASan / LeakSanitizer / valgrind 输出均为实测）；
> 类型 ①——素材池 `S-06` 作旁证：CI 一片红报「用例 FAIL」未必是内存 bug，
> 镜像 pull 失败也会长这个样，先确认二进制真的被执行过（docs/24-G3素材池.md S-06）。

### 典型现象

- 运行期崩溃或输出脏数据，且换优化级别后现象漂移（不开 `-O2` 好好的，开了就错）
  ——未定义行为的典型面貌（docs/20-开发发布增强.md §3.1 语言特有坑）。带 ASan
  重跑后是可观察的一行定位（实测）：
  `ERROR: AddressSanitizer: heap-buffer-overflow on address 0x50200000002c`、
  `READ of size 4 at 0x50200000002c thread T0`；
- 进程内存随运行时间线性增长（如 `ps -o rss` 反复采样只涨不跌）；进程退出时
  泄漏检测器报数（实测）：
  LeakSanitizer：`Direct leak of 768 byte(s) in 3 object(s) allocated from:`；
  valgrind：`768 bytes in 3 blocks are definitely lost in loss record 1 of 1`；
- 程序在 free 之后崩溃（use-after-free），或一释放就 abort（double free，
  见 `L1-023-double-free-guard`）；
- （`S-06` 旁证）CI 上整片用例 FAIL，但 stderr 里是 docker 报错（
  `manifest unknown`）而不是任何 C 诊断——代码根本没被执行过。

### 先做的三个检查

1. 编译是否带了 `-g -fsanitize=address`——没带先带上重跑，越界与泄漏大多
   直接现形（`L2-006` / `L2-009` 就是这个基准）；裸 `-O2` 下越界读是静默的（实测见下）；
2. 报错发生在哪个阶段：pull（镜像）/编译（gcc 诊断）/链接（ld）/运行
   （ASan 报告）——阶段不同，问题域完全不同；报错在 pull 阶段先修镜像，别动代码（`S-06`）；
3. 跑的是不是你改过的代码：runner 拉的镜像 tag 对不对（`TAG=latest`，C 复用
   `devbox-cpp` 层）、本地有没有未提交的旧二进制。

### 定位命令 / 工具

```bash
TAG=latest scripts/run-example.sh c L2-006-asan-bounds    # ASan 越界基准用例
TAG=latest scripts/run-example.sh c L2-009-leak-detection # LeakSanitizer 泄漏基准用例
docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:${TAG:-latest}" bash -c \
  'gcc -std=c17 -g -fsanitize=address your.c -o your && ./your'   # 单独复现
docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:${TAG:-latest}" bash -c \
  'gcc -std=c17 -g your.c -o your && valgrind --leak-check=full ./your'
```

工具速查见 [../cpp/docs/工具指南.md](../cpp/docs/工具指南.md)；gdb 批量抓栈见
`L2-008-gdb-batch-backtrace`。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| ASan `heap-buffer-overflow` READ | 索引算错 / 长度没算结尾 `'\0'` / 指针运算越出数组 | 报告自带分配点栈帧；对照 `L1-005-pointer-arithmetic` 检查步进语义 |
| ASan `heap-buffer-overflow` WRITE | 写越界（缓存区设小、`strcpy` 无上限） | 同上；换 `L3-006-dynamic-array` 的增长写法 |
| LeakSanitizer direct leak | 忘 `free` / 提前 `return` 绕过释放 / 所有权没人接 | 报告给出分配栈；`L1-022-memory-leak-pattern` 是泄漏模式清单 |
| ASan double-free / invalid free | 重复释放 / 释放了栈上指针 | `L1-023-double-free-guard`：释放后置空 |
| 只在 `-O2` 下出错 | 未定义行为，不是编译器 bug | `-fsanitize=address,undefined`（`L2-007-ubsan-overflow`） |
| 用例 FAIL 但 stderr 是 docker 报错 | 镜像/环境问题，不是代码问题（`S-06`） | `docker pull` 验证 tag；先看 probe job |

### 修复与预防

修复：按报告里的分配/释放栈修——越界改边界判断，泄漏补 `free` 或把所有权
集中到一处，double free 按置空模式改写。

预防（落成测试与 lint 规则，不是口头约定）：

- 内存类代码进用例必须带 `-fsanitize=address` 验证（`L2-006`/`L2-009` 的
  run.sh 已按此约定）；泄漏模式直接对照 `L1-022-memory-leak-pattern` 逐条自查；
- 警告当错误：`-Wall -Wextra`（`L2-010-strict-warnings`）能提前抓住隐式声明、
  未初始化等一大类根因；静态分析用 `-fanalyzer`（`L2-011-gcc-analyzer`）。

**复现实验 1：越界读（ASan 实测）**

```bash
docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:latest" bash -lc \
  'cat > /tmp/oob.c <<"EOF"
#include <stdlib.h>
#include <stdio.h>
int main(void) {
    int *p = malloc(4 * sizeof(int));
    if (!p) return 1;
    printf("%d\n", p[7]);   /* 越界读：堆对象之后 16 字节 */
    free(p);
    return 0;
}
EOF
gcc -std=c17 -g -fsanitize=address /tmp/oob.c -o /tmp/oob && /tmp/oob'
```

实测输出（节选，退出码 1）：

```
==27==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x50200000002c ...
READ of size 4 at 0x50200000002c thread T0
    #0 ... in main /tmp/oob.c:6
0x50200000002c is located 12 bytes after 16-byte region [0x502000000010,0x502000000020)
SUMMARY: AddressSanitizer: heap-buffer-overflow /tmp/oob.c:6 in main
```

同一程序裸 `gcc -std=c17 -O2` 编译运行：输出 `0`、退出码 `0`——
这就是「不开 sanitizer 什么都看不出来」的实测对照。

**复现实验 2：漏 free（LeakSanitizer 与 valgrind 实测）**

```bash
docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:latest" bash -lc \
  'cat > /tmp/leak.c <<"EOF"
#include <stdlib.h>
#include <stdio.h>
char *cache_reset(void) {
    char *buf = malloc(256);
    return buf;              /* 调用方接了指针但没人释放 */
}
int main(void) {
    for (int i = 0; i < 3; i++) {
        cache_reset();       /* 每轮丢 256 字节 */
    }
    puts("done");
    return 0;
}
EOF
gcc -std=c17 -g -fsanitize=address /tmp/leak.c -o /tmp/leak && /tmp/leak'
```

实测输出（LeakSanitizer，退出码 1）：

```
Direct leak of 768 byte(s) in 3 object(s) allocated from:
    #1 ... in cache_reset /tmp/leak.c:4
    #2 ... in main /tmp/leak.c:9
SUMMARY: AddressSanitizer: 768 byte(s) leaked in 3 allocation(s).
```

同一二进制换 valgrind（`gcc -std=c17 -g` 不带 ASan）实测：

```
==27== 768 bytes in 3 blocks are definitely lost in loss record 1 of 1
==27==    definitely lost: 768 bytes in 3 blocks
```

## 构建与链接（编译错误、头文件、未定义引用）

> 来源：类型 ②——可复现实验（缺头文件与未定义引用均为实测）；
> 类型 ①——docs/20-开发发布增强.md §3.1：C/C++ 语言特有坑（头文件与库版本错配、
> ABI 与结构体布局），并按该节要求把「链接期 / 运行期」分开看。

### 典型现象

- 编译期（实测）：`main.c:1:10: fatal error: config.h: No such file or directory`
  ——头文件找不到，`#include` 那行直接指认；
- 链接期（实测）：`/usr/bin/ld: app.c:(.text+0xa): undefined reference to 'vec_len'`
  ——编译全过，最后 `ld` 拒绝出产物；
- 单文件能过、多文件不过：include guard 缺失时的重复定义
  （`multiple definition of ...`），或互相包含导致递归展开（`L1-034-include-guard`、
  `L2-003-header-dependency` 的考点）；
- 「本地过、CI 不过」或换机器后行为变化：编译器/优化级别不同触发未定义行为
  （docs/20 §3.1 语言特有坑；`L2-020-optimization-consistency` 的考点）。

### 先做的三个检查

1. 报错停在哪个阶段：gcc 停在编译期（`error:` 行首是文件名:行号）还是 ld 停在
   链接期（`undefined reference`）——两者修法完全不同，别混着改；
2. 头文件搜索路径：`gcc -H -fsyntax-only main.c` 打印整棵包含树，看缺的头到底
   找过哪些路径、`-I` 传了没有；
3. 符号到底在不在：`nm app.o | grep vec_len`——`U` 表示未定义（真漏链），
   `T`/`D` 表示本文件已定义（多半是签名不一致或链接顺序问题）。

### 定位命令 / 工具

```bash
gcc -std=c17 -Wall -Wextra -c foo.c -o foo.o   # 只编译不链接，先清编译期错误
gcc -H -fsyntax-only main.c                     # 头文件包含树
nm app.o | grep -i vec_len                      # 符号表：U=未定义，T/D=已定义
TAG=latest scripts/run-example.sh c L2-001-multifile-build   # 多文件构建基准用例
TAG=latest scripts/run-example.sh c L2-003-header-dependency # 头文件依赖基准用例
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| `fatal error: xxx.h: No such file or directory` | 头文件没装 / `-I` 没传 / 文件名大小写不符 | `gcc -H -fsyntax-only` 看搜索路径（实测见下） |
| `undefined reference to 'sym'` | 漏链目标文件 / 声明与定义签名不一致 | `nm` 查符号是否为 `U`；把实现的目标文件补进链接命令（实测见下） |
| `multiple definition of ...` | 头文件里写了定义而非声明，或缺 include guard | `L1-034-include-guard` / `L2-003-header-dependency` |
| `implicit declaration of function` 警告 | 调用前没有声明（头文件没含对） | `-Wall` 必开（`L2-010`） |
| 换优化级别/编译器后行为变化 | 未定义行为，不是编译器 bug | 固定 `${GCC_MAJOR}`、`-O0`/`-O2` 对照（`L2-020`）+ sanitizer |

### 修复与预防

修复：缺头文件补安装或补 `-I`；未定义引用补齐链接清单或统一签名；重复定义
把定义移出头文件、补 guard。

预防（落成构建规则与测试，不是口头约定）：

- 多文件工程一律走 make/CMake（`L2-001-multifile-build`、
  `L2-002-makefile-incremental`），头文件依赖交给构建系统而不是人脑
  （`L2-003-header-dependency`）；
- `-Wall -Wextra` 当基线（`L2-010-strict-warnings`），静态分析补
  `-fanalyzer`（`L2-011-gcc-analyzer`）；
- 编译器版本只引用 `images/versions.env` 的 `${GCC_MAJOR}` / `${CLANG_MAJOR}`，
  不在构建脚本里手写版本字面量——避免「本地旧、CI 新」这类错配（docs/20 §3.1）。

**复现实验 1：缺头文件（实测）**

```bash
docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:latest" bash -lc \
  'mkdir -p /tmp/build && cd /tmp/build && cat > main.c <<"EOF"
#include "config.h"   /* 不存在的头文件 */
#include <stdio.h>
int main(void) { printf("%s\n", FEATURE_FLAG); return 0; }
EOF
gcc -std=c17 -Wall main.c -o main'
```

实测输出（退出码 1）：

```
main.c:1:10: fatal error: config.h: No such file or directory
    1 | #include "config.h"   /* 不存在的头文件 */
      |          ^~~~~~~~~~
compilation terminated.
```

**复现实验 2：未定义引用（实测）**

```bash
docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:latest" bash -lc \
  'mkdir -p /tmp/build && cd /tmp/build && cat > vec.h <<"EOF"
extern int vec_len;
EOF
cat > vec.c <<"EOF"
#include "vec.h"
int vec_len = 8;
EOF
cat > app.c <<"EOF"
#include <stdio.h>
#include "vec.h"
int main(void) { printf("%d\n", vec_len); return 0; }
EOF
gcc -std=c17 -Wall -c vec.c -o vec.o && gcc -std=c17 -Wall -c app.c -o app.o \
  && gcc app.o -o app'
```

实测输出（退出码 1，链接期）：

```
/usr/bin/ld: app.o: warning: relocation against `vec_len' in read-only section `.text'
/usr/bin/ld: app.o: in function `main':
app.c:(.text+0xa): undefined reference to `vec_len'
collect2: error: ld returned 1 exit status
```

补上漏链的目标文件（`gcc app.o vec.o -o app && ./app`）：输出 `8`，退出码 `0`——
符号本来就有，只是链接清单没写全，这是 `undefined reference` 最高频的根因。
