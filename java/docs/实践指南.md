# Java 实践指南（G1）

> 回答「什么时候用 Java 轨道的哪类用例、不用会怎样、怎么验证真的学会了」。
> 语法细节归 L1 用例（见 [知识点清单.md](知识点清单.md)），本篇只讲工程用法，不重复语法。
> 命令契约（规范 §4.3）：统一 `TAG=latest scripts/run-example.sh java <ID>`；
> 版本号只写 `images/versions.env` 的变量名（`${JAVA_MAJOR}`，版本引用契约 §4.4）。

## 1. 适用边界（什么时候用 / 什么时候别用）

**什么时候用本轨道**：你要在 devbox 体系里练 Java 工程能力——L1 语言与标准库
基础（泛型、集合、并发原语）、L2 工程能力（classpath、可执行 jar、javadoc、
模块）、L3 专题（并发流水线、虚拟线程、JVM 诊断、序列化、基准、JNI）、
L4 设计模式（23 个），共 74 个用例；终点是 `java/project` 的毕业项目
（Java 命令行文本索引器）。每一层都用「可观察判据」验收：用例跑通、输出与
`expected.txt` 逐行一致（验收口径见 [开发指南.md](开发指南.md)）。

**什么时候别用本指南**：

- 想学某个语言特性本身（类型擦除规则、switch 表达式语义）——直接跑对应 L1
  用例，指南不讲语法，读了也学不会；
- 想找某个具体故障的排查路径（OOM、死锁）——去 [问题指南.md](问题指南.md)
  （G3，按问题域组织：JVM 内存与 GC、并发与线程）；
- 想查某个工具的参数——去 [工具指南.md](工具指南.md)（G4）；
- 想引第三方框架（Spring、Jackson 等）——本轨道只用 JDK 与标准库、不下载依赖
  （[知识点清单.md](知识点清单.md) §1 的边界），用例里引依赖不会通过评审。

**反例（可执行）**

- 错误做法：把本指南当语法书，跳过用例直接背结论。
- 复现命令（语法考点的「正主」在清单与用例里，不在指南里）：

  ```bash
  grep 'L1-024-resource-closing' java/docs/知识点清单.md
  ```

  输出会指向 KP 行与建议用例 `L1-024-resource-closing`——资源关闭知识点的
  载体是用例，不是本篇。
- 后果：只读不跑，等于没碰过 `javac`；try-with-resources 漏关闭只有跑用例
  才会暴露。正确动作是
  `TAG=latest scripts/run-example.sh java L1-024-resource-closing`。

## 2. 最小可运行示例（指向具体用例 ID）

入口是 `L0-hello`——L0 是通路验证层（`KI-05` 定案：L0 表示镜像与 runner
通路验证，不属于知识难度层级），它验证镜像能编译并运行 Java 21，与任何
知识点无关：

```bash
TAG=latest scripts/run-example.sh java L0-hello
# 实测输出：java/L0-hello                 PASS (0s)
```

通路没验证之前，不要碰 L2/L3 用例。

**反例（可执行）**

- 错误做法：不验通路，直接上依赖最重的用例。
- 复现命令（把 `TAG` 指向一个不存在的标签，模拟「镜像/tag 出问题」这一最常见
  环境故障）：

  ```bash
  TAG=nosuchtag scripts/run-example.sh java L3-003-jvm-thread-diagnostics
  ```

- 后果（实测）：runner 输出
  `java/L3-003-jvm-thread-diagnostics  FAIL (exit!=0, 1s)`，stderr 含
  `docker: Error response from daemon: manifest unknown.`，退出码非零。
  通路用例 1 秒就能把这类环境问题暴露出来；不验通路时，同样的错误会发生在
  你等得最久的那一步，且极易被误读成「代码有问题」（素材池 `S-06`）。

## 3. 惯用法与反模式对照表（含可复现反例）

| 惯用法 | 反模式 | 为什么 |
|---|---|---|
| 一律经 runner 跑用例 | 手写 `docker run` / `javac && java` 复刻 runner 的行为 | CI 与本地共用 runner 真本（`scripts/run-example.sh`）；口径分裂会造成「本地假绿」——规范 §4.3 记录过 TAG 与 IMAGE_TAG 名字不一致导致 6 个用例 job 全红的真实事故 |
| 资源用 try-with-resources 关闭（`L1-024-resource-closing`） | 手写 `finally` 且把 `close` 写漏、写错顺序 | 手写 close 会被提前 return 或异常跳过（`L1-025-finally-return` 的考点）；try-with-resources 由编译器保证逆序关闭 |
| 跨线程共享标志/状态用 `volatile`、锁或并发容器（`L1-031-volatile-publication`、`L3-001-concurrent-pipeline`） | 裸字段一写了之，合并计数用 get-then-put | JIT 会提升循环里的读（实测反例见下）；非原子合并丢更新（`L3-001` 考点） |
| JVM 诊断先 `jcmd`（Thread.print / GC.class_histogram） | 一上来 `jstack`，OOM 就调大 `-Xmx` | 工具指南 §4 误用 1/2：`jstack` 对卡死进程可能连不上；OOM 不分类就调堆，修错方向 |
| 计时基准只断言操作计数（`L3-005-counted-benchmark`） | 用单次墙钟时间下性能结论 | JIT、预热与调度扰动让单次计时不可复现；expected 只收计数 |
| 版本号只引用 `images/versions.env` 变量（`${JAVA_MAJOR}`） | 在文档/脚本里手写 `21.0.12.1` | 升级时手写常量集体过期，且过不了 `scripts/check-version-truth.sh` |

**反例（可执行）：非 volatile 的写入永远看不见**

- 错误做法：工作线程自旋等一个普通（非 volatile）布尔标志，以为「主线程
  改了，工作线程总能看见」。

  ```java
  public class Vis {
      static boolean stop;   /* 非 volatile */
      public static void main(String[] args) throws Exception {
          Thread worker = new Thread(() -> {
              while (!stop) { }            /* 等 stop 变 true */
              System.out.println("seen-stop");
          }, "spin-worker");
          worker.start();
          Thread.sleep(500);
          stop = true;
          System.out.println("flag-set");
          worker.join(3000);
          System.out.println("joined-alive=" + worker.isAlive());
          System.exit(0);   /* 非 daemon 工作线程还活着时，用它结束进程便于观察 */
      }
  }
  ```

- 复现命令（对照组把 `stop` 加 `volatile`，其余逐字相同；镜像 tag 经变量传入）：

  ```bash
  docker run --rm "ghcr.io/zeek-zhao/devbox-java:${TAG:-latest}" bash -c \
    'javac Vis.java && timeout 5 java Vis'
  ```

- 后果（实测）：非 volatile 版输出 `flag-set`、`joined-alive=true`——
  `stop=true` 写入 3 秒后工作线程仍没看见，`seen-stop` 一次都没打印；
  volatile 版输出 `flag-set`、`seen-stop`、`joined-alive=false`——立即退出。
  判据是「seen-stop 出没出现」，不是时序。正解见 `L1-031-volatile-publication`。

## 4. 真实工作中的变体

**变体 1：本地已自建镜像（`make images` 或 `scripts/build-images.sh`）**
runner 的 `TAG` 取值顺序是 `TAG` → `IMAGE_TAG` → `local`（真本
`scripts/run-example.sh`），本地调试自建镜像时不用传 `TAG`（默认 `local`），
或显式 `TAG=local scripts/run-example.sh java <ID>`。`local` 只是本地约定名，
不要写死进文档或 CI 配置。

**变体 2：需要可复现的构建结果**
`:latest` 随 `main` 变动（ROADMAP `KI-08`；历史 bug `#184`：并发 PR 互推
`:latest` 互相覆盖被测镜像）。复现某个历史结果时用 CI 每次构建都打的
`sha-<commit>` 标签：`TAG=sha-<commit-sha> scripts/run-example.sh java <ID>`。

**变体 3：整轨回归**
改动波及面大（升级 `${JAVA_MAJOR}`、动公共构建配置）时跑全轨 74 例，与 CI 的
`examples` job 同款入口：`TAG=latest scripts/run-example.sh java --all`。
并发类用例（`L3-001`/`L3-002`/`L3-003`）也在这一步一起验，不要因为「本地单例
跑过」就跳过整轨。

**反例（可执行）**

- 错误做法：CI 一片红就当「并发时序 bug」去改代码，不先看报错发生在哪一层
  （素材池 `S-06`：镜像探测失败被误读为代码问题）。
- 复现命令（报错里没有 javac/java 的影子——镜像 pull 阶段就死了）：

  ```bash
  TAG=nosuchtag scripts/run-example.sh java L3-003-jvm-thread-diagnostics
  # 实测 stderr：Unable to find image 'ghcr.io/zeek-zhao/devbox-java:nosuchtag' locally
  #            docker: Error response from daemon: manifest unknown.
  ```

- 后果：对着一个根本没被执行过的字节码改并发逻辑，白烧一轮排查；正确动作是
  先看报错阶段（pull / 编译 / 运行），环境问题先修环境（见问题指南）。
