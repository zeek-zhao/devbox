## JVM 内存与 GC（OOM、堆占用、容器与堆的关系）

> 来源：类型 ②——可复现实验（小堆 OOM 抓 `jcmd GC.class_histogram`、
> jcmd 抓晚了、容器 OOMKill，输出均为实测）；类型 ①——docs/20 §3.6 Java 块
> （`OutOfMemoryError` 分类）、工具指南 §4 误用 1（OOM 只会说「内存不够」）。

### 典型现象

- 进程死掉，stderr 最后是（实测）：
  `Exception in thread "main" java.lang.OutOfMemoryError: Java heap space`，
  退出码 1——JVM 自己认输，进程是被 `OutOfMemoryError` 终止的；
- 想知道谁占了堆：进程活着时 `jcmd <pid> GC.class_histogram`（实测，32→256 MB
  小堆连续吃内存的场景）：
  `1:          8075       53829320  [B (java.base@21.0.12.1)`——
  `byte[]` 一类占掉 50+ MB，嫌疑对象直接现形；
- 容器场景的另一副面孔：JVM 没来得及抛 OOM，整只容器被内核 OOMKill
  （实测：`--memory=64m` 下 `Killed java -Xmx256m ...`，进程退出码 137）——
  报错里没有 Java 栈，只有 `Killed`；
- 抓诊断抓晚了（实测）：
  `java.io.IOException: non existent JVM pid: 52`——目标 JVM 已经退出，
  jcmd 连不上，这不是「jcmd 坏了」。

### 先做的三个检查

1. 分清「谁杀的进程」：退出码 1 + `OutOfMemoryError` = JVM 抛的；137 / `Killed`
   = 内核 OOMKill，容器内存上限先爆（两类问题修法不同）；
2. 进程还活着吗：`kill -0 <pid>` 或 `jps -l`——诊断命令只能抓活 JVM；
   已死就先把触发条件放慢（加大 `-Xmx`、放慢填充节奏）留出抓取窗口；
3. 读 OOM 的详细消息分类：`Java heap space`（堆不足/泄漏）、
   `GC overhead limit exceeded`（GC 时间占比过高，常是泄漏早期）、
   `Metaspace`（类加载器泄漏）——分类错了修复方向就错（工具指南 §4 误用 1）。

### 定位命令 / 工具

```bash
jcmd <pid> GC.class_histogram | head -12   # 谁占堆（活进程）
jcmd <pid> VM.flags | grep -o MaxHeapSize.* # 堆上限现在是多少
jmap -histo <pid> | head -12               # 备选直方图（工具指南 §2.6）
TAG=latest scripts/run-example.sh java L3-003-jvm-thread-diagnostics  # 诊断基准用例
```

工具细节见 [工具指南.md](工具指南.md) §2.6 与 §4 误用 1。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| rc=1 + `Java heap space` | 对象只增不减（缓存无上限、集合滞留） | `GC.class_histogram` 看头名；实测见下 |
| rc=1 + `GC overhead limit exceeded` | 泄漏早期，GC 疲于奔命 | 连续抓两次 histogram 对比增长 |
| rc=1 + `Metaspace` | 动态生成类、类加载器泄漏 | histogram 看类数量趋势 |
| rc=137 / `Killed` | 容器内存上限低于 JVM 实际占用（堆外+元空间+栈都要算） | `--memory` 调大或 `-Xmx` 调小，实测见下 |
| `non existent JVM pid` | 目标进程已死，抓晚了 | `jps -l` 确认；放慢触发条件再抓 |
| 只在压测/长跑出现 | 短跑测不出泄漏 | `L3-005-counted-benchmark` 的操作计数思想，别用单次墙钟 |

### 修复与预防

修复：按直方图的头名修——缓存加界、集合用完即清、`-Xmx` 与容器 `--memory`
一起定（堆之外还有元空间与栈开销）。

预防（落成测试与约定）：

- 有状态的集合/缓存必须有界或有生命周期，写用例时把「只增不减」的路径当考点
  自查（`L3-001` 的 finally 关池同理）；
- OOM 排查按分类走，不许「不分类直接调大 `-Xmx`」（工具指南 §4 误用 1）；
- 基准与压测只断言操作计数/校验和，不断言墙钟（`L3-005-counted-benchmark`）。

**复现实验 1：小堆跑 OOM + 抓直方图（实测）**

```bash
docker run --rm "ghcr.io/zeek-zhao/devbox-java:latest" bash -c \
  'cat > /tmp/Oom.java <<"EOF"
import java.util.*;
public class Oom {
    public static void main(String[] args) throws Exception {
        List<byte[]> hold = new ArrayList<>();
        while (true) {
            hold.add(new byte[1024 * 1024]); /* 每轮 1 MB，只增不减 */
            Thread.sleep(100);               /* 放慢填充，留出抓直方图的窗口 */
        }
    }
}
EOF
javac /tmp/Oom.java -d /tmp
java -Xmx256m -cp /tmp Oom > /tmp/out.log 2>&1 &
JPID=$!
sleep 5
kill -0 $JPID && echo alive-at-5s
jcmd $JPID GC.class_histogram | head -5
wait $JPID; echo rc=$?
tail -2 /tmp/out.log'
```

实测输出（直方图 + 结局）：

```
alive-at-5s
 num     #instances         #bytes  class name (module)
-------------------------------------------------------
   1:          8075       53829320  [B (java.base@21.0.12.1)
   2:          7944         190656  java.lang.String (java.base@21.0.12.1)
rc=1
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
	at Oom.main(Oom.java:6)
```

同一个场景把容器限到 `--memory=64m`、堆开 `-Xmx256m`：JVM 没来得及抛 OOM，
内核先动手——实测 `Killed  java -Xmx256m -cp /tmp Oom`，进程退出码 `137`。
这就是「JVM OOM」与「容器 OOMKill」的实测分界线。

**复现实验 2：抓晚了（实测）**

同一程序用 `-Xmx64m`（几十毫秒就 OOM 退出），3 秒后才抓：
`java.io.IOException: non existent JVM pid: 52`——诊断窗口一过，任何 jcmd
子命令都连不上；不是工具坏了，是进程没了。

## 并发与线程（死锁、可见性、丢更新）

> 来源：类型 ②——可复现实验（死锁抓栈、非 volatile 可见性对照，输出均为实测）；
> 类型 ①——素材池 `S-01` 作流程类旁证：「TAG 与 IMAGE_TAG 两名不一致 → 用例
> job 全红而本地假绿」的症状（本地/CI 结果不一致、时对时错）极易被当成并发
> 时序 bug——先核对变量与口径，再怀疑代码（docs/24-G3素材池.md S-01）；
> 类型 ①——工具指南 §4 误用 2（死进程用 jstack 抓栈）。

### 典型现象

- 程序挂死不退出，栈里两根线程互等（实测）：
  `Found one Java-level deadlock:`，`"worker-1": waiting to lock monitor ...，
  which is held by "worker-2"`，反向同样一条——jcmd 自己就能判死锁；
- 共享标志写入了、工作线程永远看不见（实测，非 volatile 对照实验）：
  输出停在 `flag-set`、`joined-alive=true`，`seen-stop` 一次都不出现；
  加 `volatile` 后立刻出现；
- 计数比预期少（丢更新）：get-then-put 两步合并非原子（`L3-001` 考点）；
- （`S-01` 旁证）本地全绿、CI 全红，或两次 CI 结果不一致，像极了「竞态」——
  实为流程口径问题（变量名不一致、可变 tag 被覆盖），代码没问题。

### 先做的三个检查

1. 抓栈两三次对比：一直 `BLOCKED` 且 `waiting to lock` 互指 = 死锁闭环；
   时而 `RUNNABLE` = 只是慢（工具指南 §4 误用 2：多次采样，单次分不清）；
2. 共享字段逐个过：有没有 `volatile` / `synchronized` / 并发容器？
   合并操作是不是原子的？等待有没有超时？
3. 本地绿 CI 红时先核对口径（`S-01`）：`TAG` 与 `IMAGE_TAG`、镜像 tag 是不是
   同一个值，排除环境差异再谈并发。

### 定位命令 / 工具

```bash
jcmd <pid> Thread.print | grep -B2 -A8 "waiting to lock"  # 阻塞点与互等闭环
jcmd <pid> Thread.print > stack1.txt; sleep 2; jcmd <pid> Thread.print > stack2.txt  # 两次采样对比
TAG=latest scripts/run-example.sh java L3-003-jvm-thread-diagnostics   # 诊断基准用例
TAG=latest scripts/run-example.sh java L3-001-concurrent-pipeline      # 并发集合基准用例
```

工具细节见 [工具指南.md](工具指南.md) §2.6、§4 误用 2；高频问答见
[FAQ.md](FAQ.md)（死锁一问已预链本节）。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 挂死 + `Found one Java-level deadlock` | 多把锁获取顺序不一致 | 栈里互等闭环指认两根线程；统一加锁顺序或改 `tryLock` 带超时（实测见下） |
| 挂死但无死锁闭环 | 等待条件永不满足（latch 没数满、`countDown` 漏调） | 抓栈看 `WAITING` 在哪个 `park`/`await`；核对条件何时置位 |
| 写入别人看不见 | 非 volatile（JIT 提升读）/ 锁缺失 | 加 `volatile` 对照重跑（实测见下）；`L1-031-volatile-publication` |
| 计数丢更新 | get-then-put 非原子 | 换 `ConcurrentHashMap.merge` / `AtomicInteger`（`L3-001`） |
| 本地绿 CI 红、时对时错 | 流程口径不一致（`S-01`），不是竞态 | 对变量名与 tag；换 sha 标签重跑 |
| 虚拟线程下依旧脏读 | 误以为虚拟线程自带同步（`L3-002` 考点） | 虚拟线程不改变同步规则，照样要 volatile/锁 |

### 修复与预防

修复：按栈指认改锁序（或 `tryLock` 超时回退）；共享可变状态收口到
`volatile`/锁/并发容器；等待一律带超时并检查返回。

预防（落成测试与约定）：

- 并发用例必须「等待完成」再断言（`L3-001` 的 allOf + 超时非零失败）；
  共享标志类考点用 `L1-031-volatile-publication` 的发布语义写法；
- 执行器在 finally 里关闭（`L3-001`）；虚拟线程执行器同样要显式等待与同步
  （`L3-002-virtual-threads`）；
- 资源关闭一律 try-with-resources（`L1-024-resource-closing`），finally 手写
  close 的顺序坑见 `L1-025-finally-return`。

**复现实验 1：死锁 + jcmd 抓栈（实测）**

```bash
docker run --rm "ghcr.io/zeek-zhao/devbox-java:latest" bash -c \
  'mkdir -p /tmp/dl && cat > /tmp/dl/Dl.java <<"EOF"
public class Dl {
    static final Object A = new Object(), B = new Object();
    public static void main(String[] args) throws Exception {
        Thread t1 = new Thread(() -> {
            synchronized (A) { sleep(300); synchronized (B) { } }
        }, "worker-1");
        Thread t2 = new Thread(() -> {
            synchronized (B) { sleep(300); synchronized (A) { } }
        }, "worker-2");
        t1.start(); t2.start();
        Thread.sleep(20000); /* 等死锁形成，再由外部 jcmd 抓栈 */
    }
    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { } }
}
EOF
javac /tmp/dl/Dl.java -d /tmp/dl
java -cp /tmp/dl Dl &
JPID=$!
sleep 3
jcmd $JPID Thread.print | grep -A 10 "Found one Java-level deadlock"
kill $JPID 2>/dev/null'
```

实测输出（节选）：

```
Found one Java-level deadlock:
=============================
"worker-1":
  waiting to lock monitor 0x000077f260001f50 (object 0x000000045e014268, a java.lang.Object),
  which is held by "worker-2"
"worker-2":
  waiting to lock monitor 0x000077f254000fe0 (object 0x000000045e014258, a java.lang.Object),
  which is held by "worker-1"
```

注意细节：main 线程若不睡够 20 秒直接退出，JVM 会随工作线程一起活着不退，
`kill $JPID` 收尾；两根线程互等时 jcmd 能自动判定死锁闭环，无需人肉比对。

**复现实验 2：非 volatile 可见性对照（实测）**

同一程序两版：`Vis.java` 用 `static boolean stop`，`Vis2.java` 把 `stop` 改成
`static volatile boolean stop`，其余逐字相同（源码见
[实践指南.md](实践指南.md) §3 反例）。实测：

```
== plain（非 volatile）==
flag-set
joined-alive=true          <- 写入 3 秒后工作线程仍没看见
== volatile ==
flag-set
seen-stop
joined-alive=false
```
