# 流水线

> 单一流水线，所有触发都跑全量。本文说明它跑什么、为什么这么排、以及加新语言要改哪两处。

## 触发与范围

| 触发 | 跑什么 | 典型时长 |
|---|---|---|
| `pull_request` | 全量：静态 + 身份 + 覆盖 + 8 门格式 + 719 例 + db + shared + release + 镜像重建 | 20–25 分钟 |
| `push main` | 同上 | 20–25 分钟 |
| `push tag v*` | 同上，另加 `VERSION` 与 tag 逐字一致性校验 | 20–25 分钟 |
| `workflow_dispatch` | 同上（手动） | 20–25 分钟 |

**为什么不给 `push` 开全部分支**：同仓分支推送会与 `pull_request` 重复触发同一次全量。
只保留 `main` + tag，一次改动只跑一次。

## 为什么不再分档

这个仓库曾经是三档：PR 不跑 / `push main` 跑 fast（180 秒预算）/ tag 跑 full。
分档的唯一理由是**省 GitHub Actions 额度**——并行派 N 张卡时，N 份全量同时在烧。

转公开之后这个前提消失了：公开仓的 Actions 分钟数不计量。于是分档只剩代价：

- PR 阶段不跑，红要等到合并后才暴露
- fast 档不含用例，等于「格式对了就算过」
- 三档意味着三份 job 定义要同步维护，最容易漂

所以现在是一档：**任何触发都跑全量**。

## Job 清单

| Job | 挡什么 | 为什么单独一个 job |
|---|---|---|
| `static` | shellcheck、用例契约（每例必须有 `run.sh`）、版本真本、文档里的命令能跑、tag 与 `VERSION` 一致 | 不依赖镜像，最快出结果 |
| `authors` | 提交身份是否在白名单、有没有 AI 署名尾巴 | 只读 git 历史，秒级 |
| `coverage` | 覆盖表与项目代码自洽（`--strict`，不允许 `pending`） | 纯文本校验 |
| `probe` | 镜像是否真的存在 | 镜像没建时 `pull` 会红，会把「镜像没建」误报成「代码有问题」 |
| `fmt` × 8 | 每门语言的格式化 | 八门串行要拉 11 GB 镜像，并行墙钟约等于最慢的一门 |
| `examples` × 8 | 每门语言的全部用例 | 同上；且要知道「到底坏了几门」，所以 `fail-fast: false` |
| `examples-db` | 数据库轨道 77 例（自起 Compose 栈） | runner 形态不同，`db/scripts/run-all.sh` 负责 up → wait-ready → 跑 → down |
| `shared` | `shared/` 三个 shell 库的自测 + README 索引与代码一致 | 依赖 bats/jq/yq，都在 shell 镜像里 |
| `release` | `shared/release` 的 Node 工具自测 | 不起容器，runner 自带 node |
| `images` | 镜像重建 + 体积预算 | 复用 `images.yml`，不复制那 200 行 |

## 外部 fork 的 PR

fork PR 拿不到可写的 `GITHUB_TOKEN`（GitHub 的机制，不是配置问题），镜像推送必然失败。
所以 `images` job 在 fork PR 上跳过：

```yaml
if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository
```

其余 job（719 例 + 格式 + 覆盖 + 身份）照常跑。**这是平台约束，不是省测。**

同理，`pull_request`（而不是 `pull_request_target`）不会把仓库 secrets 暴露给 fork PR 的
代码，这是安全默认值，不要为了「让 fork PR 也能推镜像」改成 `pull_request_target`。

## 权限

```yaml
permissions:
  contents: read
  packages: write
```

`packages: write` 是必须的：**公开仓的 `GITHUB_TOKEN` 默认只读**，私有仓默认有写权限。
少了这一行，转公开后第一次镜像构建就会红。

`images.yml` 里的每个 job 也各自声明了 `packages: write`，因为可复用工作流的权限
需要在自己内部再声明一次。

## 时长参考

| 项 | 时长 |
|---|---|
| `static` / `authors` / `coverage` / `release` | 各 30–60 秒 |
| `fmt` 单门 | 1–2 分钟 |
| `examples` 单门 | 1–3 分钟；`go` 例外，2 核 runner 上 10–12 分钟（`race-detector` 与 `cpu-profile` 编译慢） |
| `examples-db` | 5–8 分钟 |
| `images` | 约 14 分钟 |
| 整轮墙钟 | 20–25 分钟 |

没有硬预算了。但每个 job 都设了 `timeout-minutes`（用例类 45 分钟，其余 10–30 分钟），
防止一个真挂住的用例烧到 GitHub 的 6 小时上限。

## 本地总闸 `scripts/pre-merge.sh`

CI 是「每次改动都验」，本地总闸是「一次合并多个分支时先验一遍」。它的价值不在替代 CI，
而在**并行开发场景**：一次合并 10 个分支时，先在本地一次性跑完 719 例，
比在 GitHub 上等 10 次红再逐个修要快。

```bash
# 按序 squash 合并并跑全量，绿了才推 main
bash scripts/pre-merge.sh --from-file plan.txt --base main --push

# 冲突默认停下并保留现场（rc=2）；按「分支是否真改过该文件」自动取边
bash scripts/pre-merge.sh --from-file plan.txt --auto-resolve
```

它跑的东西与 CI 等价，但顺序可控：先合并、再验、再推。

## 加一门语言要改哪两处

1. `images/lang-images.tsv` —— 语言 → 镜像层的映射（`run-example.sh` / `fmt.sh` /
   CI 的 `fmt` / `examples` 都读这一个文件）
2. `.github/workflows/ci.yml` 的 `fmt` 与 `examples` 两个 matrix

**第 2 步最容易漏**：遗漏 matrix 会让该轨道静默不进入 CI——本地全绿，远端从不校验。
这是本仓库真实踩过的坑。

数据库轨道是例外：它不走语言矩阵，由 `examples-db` job 独立跑 `db/scripts/run-all.sh`。
