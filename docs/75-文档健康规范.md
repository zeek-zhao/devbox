# 文档健康规范

> 对应任务卡 `M11-W0-03`（#268，D3 拍板）。决策记录见 [73-M11并发执行计划](73-M11并发执行计划.md) §11。
> 本文管两件事：**谁对一份文档负责**（`owner`）、**这份内容新鲜到什么时候**（`last_verified`）。
> 不引入任何巡检脚本（D3 已拍板不做）；health 由人按本文维护，CI 只兜既有校验。

## 1. frontmatter 增补字段

仓库级 `docs/*.md` 的 frontmatter 在既有 `title / date / status / scope` 之上，规范 v2 起增补：

| 字段 | 含义 | 缺省 |
|---|---|---|
| `owner` | 该文档的答案归属（一人，格式 `名字 <邮箱>`） | 见 §4「owner 缺位」 |
| `last_verified` | 最近一次「内容与工程实况核对」的日期（YYYY-MM-DD） | 视同未验证 |

约定：

- 既有文档**不批量回填**（集成卡 #266 只处理状态回写需要的文件）；新文档与被大改的文档必须带这两个字段；
- `last_verified` 只在**真核对过**时更新——以磁盘/CI 实测为准，不抄旧值（同 [60-AI工作指南](60-AI工作指南.md) §5 坑 6「以代码为准，不抄注释」）。

## 2. 状态升级判据（draft → reviewed → verified）

沿用 [11-知识点清单增强规范](11-知识点清单增强规范.md) §7.1 的状态机，落成文档版判据：

| 状态 | 谁能升 | 需要的证据 |
|---|---|---|
| `draft` | 起草者 | 文件存在、frontmatter 齐、章节结构符合其类型规范 |
| `reviewed` | **owner 或维护者**人工抽读 | 至少一人读过并确认「无事实错误、命令与工程一致」；抽读留痕（卡评论或 PR 描述） |
| `verified` | owner + 维护者确认 | 文档中每条可执行命令真跑通过 + 反向测试通过（故意破坏能被发现）；逐条留痕 |

规则（与 11 §7.1 一致）：

1. 只能单向推进；回退要在 PR 写明原因；
2. **不许自评自改**到 `verified`——implementer 与 verifier 分离（[73](73-M11并发执行计划.md) §6）；
3. 规范类文档（71/72/75/76 这类「真本」）升 `reviewed` 前必须有第二双眼睛（verifier 或维护者）。

## 3. 多久算 stale

| 文档类型 | stale 判据 | 动作 |
|---|---|---|
| 口径类（版本 / 计数 / 清单） | 引用的数字与磁盘实测不一致（如 659 / 11 层 / `v0.2.0`） | 立即改，来源标实测 |
| 流程类（70/73 派单与合并纪律） | 所描述的批次已全部执行完毕且无后续批次引用 | 归档段落加「已完成」标注，不删历史 |
| 规范类（60/71/72/75） | 与实际 SOP 出现一次分歧即 stale | 当次 PR 顺带修，或开 Q 编号登记 |
| 快照类（30） | 每次里程碑边界检查 / 成批远端状态变化 | 按其 §0 快照保鲜约定更新 `last_verified` 与日期 |

判定基准：**任何「文档说 X」先对磁盘/CI 实测**，与 [60](60-AI工作指南.md) §1 单一真本表一致。

## 4. owner 缺位时归谁

- `owner` 字段缺失的文档：归**维护者**（`zeek.zhao <zeek.zhao@foxmail.com>`）；
- owner 离开项目或长期不可达（两个检查节拍未响应）：归维护者，并在 `docs/30` 快照留一行移交记录；
- 自动化产出的文档：owner 记维护者——**执行 AI 不写自己为 owner**，责任必须落在人上。

## 5. 与现有纪律的衔接

- PR 描述的「执行留痕 / UNVERIFIED / verifier 结论 / spec 版本」四段见
  [.github/PULL_REQUEST_TEMPLATE.md](../.github/PULL_REQUEST_TEMPLATE.md)（本卡同步补齐）；
- 执行 AI 的停止规则不变：碰门禁文件、凭证、范围外、连续两次验证失败 → 停并问人（[73](73-M11并发执行计划.md) §5）；
- 本文自身 `owner: zeek.zhao`，`last_verified` 随每次修订更新。
