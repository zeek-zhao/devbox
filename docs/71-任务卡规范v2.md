# 任务卡规范 v2（spec v2 规范真本）

> **本文是什么**：`.github/ISSUE_TEMPLATE/agent_task.yml`（表单载体）的**规范真本**——
> 逐字段说明九栏正文怎么写、execution trace 与 stop rules 怎么判、并发粒度怎么算。
> 口径出处：[60-AI工作指南](60-AI工作指南.md) §4（任务卡规范 v1）、
> [70-并行AI开发计划](70-并行AI开发计划.md) §5 单卡 SOP / §6 合并纪律、
> [73-M11并发执行计划](73-M11并发执行计划.md) §2 卡清单 / §3 批次 / §5 单卡 SOP。
> 本文只解释与引用这些文档，不改写它们的任何历史内容。

## 0. 一句话模型与定位

**一张卡 = 一个独立完整克隆目录 + 一个 `feat/<issue#>-<slug>` 分支 + 一个 PR + 一条 verifier 结论。**

spec v2 的核心主张：**把 issue 当成 agent 的 brief，字段即验收判据，缺一即不可派单。**
表单（`agent_task.yml`）只在网页端渲染；批量建卡走的 REST API / `gh` 路径不会自动带表单结构，
所以卡正文必须**镜像表单的 `###` 标题**手工构造（§4）。verifier（如 `#265`）按这些标题逐字段读卡、逐条取证。

两类字段分工：

| 字段层 | 内容 | 谁消费 |
|---|---|---|
| 元字段（表单 input / dropdown / checkboxes） | 卡编号、类型、批次、检查点、工作目录、派单前自查 | 派单方与 coordinator（如 `docs/76` 派单状态表） |
| 九栏正文（表单 textarea） | 目标、判据、边界、留痕、停止规则 | 接卡的 AI 与 verifier |

## 1. 元字段对照表（agent_task.yml 逐 id）

`agent_task.yml` 共 15 个 `id`。九栏正文之外的 6 个元字段在此逐 id 对应：

| 表单 id | 表单 label | 类型 | required | 写法要点 |
|---|---|---|---|---|
| `card-id` | 卡编号 | input | 是 | 形如 `M11-W0-01`；与 issue 编号（如 `#253`）并存，分支与目录以 issue 编号命名 |
| `kind` | 卡类型 | dropdown | 是 | `docs` / `lab` / `code` / `bug` / `verifier` / `decision` / `needs-human`；**`decision` 与 `needs-human` 不派 AI** |
| `batch` | 并发批次 | dropdown | 是 | `W0` / `W1` / `W2` / `W3` / `W4` / `GATE` / `串行`；决定派出时点与并发资格 |
| `checkpoint` | 检查点 | input | 是 | `YYYY-MM-DD` 纯日期；7 天窗口的检查节拍，不是考核，到期只标记提醒不自动关 |
| `workspace` | 工作目录 / 分支 | input | 是 | 完整克隆目录与分支名一一对应：`~/work/devbox/<issue#>-<slug>/` · `feat/<issue#>-<slug>` |
| `gates` | 派单前自查 | checkboxes | 4 项全勾 | 已读 60 与 73 / 基线取最新 `origin/main` / 不碰 `gate-files.txt` 命中文件 / 提交身份合规且无 AI 署名尾巴 |

> 表单不预置标签：REST API 建卡时 label 若不存在会被**静默丢弃**（73 §9），按卡类型显式传，
> 本仓库现行约定如 `type/docs`、`prio/P1`。

## 2. 九栏 ↔ 表单 id 对照表

九栏正文与表单的 9 个 textarea 逐一对应（顺序即表单顺序，也是正文骨架的 `###` 标题顺序）：

| # | 规范九栏 | 表单 id | required | 一句话职责 |
|---|---|---|---|---|
| 1 | 目标与背景 | `goal` | 是 | 说清解决什么问题 |
| 2 | 验收判据 | `acceptance` | 是 | 「做完」的可判定定义 |
| 3 | 独占文件 / 工作区 | `scope` | 是 | 本卡允许改的路径 |
| 4 | 明确不做 | `out-of-scope` | 是 | 禁止顺手改什么，为什么 |
| 5 | 验证命令与期望输出 | `verify` | 是 | 成功长什么样 |
| 6 | 执行留痕 | `trace` | 否（但 PR 描述必贴） | 本次执行的证据链 |
| 7 | 停止规则 | `stop-rules` | 是 | 什么时候停并问人 |
| 8 | 失败与升级路径 | `escalation` | 是 | 卡住了找谁、交什么 |
| 9 | 依赖与独立性测试 | `deps` | 是 | 能否并发，靠什么 |

以下 §3 逐栏展开。每栏给「写法要求」与「常见坑」。

## 3. 逐字段说明（九栏）

### 3.1 目标与背景（`goal`）

- **写什么**：要解决的真实问题、现状为什么不够、读者是谁。引用依据文档与 Q 编号。
- **不写什么**：技术方案。AI 会自己发明方案，边界靠后面几栏约束；把方案写死在 goal 里
  等于替执行者做设计，而边界却没立住。
- **常见坑**：写成一句话口号（「把任务卡规范写好」）。至少要让接卡者不读其他文档也能答出
  「这张卡为什么存在」。

### 3.2 验收判据（`acceptance`）

- **写什么**：`- [ ]` 列表，每条独立可判定——用「文件存在 / 命令退出码 / grep 命中 / 计数 ≥N」
  这类能给出证据的陈述。verifier 靠这栏逐条取证，**能用规则判的不交给主观判断**（73 §6）。
- **每条可判定的正例**：
  - `- [ ] 新建 docs/71-任务卡规范v2.md，frontmatter 七字段齐、status: draft`
  - `- [ ] 与 agent_task.yml 的 15 个 id 列一张对照表，逐 id 对应`
  - `- [ ] grep -c "明确不做" docs/71-任务卡规范v2.md ≥ 1`
- **反例（判据太软，验不出问题）**：
  - `- [ ] 任务卡规范文档写清楚、内容完整、效果良好` ——无论写成什么样都能算「过」，
    verifier 拿不到任何可取证的证据，等于没写。60 §4 的对照：反例是
    「补充 C++ 实践指南，内容完整」；正例是「产出 `cpp/docs/实践指南.md`，frontmatter 七字段齐，
    引用 ≥1 个真实 L2 用例 ID，G2 一条命令真跑过」。
- **数量口径**：3–6 条为宜（对应 15–45 分钟粒度，§7.2）；多于 6 条通常说明该拆卡。

### 3.3 独占文件 / 工作区（`scope`）

- **写什么**：本卡**允许改**的路径清单（相对仓库根），含新建文件；同批其他卡不得碰同一路径。
- **为什么硬**：并发的敌人不是 CPU，是共享文件（73 §0）。独占清单是并发资格的物理基础；
  超出清单即触发停止规则 S3（§5）。
- **常见坑**：写「docs/ 相关文档」这种模糊范围。要么精确到文件，要么精确到「新建文件」。

### 3.4 明确不做（`out-of-scope`）

- **写什么**：不许顺手改什么、为什么禁止。最容易被省略、也最省返工的一栏。
- **固定条目**（多数卡适用，直接复用）：
  - 不改 `scripts/gate-files.txt` 命中的文件（改判定标准须人工评审 + 显式放行）；
  - 不改共享状态文档（`ROADMAP` / `30` / `41` / `12` / `00`），由批次集成卡一次回写；
  - 不代拍 `decision` / `needs-human` 事项。
- **常见坑**：省略这栏。没有负面清单的卡，AI 会把「相关的一切」都顺手改掉，
  然后在合并闸门上爆出 `check-gate-files.sh` 拒绝。

### 3.5 验证命令与期望输出（`verify`）

- **写什么**：能在**最新 `origin/main`** 上真跑的命令，每条配「成功长什么样」（退出码 0、
  grep 计数、特定输出行）。这是判据的证据来源，不是装饰。
- **命令契约**：跨卡一致的命令统一写 `TAG=latest`（73 §6 交叉一致性；60 §5 坑 1 的教训）。
- **不要写会触发校验的 HTML 注释命令标记**（HTML 注释内嵌 `verify:` 加命令的那种，
  `check-docs.sh` 会把它扫出来逐条真跑，73 §4 规则 D）。这类标记**只允许标任何环境都该成功的
  只读命令**；新文档拿不准就不标，判据的「可跑」由 verifier 在 PR 里取证，不靠注释标记兜底。
- **常见坑**：写「本地跑一下看看」。命令、参数、期望输出三要素缺一不可。

### 3.6 执行留痕（`trace`）

定义 execution trace 六字段（§6），完成后在 **PR 描述**逐项贴出；没跑过的一律写 `UNVERIFIED`，
**不许写「已验证」**。表单里这栏 `required: false`，是因为它属于「完成后回填」，
但 PR 描述里它是必贴项——缺 trace 的 PR 不进合并队列。

### 3.7 停止规则（`stop-rules`）

四类触发条件（§5）+ 一条补充（判据歧义）。碰到任一情形**停止并问人，不自行发挥**。
「停下来不等于停工」：把问题按 `Q-*` 编号记进 40、写清推荐答案，其他不依赖它的卡照常并行（60 §6）。

### 3.8 失败与升级路径（`escalation`）

- **写什么**：卡住时找谁（维护者 / 卡评论）、交什么材料（分歧清单、失败输出、已试过的命令）、
  下一步是什么（等拍板 / 转人工队列 / 摘出并发组）。
- **示例**（`#253` 原文）：字段冲突或表单 schema 不确定 → 在卡评论列出分歧，交维护者拍板，
  不自行改模板。
- **常见坑**：只写「问维护者」。要写清**带什么去问**——没有失败输出与已试命令的提问会二次返工。

### 3.9 依赖与独立性测试（`deps`）

- **写什么**：明确回答「本卡能否在不知道同批其他卡结论的前提下完成」（§7.1 独立性测试）；
  列出硬前置（哪张卡的结论是本卡的输入）与弱依赖（只借术语不借结论）。
- **判定结果**：能 → 可并发；不能 → 摘出并发组，串行排在该批最后（70 §2.2 规则 B）。
- **常见坑**：把弱依赖写成硬前置会白白串行化；把硬前置写成弱依赖会派出一张「猜着做」的卡。
  判别标准只有一个：没有 B 的结论，A 的验收判据是否还**每条可判定**。

## 4. REST API / `gh` 建卡会跳过 issue 表单

**事实**：issue 表单（YAML front-matter 模板）只在网页端「新建 issue」时渲染成交互控件；
`POST /repos/{owner}/{repo}/issues`（REST API）与 `gh issue create` 把 `body` 当纯文本原样入库，
**既不注入 `###` 标题，也不校验任何 `required`**。表单写得再好，API 建卡也不会自动生效（73 §9）。

**后果**：verifier 按 `###` 标题逐字段读卡；正文不镜像标题 → 字段读不出来 → 卡不可验。

**对策**：批量建卡时按下面的**正文骨架**逐卡填空（标题一字不改，与 `agent_task.yml`
的 label 完全一致）；标签在 API 调用里显式传。真实样例见 `#253` 卡正文本身。

可复制正文骨架：

````markdown
> 由 `docs/73-M11并发执行计划.md` 批量生成。字段与 `.github/ISSUE_TEMPLATE/agent_task.yml` 一一对应；
> REST API / `gh` 建卡跳过表单，故正文按表单 `###` 标题镜像构造。

| 字段 | 值 |
|---|---|
| 卡编号 | `M11-W0-XX` |
| 里程碑 | `M11 文档增强 v2` |
| 批次 / 类型 | W0 / docs |
| 检查点 | **2026-11-12**（7 天窗口，检查节拍非考核；到期只标记提醒，不自动关） |
| 工作目录 / 分支 | `~/work/devbox/<issue#>-<slug>/`（完整克隆）· `feat/<issue#>-<slug>` |

### 目标与背景

<说清要解决什么问题，不写技术方案>

### 验收判据

- [ ] <每条可判定，3–6 条>
- [ ] <命令 / 存在性 / 计数类判据>

### 独占文件 / 工作区

- `<相对仓库根的精确路径>`

### 明确不做

- 不改 `scripts/gate-files.txt` 命中的文件（改判定标准要人工评审）
- 不改共享状态文档（ROADMAP / 30 / 41 / 12 / 00），由批次集成卡一次回写
- 不代拍 decision / needs-human 事项

### 验证命令与期望输出

- `<命令>` → <退出码 / grep 计数 / 期望输出>

### 执行留痕

PR 描述里逐项贴出 `run_id` / `files_changed` / `commands_run` / `tests_passed` /
`risk_notes` / `review_needed`；没跑过的一律写 `UNVERIFIED`，不许写「已验证」。

### 停止规则

碰到以下任一情形**停止并问人**，不自行发挥：① 需要改 `scripts/gate-files.txt` 命中的文件；
② 碰到凭证、私有路径、账号或内网信息；③ 改动超出「独占文件 / 工作区」；
④ 同一验证命令连续两次失败；⑤ 验收判据有歧义。

### 失败与升级路径

<卡住时找谁、交什么材料、下一步是什么>

### 依赖与独立性测试

<能否在不知道同批其他卡结论的前提下完成？硬前置 / 弱依赖逐条列>
````

> 骨架顶部的元字段表是 `card-id` / `kind` / `batch` / `checkpoint` / `workspace` 五个 input /
> dropdown 的镜像（表单渲染成控件，API 正文只能用表行承载）；`gates` 四项自查由派单方在
> 建卡前逐项确认，不进正文。表单里的 markdown 引导段（开头 `>` 引用块）可选复制，
> 它的作用是把「跳过表单」这件事告知接卡者。

## 5. stop rules：四类触发条件

| 类别 | 触发条件 | 判定依据 | 停下来之后 |
|---|---|---|---|
| **S1 门禁文件** | 改动命中 `scripts/gate-files.txt`：CI 定义（`.github/workflows/*.yml`）、判定实现（`run-example.sh` / `check-docs.sh` / `pre-merge.sh` 等）、清单自身、版本与预算真本、被测环境（Dockerfile 等）、身份与格式（钩子 / allowlist / 格式化配置） | 60 §2 | 停；确需改的转人工评审 + `--allow-gate-change` 显式放行，PR 写明为什么改判定标准 |
| **S2 凭证与私有信息** | 公开仓内容里出现凭证、账号、token、内网地址、内部主机、私有路径 | 60 §6 / §7 | 停；不写入任何文件，交维护者处理 |
| **S3 范围外** | 改动需要超出「独占文件 / 工作区」清单；或需要代拍 `decision` / `needs-human` 事项 | 卡正文 `scope` / `out-of-scope` | 停；在卡评论列分歧等拍板，或转人工队列 |
| **S4 连续两次验证失败** | 同一验证命令连续两次非零退出或输出与期望不符 | 73 §5 第 7 步 | 停；贴两次失败的完整输出到卡评论，不带猜测性修改继续跑 |

**补充第 ⑤ 条**：验收判据本身有歧义（表单 placeholder 与 73 §5 均列）——归入 S3 同路径处理：
停并问人，把歧义写清后交维护者拍板。本文按问题要求把主触发条件归纳为四类，第 ⑤ 条为补充。

**通用纪律**：触发 stop rule 后**不自行发挥**——不绕钩子（`--no-verify`）、不用
`--auto-resolve` 蒙过冲突、不「顺手修门禁注释」。停下来不等于停工：记 `Q-*` 编号 +
推荐答案，其余卡照常并行。

## 6. execution trace：六字段定义

完成卡后在 **PR 描述**逐项贴出；verifier 卡（`#265`）按 D2 拍板把结构化版本落
`metrics/m11-traces/<run-id>.json`（含 spec 版本、模型与会话、命令与退出码、断言、`UNVERIFIED` 项）。

| 字段 | 写什么 | 不得这样写 |
|---|---|---|
| `run_id` | 本次执行的运行标识（CI run id，或本地会话编号；trace JSON 的文件名即它） | 留空、写「本地跑过」 |
| `files_changed` | 实际改动文件清单（相对仓库根，与 `git diff origin/main --stat` 一致） | 「若干文件」「docs 下几个」 |
| `commands_run` | 真跑过的命令及退出码 | 只列「打算跑」的命令 |
| `tests_passed` | 通过的检查与断言（`git diff --check`、`check-docs.sh`、`check-version-truth.sh` 等），逐条对应验收判据 | 无命令支撑的「全部通过」 |
| `risk_notes` | 风险与不确定处：没验到的环境差异、假设、边界情况 | 留空 |
| `review_needed` | 需要人工看的地方（价值取舍、教学判断、门禁相关疑问）；确无则写 `none` | 留空 |

**两条硬规则**：没跑过的一律写 `UNVERIFIED`，**不许写「已验证」**（状态诚实，60 §5 坑 11）；
`status: draft` 不自评 `verified`——升级判据由 `#268` 产出 `docs/75` 正式定义（D3 拍板）。

## 7. 独立性测试、粒度与单批上限

### 7.1 独立性测试

**定义**：派出前对批次内每张卡问一句——

> 「A 卡能不能在不知道 B 卡结论的前提下完成？」

- **能**（A 的验收判据在缺少 B 结论时仍每条可判定）→ A、B 可并发。
- **不能** → B 是 A 的**硬前置**：串行，B 结论落地前 A 不派。
- **只借术语、不借结论**（如 `#270` 之对 `#254`）→ **弱依赖**：可同批派，字段不一致由集成卡统一，
  不在卡内互改。

**实例**（73 §3）：W0 四卡（`#253` `#254` `#268` `#269`）只依赖已提交的表单与 `docs/73` → 可并发；
W2 各 lab 卡依赖 `#255` 的人工判定「样板能否复制」→ 硬前置，W1 串行；
W4-02（`#266` 集成回写）依赖 `#265` verifier 报告 → 串行。

### 7.2 卡粒度：15–45 分钟

一张卡「验收判据全勾」的目标工作量定为 **15–45 分钟**（熟练执行者，含跑验证命令的时间；
本文新增口径，出处为本规范，非 73 原文）：

- **超过 45 分钟** → 拆卡。信号：验收判据 > 6 条、独占文件跨多个互不相关的目录、
  goal 里出现「并且」。
- **低于 15 分钟** → 并入同主题、同独占文件的相邻卡，不单开（避免派单开销大于产出）。
- 粒度是判据侧的约束，不是计时考核：判据条数与可判定性才是被检查的对象。

### 7.3 单批上限：8

同一并发批次**同时进行的卡不超过 8 张**。超出即拆批（73 §3 实例：W2 新增 2 张卡后共 10 张
> 8，拆成 W2a 6 张 / W2b 4 张，db 卡另因 compose 项目名固定单独串行验证）。

上限的依据是合并纪律而非算力：批次末由本地总闸 `pre-merge.sh` 一次 squash、跑全量、推 `main`，
批越大，共享状态回写与冲突面越大。`decision` / `needs-human` 卡不占并发名额（本来就不派 AI）。
