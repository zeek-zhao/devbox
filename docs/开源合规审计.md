## 3. 逐项发现与依据

### A. 许可证与版权

#### A-1　无 LICENSE（阻断）

```
$ ls LICENSE* COPYING* NOTICE*
NONE
$ curl .../repos/zeek-zhao/devbox | jq .license
null
```

没有许可证时，默认法律状态是「保留所有权利」。别人 fork 之后**没有合法使用权**，
连「拿去学」都处在灰区。对教学仓库来说这是致命的——仓库的目的就是让人抄着学。

**处置**：`LICENSE` 放 Apache-2.0 全文（11358 字节，来自 apache.org 官方文本），
`NOTICE` 声明版权归属与第三方组件。

**为什么选 Apache-2.0 而不是 MIT**：这个仓库的代码会被人整段抄进自己的项目，
Apache-2.0 比 MIT 多两样东西——**明示的专利授权**（第 3 条）与**商标条款**（第 6 条）。
前者避免贡献者日后拿专利起诉使用者，后者防止别人拿 `devbox` 这个名字做衍生产品。
代价是文本更长、需要维护 NOTICE，对本仓库可以接受。

不选 GPL/AGPL：教学仓库用 copyleft 会直接劝退「想抄一段去用」的学习者，与目标冲突。

### B. 提交历史与身份

#### B-1 / B-2 / B-3　作者身份不唯一（阻断）

重写前的统计：

```
$ git log --all --format='%an <%ae>' | sort | uniq -c | sort -rn
    179 zeek.zhao <zeek.zhao@foxmail.com>
      1 zeek-zhao <42319166+zeek-zhao@users.noreply.github.com>
      1 RollingWireless-Zeek.Zhao <zeek.zhao@<企业域名>>

$ git log --all --format='%cn <%ce>' | sort | uniq -c | sort -rn
    179 zeek.zhao <zeek.zhao@foxmail.com>
      2 GitHub <noreply@github.com>
```

三个问题叠在一起：

1. **企业域名邮箱进了公开历史**。这是最容易被企业合规挑的一条：公开仓库上
   `git log` 就能看到「某公司邮箱 + 某内网地址」绑在一起，等于公开了内部环境线索。
2. **committer 是 `GitHub <noreply@github.com>`**，来自网页端提交，与本地提交的
   author/committer 不一致，`git blame` 会显示两个来源。
3. **`Co-authored-by` 尾巴**让「这行代码谁负责」变模糊。本仓库的两条恰好是同一人，
   但形态上已经破坏了单一贡献者的事实。

**处置**：`git filter-repo` 全量重写，用 `--commit-callback` 强制改写
author/committer 的 name 与 email，用 `--message-callback` 正则删除
`Co-authored-by` 行。

**验证**（重写后）：

```
$ git log --all --format='%an <%ae>' | sort -u
zeek.zhao <zeek.zhao@foxmail.com>          # 唯一一行
$ git log --all --format='%cn <%ce>' | sort -u
zeek.zhao <zeek.zhao@foxmail.com>          # 唯一一行
```

**为什么保留历史而不是新建仓库**：180 个提交的演进过程对学习者有价值（能看到一个
用例怎么从粗糙改到可验证）；而重写的成本可控——仓库只有 285 KiB、122 个主分支提交，
重写耗时 0.35 秒。

**代价**：所有 SHA 变化。`v0.1.0` 已重建（`133c9d1` → `dd23d29`），
13 个 `feat/*` 与 1 个 `backup/*` 分支全部失效并已删除，本地 22 个 worktree 已清理。

- 这些服务只在 Docker 内部网络监听，`docker-compose.yml` 没有把它们映射到宿主机的

### F. 流水线与权限

#### F-1　公开仓的 GHCR 推送权限（中）

这是**转公开后才会炸**的一条。私有仓的 `GITHUB_TOKEN` 默认有写权限；**公开仓默认只读**。

**处置**：在 workflow 顶层显式声明权限（见第 4 节）。

顺带修的同类问题：

  改为 30 分钟兜底
- `examples` / 镜像 job 原来没有 timeout，一个真挂住的用例能烧到 GitHub 的 6 小时上限

#### F-2　一档全量的实测记录

改 YAML 只证明「写对了」，不证明「跑通了」。转公开后连跑五轮，每轮都逐 job 看明细：

| 运行 | 提交 | job | 结果 | 耗时 |
|---|---|---|---|---|
| `41292000003` | `2bf5e81` | 33 | ❌ `用例-db` 红 | — |
| `41293049314` | `85df246` | 33 | ✅ 33/33 | 12.4 分钟 |
| `41293246434` | `f2d0828` | 33 | ✅ 33/33 | 21.1 分钟 |
| `41294645104` | `5949d58` | 33 | ❌ `用例-db` 红（同一用例复发） | — |
| `41295259376` | `6917851` | 33 | ✅ 33/33 | 16.7 分钟 |

两轮全绿之间差 8.7 分钟，差在 `镜像重建 / all + runtime` 这一步要不要从零构建
六语言总环境 —— 命中缓存 12 分钟，冷构建 21 分钟。**这是当前流水线的真实区间**，
写「约 15 分钟」是错的，写「约 25 分钟」也偏高。

第一轮的红是**真发现**，不是噪声：`db` 的 77 个用例是第一次进 CI，其中一个
（`L2-10-conn-security`）在 runner 上静默失败（`FAIL (exit!=0)`，stderr 全空），
而同一用例在 215 上冷启动重跑（`docker compose down -v` + 删镜像 + 重建 + `wait-ready`）却通过。

处置方式刻意不是「放宽判据」：

- `db/scripts/run-example.sh` 失败时**连 stdout 一起打**，并显式处理「stdout 与 stderr 都空」的情况
- 用例本身加 `ERR` trap 打印失败行号与失败命令
- 唯一一处 `>/dev/null 2>&1` 改成只静默 stdout

第二轮、第三轮 33/33 全绿。**然后第四轮它又红了**，这次 ERR trap 直接指到第 38 行：

```
ERROR: 第 38 行失败: docker exec "$NAME" pg_isready -U postgres > /dev/null
```

到这一步才能下结论：不是环境差异，是**用例自己的就绪门有竞态**。
原来的写法是「循环里 `pg_isready` 成功一次就 `break`，循环外再断言一次」——
服务重启的间隙里成功一次就放行，紧接着的那次断言替它背锅。215 上连跑 10 次全过，
说明它偶发到本地根本撞不上。

处置仍然是收紧判据，不是重跑洗白：

- 就绪探测走 TCP（`-h 127.0.0.1`）而不是默认的 unix socket，避免把 initdb 阶段的临时服务当就绪
- 要求**连续 3 次**成功才放行，而不是成功一次就 `break`
- 超时后打印容器状态、退出码与 `docker logs`，让下一次失败能自证

代价是这个用例从 3 秒变成 5–6 秒。这个代价该付：偶发失败被重跑洗掉一次，
下一次它会以更贵的方式回来。

第五轮 33/33 全绿，`用例-db` 整个 job 用时 200 秒。

## 5. 残留风险

### 5.1　旧提交对象仍可按 SHA 访问（低）

`git push --force` 加删除 ref 之后，旧提交不再被任何 ref 引用，但 GitHub 的对象回收
是异步的。实测重写后立刻查询旧 SHA 仍返回 200：

```
$ curl -o /dev/null -w '%{http_code}' .../repos/zeek-zhao/devbox/commits/c6b39c4...
200
```

**影响**：知道完整 40 位 SHA 的人可能取到旧提交的元数据（一个 RFC1918 私有地址、
两个非规范作者邮箱）。不会进入搜索索引，也没有 ref 指向它们。

**三种处置**，按彻底程度排序：

1. **删除仓库后重建**（最彻底，秒清所有对象；代价是丢失已关闭的 PR 历史）
2. **联系 GitHub Support 触发 GC**（保留仓库，需等待）
3. **接受并记录**（当前选择）

### 5.2　外部贡献者的身份

`main` 的历史要求单一身份，但**外部贡献者保留自己的署名**——这是开源惯例，
强行把别人的提交改成维护者邮箱等于伪造。门禁的实现方式因此分两档：

- `push main` 与打 tag：全历史必须命中白名单，**硬失败**
- `pull_request`：只检查「有没有 AI 署名尾巴」，外部作者身份**只告警**

### 5.3　fork PR 的镜像推送

公开仓的 fork PR 拿不到可写的 `GITHUB_TOKEN`，`images` job 的 push 步骤会跳过
（构建仍然跑）。这是 GitHub 的机制，不是配置问题。

## 6. 复扫方法

以下命令可在任意克隆上重跑，用于定期自查。全部只读。

```bash
# ① 密钥与私钥
git grep -nIE 'ghp_[A-Za-z0-9]{20,}|github_pat_[A-Za-z0-9_]{20,}|gho_[A-Za-z0-9]{20,}|sk-[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----'

# ② 内网地址与内部主机名
git grep -nIE '10\.[0-9]+\.[0-9]+\.[0-9]+|192\.168\.[0-9]+\.[0-9]+|/home/jenkins|RSZ-ED-SVR'

# ③ 历史全域扫描（不只是当前树）
git grep -lIE '10\.[0-9]+\.[0-9]+\.[0-9]+' $(git rev-list --all) 2>/dev/null | head

# ④ 作者与提交者身份
git log --all --format='%an <%ae>' | sort | uniq -c | sort -rn
git log --all --format='%cn <%ce>' | sort | uniq -c | sort -rn

# ⑤ AI 署名与生成器标记
git log --all --format='%b' | grep -iE 'co-authored-by|generated with|claude|copilot|chatgpt|openai|cursor|gemini'

# ⑥ 第三方代码的版权头（有命中就说明可能抄了别人的代码）
git grep -nIiE 'copyright|SPDX-License-Identifier'

# ⑦ 大文件
git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectsize) %(rest)' \
  | awk '$1=="blob" && $2>200000 {print $2, $3}' | sort -rn | head

# ⑧ 不该入库的目录
git ls-files | grep -E '^(logs|tasks|tools|\.dev)/'

# ⑨ 仓库设置
curl -sS -H "Authorization: token $TOKEN" https://api.github.com/repos/zeek-zhao/devbox \
  | jq '{private, visibility, license: .license.spdx_id, has_issues, default_branch}'
```

`scripts/check-authors.sh` 把 ④⑤ 固化成可执行门禁，随 CI 一起跑。

**② 与 ⑥ 会自指**：本节贴了正则原文，正文里也写了 `copyright` 这个词，所以直接在仓库根跑
