# 排障总入口

> 你正在排查某个具体故障——从症状进来，跳到对应的轨与手册；
> 模型与分类（为什么这样分类）见 [81-错误处理四模型与分类法](81-错误处理四模型与分类法.md)，
> 错误结构见 [82-错误码与错误结构](82-错误码与错误结构.md)。
> 每条命令**可原样粘贴**；命令契约统一为
> `TAG=latest scripts/run-example.sh <轨道> <用例ID>`。

## 1. 先分诊：是基础设施还是你的代码

**症状：镜像拉取失败 / `TLS handshake timeout`（docker.m.daocloud.io）/ `Could not resolve 'archive.ubuntu.com'` / service not running / runner 磁盘或网络报错。**

这是**基础设施瞬态故障（infra_transient）**，按 [78-CI失败分类规范](78-CI失败分类规范.md) §2.1
直接重跑，**不要改 db 用例或任何被测代码**——判据：失败面与改动无关、同一提交重跑结论翻转、
命中基础设施错误串。处理动作：

```bash
# 只重跑：推同一个 commit 重新触发，或本地重跑前先确认镜像本地可解析
docker image ls | grep devbox
```

本地自检通过、CI 又挂时，到失败 job 的日志里找上面五个错误串；命中即 infra_transient，
到对应 issue 里评论留痕（像 #323 那样写明分类依据），**不改代码、不重写用例**。

## 3. 排障时的三条纪律

1. **先分类再动手**——错误先归入五分类（[81 §3](81-错误处理四模型与分类法.md)），
   transient 直接重试，permanent 别浪费时间重试。
2. **证据落 issue**——分类结论（尤其 infra_transient）要在对应 issue 评论里写明依据；
   「同 commit 重跑翻绿」就是最硬的证据。
3. **不吞现象**——排查中发现的次生现象记进手册对应节，而不是只在口头里说；
   各轨手册的「四件套」（现象/定位/修复/验证）就是为此准备的格式。
