## S-01　TAG 与 IMAGE_TAG 两名不一致

### 典型现象

CI 上同一门语言的 6 个用例 job 全红，报「镜像不存在 / pull 失败」；
但本地逐条跑同样的用例全部通过——各跑各的都「正常」，合到 CI 就红。

### 先做的三个检查

1. 本地与 CI 传的镜像标签变量是否同一个名字：runner 读 `TAG`，CI 传 `IMAGE_TAG`；
2. `TAG=latest scripts/run-example.sh <track> <ID>` 本地真跑一次，确认 runner 本身没坏；
3. 对比 CI 报错里的镜像名与本地实际使用的镜像名是否逐字一致。

### 定位命令

```bash
grep -n 'TAG' scripts/run-example.sh | head        # runner 读哪个变量
grep -rn 'IMAGE_TAG' .github/workflows/            # CI 传哪个变量
TAG=latest scripts/run-example.sh <track> <ID>     # 本地复跑
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| CI 红、本地绿 | 变量名不一致，CI 的值没传进 runner | `grep` 两处变量名对一遍 |
| 本地也红 | 镜像没构建或 tag 不存在 | `docker images | grep devbox` |
| 改名后 CI 还红 | 有一处残留旧名 | 全仓 grep 旧名 |

### 修复与预防

修复：统一写法 `TAG=latest`（`IMAGE_TAG` 作为兼容别名保留在 runner 里）。
预防：新增环境变量时先在 runner 与 workflow 两边对一次名字（[60](60-AI工作指南.md) §5 坑 1）；
指南里的命令统一 `TAG=` 前缀。

## S-02　`:latest` 并发覆盖被测镜像

### 典型现象

两个并发 PR 各自的用例 job 先绿后红（或结果互相矛盾）：A PR 刚推的镜像被 B PR 覆盖，
A 重跑时拉到的已经是 B 的构建产物。

### 先做的三个检查

1. 失败 PR 的 workflow 日志里 push 的镜像 tag 是不是 `:latest`；
2. 两个 PR 的时间窗是否重叠；
3. 用 sha tag 重跑一次是否恢复（能恢复 → tag 被覆盖实锤）。

### 定位命令

```bash
grep -n 'IMAGE_TAG' .github/workflows/images.yml      # 确认当前是 sha-<commit>
docker manifest inspect ghcr.io/zeek-zhao/devbox-<layer>:sha-<commit>   # 按 sha 取，可复现
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 并发 PR 结果互相污染 | 都推 `:latest`，后写覆盖先写 | 对照两份日志的 push tag |
| 复现不了旧结果 | 用了可变 tag | 换 `sha-<commit>` 重试 |
| 单个 PR 自己红 | 构建/推送瞬时故障（如 unknown blob） | 重跑该 job |

### 修复与预防

修复：PR 只推 `sha-<commit>` 不可变标签，`:latest` 只随 main 推进（`KI-08`）。
预防：可复现场景一律用 sha tag；文档不默认省略 tag（[60](60-AI工作指南.md) §5 坑 3）。

## S-03　合并冲突自动取 ours → 用例被静默退回

### 典型现象

合批「全部成功」、退出码 0、CI 还全绿——但 db 轨道用例从 77 条悄悄退回成 8 行骨架，
骨架自己也能跑通，数字口径对不上才发现。

### 先做的三个检查

1. 合并提交的 diff 里被改文件数是否异常（远超本批分支的独占文件）；
2. 用例计数是否与真本一致：`ls */examples/*/run.sh | wc -l` 对比 659 口径；
3. 合批日志里有没有 conflict 处理记录（`--auto-resolve` 打印的取边决定）。

### 定位命令

```bash
ls */examples/*/run.sh | wc -l                       # 磁盘实测用例数
git show <merge-commit> --stat | tail -5             # 合并提交实际动了哪些文件
git log --oneline --all -- db/examples | tail -5     # db 用例目录的最近变更
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 合并后用例数变少 | 冲突自动取 ours，删掉了别卡的改动 | `git show --stat` 对照 |
| CI 仍全绿 | 骨架用例自己能跑通，绿不等于内容在 | 数数，别信绿 |
| 只有一个文件冲突 | 多卡同改共享文件 | 对照 [70](70-并行AI开发计划.md) §2.2 独占表 |

### 修复与预防

修复：pre-merge 默认不自动解冲突，停下来人工看。
预防：一卡一目录一分支、只改独占文件；共享文件由集成卡一次回写（[70](70-并行AI开发计划.md) §2.2 规则 A）。

## S-04　db toolbox 以 root 运行

### 典型现象

九层 devbox 镜像已全部非 root（默认 `dev` 用户），但 db 轨道的客户端容器里
`whoami` 返回 root——与语言轨道行为不一致。

### 先做的三个检查

1. 看 `db/docker/toolbox/Dockerfile` 有没有 `USER` 指令；
2. 确认它的使用路径：`docker compose exec` 进去跑客户端，只在内网 compose 网络里；
3. 确认它是否往宿主 bind mount 写文件（不写 → 风险面小）。

### 定位命令

```bash
grep -n 'USER' db/docker/toolbox/Dockerfile           # 无输出即默认 root
grep -rn 'toolbox' db/docker/docker-compose.yml
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| toolbox 是 root | Dockerfile 没写 USER | grep |
| 改成非 root 后 db 用例红 | `docker compose exec` 的用户语义连带变化 | 本地 compose 复跑 |
| 只有 toolbox 特殊 | 独立镜像（FROM ubuntu），没跟上九层的改造 | 对照 `images/` 下各 Dockerfile |

### 修复与预防

结论：**暂不改是取舍**（`KI-07`）——改它要连带调整 77 条 db 用例依赖的 exec 用户语义，
收益小风险大。预防：新增独立镜像时对照主镜像体系的安全默认（非 root、显式提权入口）。

## S-05　文档/注释与代码漂移

### 典型现象

文档写的口径与磁盘实测对不上：注释里残留旧用例数 608（实际 659）；
`images/runtime/Dockerfile` 注释写 `python3-minimal`、实际 `apt install python3`。

### 先做的三个检查

1. 数字以磁盘实测为准：`ls */examples/*/run.sh | wc -l`；
2. 注释与实现对照：读 Dockerfile 的实际 RUN 指令，不抄注释（[60](60-AI工作指南.md) §5 坑 6）；
3. 判断改动是否命中 `scripts/gate-files.txt`——命中就登记编号，不顺手改。

### 定位命令

```bash
ls */examples/*/run.sh | wc -l
grep -n 'python3' images/runtime/Dockerfile
grep -rn '608' scripts/ docs/ | grep -v '659'
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 数字两套口径 | 门禁注释残留 | grep 对比实测 |
| 注释与安装包不符 | 注释陈旧 | 读 RUN 指令 |
| 改注释导致 CI 红 | 命中了门禁文件 | `check-gate-files.sh` |

### 修复与预防

修复：文档按实测改正（已完成）；门禁文件内的残留单独登记编号（`Q-S-07` / `Q-S-08`），
由人工放行处理，自动化不顺手改。预防：单一真本纪律（[60](60-AI工作指南.md) §1）；
以代码为准，不抄注释。

## S-06　镜像探测失败被误读为代码问题

### 典型现象

PR 一片红，报错像「用例失败」，实际是镜像 pull 不下来——代码根本没被执行过。

### 先做的三个检查

1. `probe` job 是否红（它只验镜像存在性，秒级）；
2. 本地 `docker pull` 同一 tag 是否成功；
3. 报错发生在编译/运行之前还是之后。

### 定位命令

```bash
docker pull ghcr.io/zeek-zhao/devbox-<layer>:latest
TAG=latest scripts/run-example.sh <track> <ID> --keep   # 卡在 pull 阶段即环境问题
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| probe 红、用例红 | 镜像没建/没推 | 先修镜像再谈用例 |
| probe 绿、用例红 | 真是代码问题 | 本地按 §S-01 排查 |
| 时红时绿 | 推送/网络瞬时故障 | 重跑 job |

### 修复与预防

修复：`probe` 独立成 job，把「镜像没建」与「代码有问题」分开报（[02-流水线](02-流水线.md)）。
预防：看到整片红先看 probe；任何「探测不到就跳过」的分支必须能报红或显式记录，防假绿
（[60](60-AI工作指南.md) §5 坑 2）。

## S-07　CI 全绿 ≠ 教学质量达标

### 典型现象

覆盖率、格式、用例全部绿，但抽读发现用例的考点说明讲错、边界没覆盖、
覆盖表只证明「ID 出现在文件里」不证明「文件真在用这个模式」。

### 先做的三个检查

1. 分清机器判据与人工判据：跑得过 ≠ 教得对（`KI-01`）；
2. 抽读用例 README 的考点说明与代码实际行为是否一致；
3. 抽读覆盖落点文件是否真在用声明的模式。

### 定位命令

```bash
cat cpp/examples/<ID>/README.md          # 考点说明（人工判读）
grep -rn '<模式关键词>' go/project/       # 覆盖落点抽查
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 全绿但讲错 | 判定标准不覆盖语义 | 人工抽读（判据：问题数 ≤ 2/10） |
| 覆盖表自洽但失真 | ID 存在 ≠ 模式在用 | 抽读落点文件 |
| 想自动化语义判据 | 超出自动化边界 | 登记为 needs-human |

### 修复与预防

修复：`#178` 已按人工判据闭环（2026-11-04 确认通过）。
预防：`decision` / `needs-human` 类卡不派自动化（[60](60-AI工作指南.md) §4）；
硬关口 C6/C7/C9 的人工检验记录写进对应 issue。

## S-08　L4 覆盖豁免掩盖「没接入」

### 典型现象

覆盖表显示 L4 设计模式用例「已接入」毕业项目，实际是 `coverage: exempt` 整批豁免——
表自洽，但毕业项目里根本没有这些模式。

### 先做的三个检查

1. 数豁免行：`grep -c 'coverage: exempt' <lang>/project/COVERAGE.md`；
2. 豁免是否逐条写了具体理由（整批豁免 = 没写）；
3. 抽读一个「已接入」落点，确认模式真的在用。

### 定位命令

```bash
grep -n 'coverage: exempt' go/project/COVERAGE.md
bash scripts/coverage-check.sh --strict
grep -rn 'L4' go/project/ --include='*.go' | head
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| exempt 数量成片 | 选 A 整批豁免的历史遗留 | 数行数（2026-11-04 实测 43 条） |
| 豁免无理由 | 「可复用结构练习」一句话带过 | 逐条看理由字段 |
| 接入后项目变形 | 为凑覆盖改形 | 人工抽读（`KI-02` 的风险） |

### 修复与预防

修复：`#179` 定案 B——默认强制接入，例外单条举证 + 人工判定；落地由 `#228` 跟踪
（go/java/python 三路，不进自动合并队列）。
预防：「默认强制 + 例外需举证」；不许把「没写」记成「不适用」（[41](41-里程碑拆分.md) §4）。


## S-09　C：堆越界 + 双重释放（裸跑沉默通过）

### 可复现现象

堆缓冲区越界写 4 字节、再对同一段内存 double free：裸编译（无工具）运行**退出 0、无任何提示**；
开 ASan 立刻报 `heap-buffer-overflow`，修复越界后再次触发释放路径则报 `attempting double-free`。
可复现：M11-W1 样板 `cpp/labs/T-001-asan-heap-overflow/`（同族现象，C 轨道 lab 用双重释放变体）。

### 前 60 秒三条只读检查（各带期望输出）

1. 裸跑程序看退出码——期望输出：`echo $?` = `0`，stdout 正常（**这就是「健康假象」**）；
2. `ldd <二进制> | grep -c asan` —— 期望输出：`0`（裸构建不含 ASan，解释为什么没报）；
3. `ls -l <二进制>` 看构建时间戳——期望输出：时间戳与最近一次源码修改一致（确认测的是新二进制，防 S-06）。

### 定位命令

```bash
gcc -g -fsanitize=address -o bad bad.c && ./bad        # ASan 构建重跑
valgrind --leak-check=full ./bad                        # 无工具构建 + valgrind
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 裸跑退出 0，ASan 报越界 | 4 字节落在堆分配布局的空闲区，未触发崩溃 | 换分配顺序/加大越界量，症状随布局漂移（不可靠） |
| `attempting double-free` | 同一段内存两次 `free` | ASan 报告的两处分配/释放栈互证 |
| 只报泄漏不报越界 | 越界量太小未踩到哨兵区 | valgrind 与 ASan 交叉（工具互证，不单信一个） |

### 修复与预防

修复：越界循环边界改 `<`；释放后置 `NULL` 并只保留一处 `free`。
预防：所有 C 用例默认带 `-fsanitize=address` 跑一遍（现有 L2-006/L2-009 的形态）；code review 里
「边界条件 + 所权单一」两问固定化。

## S-10　Go：goroutine 泄漏（NumGoroutine 只增不减）

### 可复现现象

往无读取端的 channel 发送，goroutine 永久阻塞：程序正常退出 0（若主协程不等待），
但 `runtime.NumGoroutine()` 在触发前后从 1 涨到 2 且不回落。可复现：M11-W2 Go lab（类型②实验，
真实输出 `before: 1` / `after: 2`）。

### 前 60 秒三条只读检查（各带期望输出）

1. `go vet ./...` —— 期望输出：无输出（vet 查不出泄漏，排除「忘跑 vet」）；
2. `GODEBUG=schedtrace=1000 ./app 2>&1 | head -3` —— 期望输出：sched 队列里 goroutine 数持续 >1；
3. `go build -race && ./app` —— 期望输出：无 race 报告（泄漏不是数据竞争，排除错误方向）。

### 定位命令

```bash
go test -run TestLeak -v ./...          # 带 NumGoroutine 对照的测试
go tool pprof -http=: <profile>          # goroutine profile 看阻塞点
curl -s localhost:<port>/debug/pprof/goroutine?debug=1 | head -20
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| NumGoroutine 持续增长 | 发送/接收端不平衡：channel 无读端或无缓冲满 | profile 看 `chan send` 阻塞栈 |
| 泄漏但无 channel | `context` 未取消 / `time.After` 在循环里 | 栈顶是 `time.Sleep` 或 `select` 无 default |
| 只在高并发出现 | 关闭顺序：先关 channel 后收尾 | `go vet` + 复现脚本缩并发到 2 |

### 修复与预防

修复：加缓冲/读端，或用 `context` 级联取消。
预防：goroutine 启动点必须配「退出路径」；并发测试断言 NumGoroutine 收敛（进 CI 的防退化测试形态）。

## S-11　Rust：借用检查 E0502（不可变与可变借用冲突）

### 可复现现象

同时持有 `Vec` 的不可变引用（迭代）又调用可变方法：编译期直接被拒，退出码 1，
错误码 `error[E0502]`，附三条标注（原借用位置 / 冲突借用位置 / 借用结束点）。
可复现：M11-W2 Rust lab（类型②实验，三标注原样记录）。

### 前 60 秒三条只读检查（各带期望输出）

1. 看 cargo 输出首行错误码——期望输出：`error[E0502]: cannot borrow ... as mutable because it is also borrowed as immutable`；
2. 数标注段数——期望输出：三条 `-->` 标注（NLL 精确指出借用生命周期）；
3. `cargo build --message-format=short` —— 期望输出：单行定位（文件:行号），确认无连带错误。

### 定位命令

```bash
cargo check 2>&1 | head -30              # 错误码 + 三标注
cargo clippy 2>&1 | tail -5              # 顺带看是否有惯用法建议
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| E0502 | 迭代器还活着就 push/修改容器 | 把可变操作移出迭代块再编译 |
| E0502 但逻辑上没同时用 | 借用存活期被 NLL 之外的因素拉长（如中间变量） | 缩小借用作用域（加大括号） |
| 换成索引遍历能过 | 迭代器借用了整个容器 | 权衡：索引越界风险 vs 借用约束 |

### 修复与预防

修复：拆分「读」与「改」两个阶段，或先 `collect` 再改。
预防：不与借用检查器对抗——需要同时读写时用索引/分片拆分；把「编译器三标注怎么读」写成新手指引（本 lab 的判读内容）。

## S-12　Shell：分词炸路径 + 管道吞错（假绿同型）

### 可复现现象

`cat $f`（`f` 含空格）被拆成两个参数报 `No such file or directory`；
`set -e` 下 `false | true` 整条管道退出 0——中间命令失败被吞，脚本「全绿」继续跑
（与 S-03「静默退回仍全绿」同型的假绿）。可复现：M11-W2 Shell lab（类型②实验，真实输出
`cat: /tmp/my: No such file or directory` + `survived-middle-failure`）。

### 前 60 秒三条只读检查（各带期望输出）

1. `echo "$f"` —— 期望输出：完整路径（变量本身没问题，是展开后被分词）；
2. `shellcheck -S warning script.sh` —— 期望输出：`SC2086`（未加引号的变量展开）；
3. `bash -x script.sh 2>&1 | grep -m1 'cat '` —— 期望输出：`cat /tmp/my dir/file.txt`（亲眼看到拆成两个词）。

### 定位命令

```bash
set -- $f; echo $#     # 看分词结果：2（错） vs set -- "$f" 后 1（对）
bash -x script.sh       # 逐行追踪实际执行
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 带空格路径被拆 | 变量展开未加引号 | SC2086；`set --` 数参数 |
| 中间命令失败被吞 | 管道只看最后一个命令的退出码 | `set -o pipefail` 后复跑 |
| `if f` 里 `set -e` 失效 | 条件上下文豁免 errexit | 命令体里加显式 `|| return 1` |

### 修复与预防

修复：所有变量展开加双引号；脚本头 `set -euo pipefail`。
预防：shellcheck 进门禁（warning 级，本仓库 `SHELLCHECK_SEVERITY` 真本）；「管道中间失败」写进评审清单。

## S-13　Python：虚拟环境串味（装进 A 环境从 B 里 import）

### 可复现现象

包装进 venvA，venvB/系统解释器里 `import` 报 `ModuleNotFoundError: No module named 'myproj'`；
`PYTHONPATH` 指到 venvA 后 venvB 能「串味」成功 import——依赖解析跟人走的不是同一个环境。
可复现：M11-W2 Python lab（类型②实验，真实输出 `ModuleNotFoundError` + 串味成功对照）。

### 前 60 秒三条只读检查（各带期望输出）

1. `which python3 && which pip` —— 期望输出：两者指向**同一个** venv 的 bin/（不同 → 找到根因）；
2. `python3 -m pip list | grep -c myproj` —— 期望输出：`0`（当前环境确实没装）；
3. `echo $PYTHONPATH` —— 期望输出：空（非空即串味通道）。

### 定位命令

```bash
python3 -c "import sys; print(sys.executable, sys.path)"   # 实际解释器与搜索路径
python3 -m pip show myproj                                  # 装在哪、版本
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 装了但 import 不到 | pip 与 python3 来自不同环境 | `sys.executable` 对照 |
| 没装也能 import | PYTHONPATH/sitecustomize 串味 | `sys.path` 里混进别的 venv |
| 系统层 pip 被拒 | PEP 668 externally-managed-environment | 错误原文即此提示，属正常防线 |

### 修复与预防

修复：统一用 `python3 -m pip`；激活正确的 venv 再操作；清掉杂散 PYTHONPATH。
预防：CI 里固定 `python3 -m pip` 写法（现有 L2-005-ruff-check 同型）；镜像内系统 Python 按需隔离。

## S-14　Java：两把锁反序死锁（jcmd 抓互等闭环）

### 可复现现象

两个线程以相反顺序获取 lockA/lockB：程序不退出也不报错（活着但卡死）；
`jcmd <pid> Thread.print` 输出 `Found one Java-level deadlock:`，互等闭环一目了然。
可复现：M11-W2 Java lab（类型②实验，真实输出含 `"worker-1": waiting to lock monitor ... which is held by "worker-2"`）。

### 前 60 秒三条只读检查（各带期望输出）

1. `jps -l` —— 期望输出：进程还在（不是崩了，是卡死）；
2. `top -b -n1 -p <pid>` —— 期望输出：CPU 占用接近 0%（区分「忙循环卡死」与「锁等待卡死」）；
3. `jstack <pid> | grep -c 'BLOCKED'` —— 期望输出：`>= 2`（两个线程都在等锁）。

### 定位命令

```bash
jcmd <pid> Thread.print | grep -A8 'Found one Java-level deadlock'   # 互等闭环与两把锁地址
jcmd <pid> VM.uptime                                                 # 排除「启动慢」
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| Java-level deadlock | 加锁顺序不一致 | Thread.print 的闭环描述直接指认两把锁 |
| 卡死但无 deadlock 段 | 死等外部资源（连接池/远端） | 看 waiting on condition 的栈顶 |
| 偶发才卡 | 锁序随分支变化 | 压测 + 多次抓栈对比持锁顺序 |

### 修复与预防

修复：全仓统一加锁顺序（按锁对象的全局序），或改 `tryLock` 带超时。
预防：锁获取点集中在单一工具方法；`jcmd Thread.print` 抓栈纳入排障 SOP（本 lab 的定位命令）。
