# CI 失败取证规范

> 对应任务卡 `M12-CI-06`（#342）。分类口径的唯一真本是 [78-CI失败分类规范](78-CI失败分类规范.md)，
> trace schema 真本是 [80-M12度量规范](80-M12度量规范.md)；本文只定**取证操作**：
> 失败时保留哪些日志、怎么下载、怎么留档、往 `$GITHUB_STEP_SUMMARY` 写什么。
> 本文不改 `ci.yml`、不实现上传逻辑（接入归 `#264` 人工批次）。

## 1. 日志下载：两跳命令与 401 取证坑

GitHub 把 Actions 日志 302 到 Azure blob（`productionresultssa*.blob.core.windows.net`）。
**第一次请求带 `Authorization`（打 api.github.com），第二次请求（跟 302 到 blob）必须不带**——
带了会返回 401，因为 blob 用的是预签名 URL，多余的头会破坏签名校验。
因此**禁止 `curl -L` 一跳到底**：`-L` 会把 Authorization 原样带到 blob。正确写法是手工两跳：

```bash
# 第 1 跳：向 api.github.com 要 302 Location（带 token）
LOC=$(curl -sD - -o /dev/null \
  -H "Authorization: Bearer $GH_TOKEN" \
  "https://api.github.com/repos/zeek-zhao/devbox/actions/jobs/$JOB_ID/logs" \
  | grep -i '^location:' | tr -d '\r' | awk '{print $2}')

# 第 2 跳：跟随 Location 下载日志（不带 Authorization——带了必 401）
curl -s -o "$JOB_ID.log" "$LOC"
```

**实测留痕（2026-11-12，run `43075612711` 的 job `130714505275`）**：按上述两跳取得
145102 字节日志，`grep -ciE "error|timeout"` 命中 14 行；二跳未带任何认证头，`rc=0`。
该实测同时是 [83-排障总入口](83-排障总入口.md) §1 infra_transient 分诊的证据来源。

取证三纪律（与 [78](78-CI失败分类规范.md) §2.1 一致）：

1. **grep 原文，不转述**——取证评论里贴错误行原样，不写「大概是超时了」；
2. **同 job 对照**——给出同一 job 在相邻 run 的结论（success 或同因失败），供分类复核；
3. **首次失败即留档**——分类可以后补，日志必须当场抓：GitHub 日志仅保留 90 天，
   到期 302 链路整体失效，届时无法补证（docs/78 §4「首次发现即登记」的落地原因）。

## 2. artifact 命名与保留天数

失败留档一律走 artifact（workflow 上传后可从 run 页面下载），命名契约：

| 场景 | 命名 | 保留 |
|---|---|---|
| 首次失败日志（必传） | `ci-fail-<run_id>-<job_slug>` | **30 天** |
| 首次失败的关键行摘录（必传） | `ci-fail-<run_id>-<job_slug>-grep` | 30 天 |
| 重试 run 的对照日志（如有） | `ci-retry-<run_id>-<job_slug>` | 30 天 |

- `job_slug`：job 名里的 `/` 与空格换成 `-`（如 `用例-db` → `用例-db` 保留中文，仅替换路径分隔符）；
- **首次失败留档是 [80-M12度量规范](80-M12度量规范.md) §2 trace 的证据底座**：
  `ci_failure.first_failure_archive` 字段填 artifact 名或 `UNVERIFIED`（docs/78 §4）；
- 保留 30 天短于 GitHub 默认 90 天日志：留档的价值集中在分类与复核窗口内（两轮同因判定、
  flake rate 周报），30 天足够且省存储；被引用进 trace 的 artifact 在复核关闭前不许删；
- 本地补档（blob 二跳产物）命名 `<JOB_ID>.log`，归档目录自定（如 `metrics/ci-fail-logs/`），
  不进 `examples/`、不计用例数。

## 3. `$GITHUB_STEP_SUMMARY` 内容契约

失败 job 的收尾 step 向 `$GITHUB_STEP_SUMMARY` 追加一段 Markdown，固定五要素
（顺序即书写顺序，缺项写 `UNVERIFIED`，不空着）：

```markdown
## CI 失败取证（run <run_id>）
- **job / step**：<job 名> / <step 名>
- **分类**：<infra_transient | real_regression | flaky_test | UNVERIFIED>（依据 docs/78 §2）
- **命中信号**：<grep 原文关键行，最多 3 行；无则写「无 infra/code 信号」>
- **留档**：<artifact 名或 UNVERIFIED>；**移除条件**：<docs/78 §4 必填项或 UNVERIFIED>
- **重试**：<同 head_sha 结论序列或「未重试」；重试通过不折叠本条，首次结论仍为 failure>
```

要点：

- **分类判定用 [scripts/classify-ci-failure.sh](../scripts/classify-ci-failure.sh)（#338 产出）跑一遍**，
  把其 stderr 摘要与 JSON trace 一并贴进 summary/trace，避免手判口径漂移；
- **重试通过不删摘要**：summary 是首次结论的展示面，`fail → pass` 必须可见
  （[78](78-CI失败分类规范.md) §4「不把重试后绿显示成干净的绿」）；
- summary 里**不写修复动作**、不写「已修复」——那是后续卡的事，取证面只记录事实。
