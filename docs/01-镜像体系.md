# 镜像体系

## 1. 分层图

```
                    ubuntu:24.04
                         │
                  ┌──────┴──────┐
                  │             │
            devbox-base    devbox-runtime      ← runtime 刻意不继承 base
            (公共底座)       (部署运行时)
                  │
            devbox-tool     ← 调试工具层（独立可用）
                  │
     ┌────────┬──────┬──────┬───────┬────────┬──────┬──────┐
     │        │      │      │       │        │      │      │
   cpp       go    rust   shell   python   java   vue
     │        │      │      │       │        │      │
     └────────┴──────┴──────┴───────┴────────┴──────┴──────┘
                  │
            devbox-all      ← 七个工具链安装层；C 复用 cpp
```

C 与 C++ 是两条学习轨道，共用 `devbox-cpp` 镜像层；数据库轨道使用独立 Compose runner，不属于语言镜像矩阵。

## 2. 为什么是「并列」而不是「一条链叠到底」

链式 `base → tool → cpp → go → rust → ...` 看着更"叠加"，但：

- **中间某门语言坏了，整条链全断**。学 Rust 的人会被 Java 层的构建失败卡住。
- **无法按需拉取**。你只学 C++ 时也要拖 8G。
- **缓存失效粒度变大**。改 Java 层会让 Rust 之后的层全部重建。

并列的代价是每个语言镜像都含一份 tool 层（约 +2.2G），但 tool 层是**共享的同一个 layer digest**，
本地存一份、registry 存一份，不是真的重复 7 次。

## 3. 为什么 `all` 用 RUN 重跑，而不是 COPY 其它镜像的工具链

`COPY --from=devbox-rust /usr/local/cargo` 能省下载时间，但会得到**残废环境**：
工具链自带的二进制在，apt 装的运行时依赖（libssl、fontconfig、pkg-config、gcc 的 libgcc 等）不在，
表现是 `rustc --version` 正常、一编译就缺头文件——这种 bug 极难排查。

所以 `all` 用 7 个独立 `RUN` 调同一批 install 脚本（C 与 C++ 共用 cpp 工具链）：
- 每层独立缓存，改 java 不影响 cpp 层
- 依赖由各自的 install 脚本负责装全，不会漏
- 代价只是下载时间，镜像体积与 COPY 方案接近

## 4. 版本与 pin 策略

- 版本只在 `images/versions.env` 写一次；CI 有一条门禁专门拦「Dockerfile 里写死版本号」。
- 跨镜像引用一律用 `BASE_IMAGE=<registry>/devbox-tool:<tag>`，tag 是本次 CI 的 `sha-xxxxxxx`。
- **禁止 `FROM tool:latest` 作为语言镜像的父层**：改了 tool 层，语言镜像还在用上次 CI 的旧层，
  镜像里两套 gdb 并存且不报错。

## 5. 构建方式

| 场景 | 怎么建 |
|---|---|
| 日常迭代（改了 Dockerfile） | 215 上 `scripts/build-images.sh --only base,tool`，几分钟一轮 |
| 权威构建 | push 到 main，`images.yml` 自动跑，产物带 `sha-xxxxxxx` tag |
| 本地开发机 | 不建，只 `docker pull` |

CI 的 job 结构：

```
base-tool  ──┬──> lang-cpp ───┐
             ├──> lang-go  ───┤
             ├──> lang-rust ──┤
             ├──> lang-shell ─┤
             ├──> lang-python ├──> aggregate(all + runtime)
             ├──> lang-java ──┤
             └──> lang-vue ───┘
```

images workflow 的七个镜像层 job 在推送前必须跑通 `hello` 用例（C 复用 cpp 镜像；数据库轨道使用独立 runner），
这是唯一能证明「镜像能跑」的手段——因为本地没有 docker，静态检查全绿也可能是废镜像。

## 6. 已知限制

- **perf 不可用**：容器内 `perf` 依赖宿主内核版本，装了也大概率报版本不匹配。
  真要做性能剖析：
  ```bash
  docker run --rm -it --privileged --pid=host \
    -v /sys:/sys -v /usr/src:/usr/src -v /lib/modules:/lib/modules \
    devbox-cpp:latest bash
  ```
  或直接用 `valgrind --tool=callgrind`（容器内可用）。
- **eBPF / bpftrace**：需要 `--privileged` + 匹配的宿主内核头文件，镜像里不预装。
- **Java 只装了 Maven**：Gradle 在 24.04 源里是 4.4（太旧，不支持 Kotlin DSL 和现代插件），
  所以 Java 项目统一用 Maven + Spring Boot。需要 Gradle 时在项目里用 wrapper 下载。
- **`all` 镜像 8G+**：只在需要「一个容器里切语言」时用，日常按语言进各自容器。
