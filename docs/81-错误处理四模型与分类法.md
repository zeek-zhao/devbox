# 错误处理四模型与分类法

> 本文是**解释**类文档（Diátaxis Explanation）：回答「为什么这门语言这样处理错误」，
> 不教语法。一页一个主要承诺：给你一套能跨 9 轨迁移的心智模型 + 一张可执行的错误分类表。
> 逐轨操作步骤在各轨 `docs/错误处理指南.md`；错误码结构与字段约定见
> [82-错误码与错误结构](82-错误码与错误结构.md)。
> 写法契约（禁长篇语法讲解、每条结论可验证、不适用要声明）沿用
> [11-知识点清单增强规范](11-知识点清单增强规范.md) §4。

## 1. 为什么需要「模型」而不是「语法」

`try/catch`、`if err != nil`、`Result<T, E>` 是**写法**；它们背后是同一个问题的不同回答：

> 一个函数**可能失败**时，这个「可能」应该出现在哪里？返回值、控制流，还是类型签名？

四种模型就是四个回答。换语言时先换模型再换语法——带着异常的思维写 Go（用 panic 做分支）、
带着返回码的思维写 Rust（到处 `unwrap()`），都是模型错位，不是语法生疏。

## 2. 四种错误处理模型

### 2.1 模型一：错误即值（error as value）

**代表**：C（返回码 + `errno`）、Go（`error` 接口）、Shell（退出码 + stderr）、
db（SQLSTATE + 受影响行数）。

错误和正常数据走**同一条通道**：函数返回它，调用方像处理普通值一样检查它。
失败不改变控制流形状——`if` 还是那个 `if`。

**为什么这门语言选它**：

- C（1972）：没有异常机制可用，寄存器和调用约定也不允许隐藏的控制流；
  返回码是唯一能与汇编、操作系统调用对齐的通道。
- Go（2009）：显式拒绝异常式控制流。设计者要的是**失败点在调用链上逐行可见**——
  review 一个函数时，哪一行可能失败、失败后去哪，不用跳出函数体去找。
- Shell / db：进程与 SQL 语句的「返回通道」本来就只有退出码 / SQLSTATE，
  错误即值是环境事实，不是设计偏好。

**跨轨反例**：把 Go 的 `panic` 当异常用，在业务分支里 `panic/recover` 传递错误——
模型错位的典型。panic 的本分是**快速失败**（模型分类见 §3 的 system/permanent 类），
见 [go E-014-fail-fast](../go/examples/E-014-fail-fast/README.md)；
C 侧同型反例是**忽略返回码**（`read()` 的返回值不查就当成功），见
[c E-015-antipattern-compare](../c/examples/E-015-antipattern-compare/README.md)。

### 2.2 模型二：异常控制流（exception control flow）

**代表**：Java、Python、C++、JS/Vue（同步 `throw` + 异步 rejection）。

错误走**第二条控制流**：`throw` 把调用栈逐层炸开，直到遇到第一个匹配的 `catch`。
正常路径与失败路径在文本上分离，构造函数、运算符这些**没有返回值可借用**的位置也能报错。

**为什么这门语言选它**：

- Java：企业级代码里「每一层都检查返回码」的样板代码在 1995 年已经把 C 项目拖垮过；
  checked exception 把「这里会失败」写进方法签名，编译器强制调用方表态。
- Python：脚本语言的取向是**省事的主路径**——正常逻辑不被错误检查打断；
  EAFP（请求原谅比请求许可容易）是它的官方哲学，
  见 [python E-004-eafp-lbyl](../python/examples/E-004-eafp-lbyl/README.md)。
- C++：异常是给「构造失败」准备的——构造函数不能返回错误码，
  这是 C++ 保留异常的硬理由；同时它保留返回码两条路并用（混合模型）。

**跨轨反例**：Python 里 `except Exception: pass` 把炸开的栈吞掉——
异常模型给了你上下文丰富的栈，吞掉等于比返回码模型还糟
（db 轨同型反例 [db E-015-antipattern-swallow](../db/examples/E-015-antipattern-swallow/README.md)）；
Java 里吞 `InterruptedException` 会把「取消」这个信号也吞掉，
见 [java E-004-interrupt-handling](../java/examples/E-004-interrupt-handling/README.md)。

### 2.3 模型三：Result 代数类型

**代表**：Rust（`Result<T, E>` + `?` 运算符）、以及一切把错误建模为枚举的语言。

失败是**类型签名的一部分**：函数返回 `Result` 而不是裸值，编译器强制你在拿到 `T` 之前
先处理 `E`。错误处理从「纪律问题」变成「类型问题」。

**为什么这门语言选它**：Rust 没有异常也没有 GC，栈展开（模型二）在系统编程语境里
代价不可控，返回码（模型一）又没有编译器兜底。`Result` 是两条路的合取：
通道仍是返回值，但「必须检查」由类型系统而非自觉保证。

**跨轨反例**：满屏 `unwrap()`——类型系统搭好的强制检查被一行行亲手清零，
等价于回到「忽略返回码」的 C 反例。
见 [rust E-003-unwrap-expect-hygiene](../rust/examples/E-003-unwrap-expect-hygiene/README.md)
与 [rust E-014-antipattern-catalog](../rust/examples/E-014-antipattern-catalog/README.md)。

### 2.4 模型四：效果系统（前沿，仓库内无原生示例）

**代表**：Koka、Unison、OCaml 5 的 effect handlers。

把「这个函数可能失败」「可能做 IO」本身建模为**效果**，由类型行签名声明、由 handler 在
调用侧解释执行。可以理解为前三个模型的「类型化推论」：模型一把错误当普通值，
模型四把「可能出错」这个事实本身也变成值。

**为什么提它**：读论文、读新语言文档时会撞上它；知道它在坐标系里的位置，
四个模型就构成一条完整的谱系——**错误信息从隐式（errno 全局变量）到显式（error 值），
再到「可能失败」本身被显式声明**。

**不适用声明**：本仓库 9 轨镜像不含效果系统语言，本节是概念锚点，没有本地可运行示例
（正文其余可执行结论均已对到具体 E 例）。

## 3. 错误五分类法

分类回答的不是「怎么报」而是「怎么**办**」。每个错误先归入五类之一，动作就跟着定了：

| 类别 | 定义 | 是否重试 | 是否上报 | 是否快速失败 | 本仓库例子 |
|---|---|---|---|---|---|
| **transient** 瞬态 | 重试大概率成功的环境抖动（网络闪断、锁竞争、临时资源不足） | **重试**，带退避与上限 | 记指标，不告警 | 不——重试就是它的处理 | db 死锁 [E-003](../db/examples/E-003-deadlock-retry/README.md)；连接失败重试 [E-001](../db/examples/E-001-conn-fail-retry/README.md)；各轨退避 [c E-010](../c/examples/E-010-retry-backoff/README.md) |
| **permanent** 永久 | 重试到天荒地老也不会成功（逻辑错、数据坏、schema 冲突） | 不重试 | 告警（需要人介入） | 修不好就**快速失败**，别带病跑 | 迁移部分失败 [db E-011](../db/examples/E-011-migration-partial-fail/README.md)；备份损坏 [db E-013](../db/examples/E-013-backup-corrupt-detect/README.md) |
| **validation** 校验 | 输入不合法，责任在调用方 | 不重试（重试同样输入同样失败） | 不告警，**返回给调用方**，信息要可行动 | 立即拒绝，不进主流程 | 校验错误聚合 [python E-009](../python/examples/E-009-error-aggregation/README.md)；断言契约 [java E-009](../java/examples/E-009-assert-contract/README.md) |
| **business** 业务 | 输入合法但违反业务规则（权限不足、余额不够、重复下单） | 不重试 | 按需审计上报 | 按规则拒绝——这是**正常分支**不是故障 | 权限拒绝 [db E-008](../db/examples/E-008-permission-denied/README.md) |
| **system** 系统 | 进程级故障：OOM、配置缺失、依赖组件死亡 | 一般不重试（先熔断/降级） | **必须上报**（日志 + 告警） | **快速失败**，让进程管理器接手 | OOM 分类 [java E-008-oom-taxonomy](../java/examples/E-008-oom-taxonomy/README.md)；fail-fast [go E-014](../go/examples/E-014-fail-fast/README.md) |

两个边界判据，判「重试」时最容易混：

- **transient vs permanent 的分界线是「再试一次会不会变」**，不是「错误吓不吓人」。
  TLS 握手超时会变（重试）；外键级联陷阱不会变（db E-014 是陷阱教学，不是瞬态故障）。
- **validation vs business 的分界线是「语法对不对」**：JSON 解析失败是 validation，
  「金额为负」是 business——前者机器能判，后者只有业务规则能判。

与 [78-CI失败分类规范](78-CI失败分类规范.md) 的 `infra_transient` 对齐：
CI 里的 `TLS handshake timeout`、镜像 pull 失败就是本表的 transient——重跑是正确处理，
**不得据此改 db 用例**；那是基础设施层的锅，不是被测代码的。

## 4. 判据：在能增加价值的地方处理错误

「在哪一层 catch」不靠层级数数，靠三个问题。每一层都问，**答案全是否，就原样上抛**：

1. **能补上下文吗？**——把「这一层知道、下一层不知道」的信息附上去
   （Go `%w` 包装、Python `raise ... from`、Rust context layering）。
   例：[go E-006-error-context](../go/examples/E-006-error-context/README.md)。
2. **能做决策吗？**——只有这一层有资格决定重试 / 降级 / 放弃
   （超时预算在调用方手里，见 [go E-011-context-timeout](../go/examples/E-011-context-timeout/README.md)）。
3. **能翻译成调用方的语言吗？**——把内部实现细节（errno、SQLSTATE、第三方异常原文）
   换成边界稳定结构再出门（映射规则见 [82-错误码与错误结构](82-错误码与错误结构.md) §4）。

三问全否却仍然 catch 了，几乎必然是吞错误（五分类里所有「是否上报 = 上报」的类别
都会因此失明）。反模式对照全部落在各轨 E-015。
