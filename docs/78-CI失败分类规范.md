# CI 失败分类规范

> 对应任务卡 `M12-W1-01`（#272）。M12 六卡分工见 [ROADMAP](ROADMAP.md) Issue↔里程碑对照与
> [73-M11并发执行计划](73-M11并发执行计划.md) §12。本文只定**判定口径与留痕格式**，不改任何门禁文件：
> 单次退避等实现动作归 `#264`（人工批次），工程故障 lab 归 `#273`，`docs/30` 快照回写归 `#277` 集成卡。
> 分类纪律与 [24-G3素材池](24-G3素材池.md) 一致：**只许基于真实 run 证据分类，禁止猜**；
> 拿不到证据的字段一律写 `UNVERIFIED`，不许写「已确认」。

## 1. 为什么需要分类

一个红叉有三种完全不同的含义：环境抖了、代码真坏了、用例本身不稳定。不加区分的后果已经发生过：
纯文档提交打挂了 77 个 db 用例里的 76 个，红叉把无关的 PR 卡在总闸上（[73](73-M11并发执行计划.md) §9）。
分类的目的只有一个：**让每类失败走各自的处理路径，不让任何一类伪装成另一类。**

## 2. 失败三分类（枚举，只有这三个值）

| 分类 | 一句话定义 |
|---|---|
| `infra_transient` | 环境与基础设施抖动：镜像源、网络、runner、compose 等与被测代码无关的故障 |
| `real_regression` | 真实缺陷：被测代码或用例本身的错误，稳定复现，重跑同样失败 |
| `flaky_test` | 用例不稳定：同一 commit 无代码变化时，结果在 pass / fail 之间摆动 |

### 2.1 `infra_transient`

- **判定信号**（至少命中一条）：日志命中基础设施错误串（`TLS handshake timeout`、镜像 pull 失败、
  `service "..." is not running`、runner 磁盘或网络错误）；同一 commit 前后两个 run 结论翻转且 diff 无代码改动；
  失败面与本次改动无关（如纯文档提交打挂 db job）。
- **必留证据**：失败 run id 与 job id；命中的错误日志行（grep 原文，不转述）；
  同一 commit 或相邻 run 的结论对照（如「同 job 在另一 run 为 success」）。
- **处置动作**：取证贴到对应卡评论区留痕；按 §6 判「连续两轮同因」后才立环境故障条目；
  不动用例代码；重跑或等 `#264` 的单次退避落地。
- **反例**：把用例里逐字比对整段输出造成的偶发失败记成 `infra_transient`——那是用例自身的假失败制造机
  （断言方式纪律见 [72-排障演练规范](72-排障演练规范.md) §2），应归 `real_regression` 或 `flaky_test`。

### 2.2 `real_regression`

- **判定信号**：失败与本次 diff 有因果（改什么坏什么）；错误稳定复现（同一 head_sha 连续失败）；
  报错指向代码逻辑或断言本身，而非基础设施层。
- **必留证据**：`head_sha`；复现命令与退出码；最小复现 diff 或失败断言原文。
- **处置动作**：停并修复，或回滚引入 commit；修复 PR 必须引用本条分类留痕；
  **不得用重跑掩盖**——重跑转绿不改变首次结论的分类。
- **反例**：镜像源超时导致 76 个 db 用例报 `service "toolbox" is not running` 时按
  `real_regression` 处置、去「修用例」——那是无关红叉（§6 明确禁止）。

### 2.3 `flaky_test`

- **判定信号**：同一 `head_sha` 多次运行结论不一致；失败点含时序、端口、并发、外部依赖竞态特征；
  单跑通过、并发或 CI 上失败。
- **必留证据**：同一 `head_sha` 的多次 run id 与结论序列（按时间排）；失败日志关键行；复跑命令。
- **处置动作**：登记到 flaky 清单（§4 留痕字段）→ owner 复核 → 隔离（retry / skip 必须附注释与移除条件）→ 修复后移除。
- **反例**：rerun 通过就直接标「稳定」不再登记——rerun 通过既不证明 flaky、也不证明稳定（§3 口径）。

## 3. flake rate 口径

flake rate 衡量的是**基础设施抖动占比**，计算只认首次结论：

- **观察窗口**：按自然周或里程碑边界划定的区间，起止日期必须写进报告；
- **分母** = 观察窗口内 **push 触发**的 CI 运行数（同一 push 多个 job 只算一个运行；
  手动重跑、schedule、fork PR 触发不计入分母）；
- **分子** = 其中**首次结论为 `infra_transient`** 的运行数（重跑后转绿不改变首次结论，也不移出分子）；
- **flake rate = 分子 / 分母**（百分数，保留一位小数），报告时必须附三分类分布
  （`infra_transient` / `real_regression` / `flaky_test` 各自的运行数），供 [80-M12度量规范](80-M12度量规范.md)（#275）直接消费。

**rerun 通过 ≠ flaky，也 ≠ 稳定**：重跑通过只说明「本次故障未在重跑中复现」。
既不能据此把原 run 改判成 `flaky_test`（那是凭结果倒推分类），也不能据此宣称用例或环境稳定
（抖动本来就是低概率事件，一次复现不了不能证伪）。结论永远以**首次 run 的分类留痕**为准，
重试结果单独上报（§4）。

## 4. 首次失败留痕字段

任何一次 CI 失败，无论最终分类，**首次发现即登记一条留痕**（本文定字段；
落盘位置与消费方式归 `#273` 的工程故障 lab 与 `#275` 的 trace schema）：

| 字段 | 含义 | 缺省 |
|---|---|---|
| `run_id` | CI run id | 必填；写不出即 `UNVERIFIED` |
| `head_sha` | 该 run 对应的提交 | 必填 |
| `首次结论` | success / failure / cancelled | 必填 |
| `分类` | §2 三分类之一 | 证据不足写 `UNVERIFIED`，不许猜 |
| `重试结论` | 重跑 run 的结论与 run id | 没重跑写 `UNVERIFIED` |
| `owner` | 负责复核的人 | 缺省归维护者（[75-文档健康规范](75-文档健康规范.md) §4） |
| `复核日期` | 最近一次复核（YYYY-MM-DD） | 视同未复核 |
| `移除条件` | 满足什么条件这条留痕可移除（如「容错上线后连续 14 天无同因失败」） | 必填 |

**上报纪律：重试结果单独上报，不显示成干净绿。** 任何仪表盘、快照或报告里，一条
「首次失败、重跑通过」的 run 必须以 `fail → pass` 的形式呈现，不得折叠成一次 success——
折叠会把 §3 的分子算丢，flake rate 从此系统性偏低。

## 5. `docs/30` 快照列「最近 3 次 CI 结论」

[30-GitHub现状与时限](30-GitHub现状与时限.md) 是快照真本，本文只定义格式，**实际回写归 `#277` 集成卡**：

- 对每个跟踪对象（如「db 用例 job」）在快照表新增一列「最近 3 次 CI 结论」；
- 取值为按时间**倒序**的最近 3 次 push 触发 run 中该对象自身 job 的结论，格式 `最新→次新→最旧`，
  每个值取 `pass` / `fail` / `cancel`，并在括号内附分类缩写（`i`=infra_transient，`r`=real_regression，`f`=flaky_test）；
- 一行示例：

  ```text
  | db 用例 job | fail(i)→pass→pass | 2026-11-07 |
  ```

  （对应 run `42009114733` 首次 fail、分类 `infra_transient`，该 job 在更早两个 run 为 pass。）
- 该列只记录事实与分类缩写，不写完成度评价——与 `docs/30` §0「快照只记录事实与定案结论」一致。

## 6. 环境故障登记判据：连续两轮同因，且不让 AI 修无关红叉

- **连续两轮同因失败才按环境故障登记**：单次失败只做 §4 留痕 + 取证评论；同一 job、同一根因
  在连续两个 push 触发的 run 里失败，才立为环境故障条目并触发处置（单次退避与备用源，实现归 `#264`）。
  只看一轮会把偶发抖动误立成故障；等三轮起再立，无关红叉已经拖了两轮总闸——两轮是平衡点。
- **不让 AI 改 db 用例修无关红叉**：环境故障分类一旦成立，禁止任何任务卡「顺手修」被牵连的用例代码
  来让 CI 变绿——用例与红叉无因果，改用例只会制造假修复、污染 659 用例计数。
- 出处与取证链（仓库 `#197` 评论区的取证记录，同见 [73](73-M11并发执行计划.md) §9）：
  纯文档提交 `750bf20` 的 CI run `42009114733` 中 db job 失败 →
  `GET /actions/runs/<id>/jobs` 定位失败 job → `GET /actions/jobs/<id>/logs` 拿 302 `Location` →
  **第二次请求不带 `Authorization` 头**（带到 Azure blob 会返 401）→
  grep `error|timeout|service .* is not running` → 根因为 `docker.m.daocloud.io` 的
  `TLS handshake timeout`（镜像拉不下来 → compose 网络 `devbox-db_default` 未创建 →
  77 个 db 用例 76 个报 `service "toolbox" is not running`）；
  同一 job 在 run `41938551949` 为 success。按 §2 该 run 分类 `infra_transient`，
  是本规范口径下第一条已留痕实例。

## 7. 卡失败三分类（spec 不清 / 环境抖动 / 真实缺陷）

任务卡跑不完不都是同一个原因。本节给**卡**（issue 任务）层面的失败三分类，
与 §2 的 CI run 三分类相互独立，供 `#275` 的度量与 19 张 M11 卡的结果解读统一复用：

| 分类 | 判定信号 | 处置动作 |
|---|---|---|
| `spec 不清` | 验收判据歧义、字段口径冲突、同一命令两人读出两种期望输出 | 停止规则 S3 / 补充第 ⑤ 条：记 `Q-*` 编号问人，不自行发挥（[71-任务卡规范v2](71-任务卡规范v2.md) §5） |
| `环境抖动` | 失败与卡内容无关、换时点或复跑即过、命中 §2.1 信号 | 贴证据留痕（§4 字段），按 §6 判连续两轮；不动卡产物 |
| `真实缺陷` | 卡产物（文档 / lab / 脚本）自身错误，稳定复现 | 修产物，或转 bug 卡；不许靠重跑、改无关文件掩盖 |

- **数据出处**：每张卡 PR 描述里的 execution trace 六字段（[71](71-任务卡规范v2.md) §6）中的
  `risk_notes`、失败输出与 `UNVERIFIED` 项，是本节三分类判定的证据来源；
- `#275` 按本节口径对 19 张 M11 卡与 M12 各卡的结果做统一解读，卡三分类分布随度量报告一并给出。
