# 开发发布维度增强

> 对应 [10-多维度学习模型](10-多维度学习模型.md) 的 **D6 运行时与生产就绪** / **D7 开发发布与供应链**。
> 本轮只写「该补什么、挂在哪」，不新增脚本、不改 CI、不发版。

## 1. 现状：有版本工具，但还没有发布工程

| 已有 | 位置 | 说明 |
|---|---|---|
| 版本真本 | `VERSION`（`0.1.0`）、`images/versions.env` | 项目版本 + 依赖版本分离 |
| 版本管理 | `shared/release/`（`@zeek/release`） | Conventional Commits → 算版本 → 写版本 → CHANGELOG → tag → 提交，含六条安全默认 |
| 发版档校验 | `scripts/check-version-truth.sh` | `VERSION` 与 tag 逐字一致 |
| 镜像发布 | `images.yml` | `sha-<commit>` 不可变 tag + 可变的 `:latest`，PR 只推 sha 不推 latest |
| 流水线 | `ci.yml` / `images.yml` | 全量 33 job |
| 已知限制登记 | [ROADMAP](ROADMAP.md) KI-08 | 「镜像标签可变」已显式记录（原 `KNOWN-ISSUES.md` 已并入 ROADMAP） |

**缺口**（本轮识别，均未实施）：

| 缺什么 | 为什么重要 | 公开方法论依据 |
|---|---|---|
| 独立 `release.yml` / 发布 runbook | 现在发版靠人工跑工具，没有可审计的流水线与 go/no-go 记录 | Release Engineering：release process / readiness gates |
| 制品不可变的完整证据链 | 有 sha tag，但缺 digest、provenance、SBOM、构建日志留存策略 | Build once, promote many；artifact immutability |
| 签名与供应链校验 | 镜像/包未签名，消费者无法验真 | SLSA / SBOM / sigstore provenance |
| 回滚演练 | 没有演练记录，「能回滚」只是假设 | Rehearse rollback（未演练的回滚会在压力下失败） |
| 生产就绪语义 | 毕业项目能构建，但没有健康检查、优雅退出、超时/重试、结构化日志 | Production Readiness Checklist |
| 渐进式发布 | deploy 与 release 没有解耦概念 | Decouple deploy from release / canary / feature flag |
| 度量 | 没有 DORA 口径，无法回答「发得快不快、稳不稳」 | DORA 四指标是系统结果，不是目标 |

> **能力边界（正式约束，`Q-D-05` 2026-11-04 定案）**：本工程是**学习仓库**，
> 不是线上服务。D6/D7 的目标是「让学习者见过并能复现这套流程」，
> **不搭生产级发布平台**，一切增强按「可在一个容器里演示」的尺度设计。
> 判定标准与「做 / 不做」对照表见 [10-多维度学习模型](10-多维度学习模型.md) §8。
> 本节此前是「建议」，现已升级为约束；`Q-R-01`~`Q-R-08` 任何一条都不得突破它。

## 2. 通用框架：发布工程 7 个能力域

每门语言的指南都应覆盖这 7 域中的适用项（不适用要写明理由，不能默默跳过）：

| # | 能力域 | 最小可演示产物 | 验收判据 |
|---|---|---|---|
| R1 | 版本语义 | SemVer 版本号 + tag + CHANGELOG | 能从 commit 推导出下一个版本号 |
| R2 | 可复现构建 | 固定依赖 + 固定基础镜像 + 一条构建命令 | 同 commit 两次构建产物一致 |
| R3 | 制品与不可变 | 带 digest 的制品 + 版本化 tag | 同一版本重跑不会覆盖已有制品 |
| R4 | 变更与兼容 | CHANGELOG 含 breaking change 段 |  breaking change 时版本号按 SemVer 递增 |
| R5 | 供应链 | 依赖清单 / SBOM / 校验和 | 能列出产物里所有直接依赖 |
| R6 | 部署与回滚 | 部署记录 + 回滚脚本 + 演练记录 | 回滚在演练环境真跑通过 |
| R7 | 运行时就绪 | 健康检查、优雅退出、结构化日志、超时 | 故意杀进程不会留下半写状态 |

**R1–R5 偏「开发发布」，R6–R7 偏「运行」**，两者缺一不可：
只做前五个叫「能发」，加后两个才叫「发完还能活」。

## 3. 分语言增强要点

> 版本一律来自 `images/versions.env` 的变量名（${GCC_MAJOR} / ${CLANG_MAJOR} / ${GO_VERSION} / ${PYTHON_VERSION} / ${JAVA_MAJOR} / ${RUST_TOOLCHAIN} / ${CMAKE_MIN_VERSION}）。下表只写变量名不写字面量，避免与真本冲突。
>
> **`Q-R-05` / `Q-R-06` 的成文口径**：9 轨道增强表按**集中一份**（本文件 §3）成文，各语言 G2 以链接引用、不复制；依赖清单按**统一一份**（见 §4 R5 行）成文。两项最终拍板见 M9-GATE（#224），未拍板前不建实现卡。

### 3.1 C / C++

| 域 | 现状 | 该补什么 |
|---|---|---|
| R2 | Makefile / CMake，容器内编译 | 记录编译选项、优化级别、`-D` 宏来源；区分 Debug/Release |
| R3 | ELF 二进制，静态/动态链接混用 | ABI 兼容说明；`ldd` 输出留档；动态库版本（soname）语义 |
| R5 | 无依赖清单 | 记录系统库依赖（对应 `runtime` 镜像的 `libstdc++6`/`libgcc-s1`） |
| R6 | 无 | 二进制替换即回滚；演示「旧二进制 + 新配置」的兼容性 |
| R7 | 无 | 信号处理（`SIGTERM` 优雅退出）、资源释放、core dump 与 ASan/UBSan 接入 |
| R1 | 版本真本 `VERSION` / `shared/release`（全仓级） | 构建期把版本注入产物（宏 / soname 联动）并在 CHANGELOG 登记 |
| R4 | CHANGELOG 由 `shared/release` 生成（全仓级） | 头文件变更按 ABI 影响分类（增字段 / 改签名 / 删符号），breaking 变更显式标记 |

**语言特有坑**：未定义行为在换编译器/优化级别后行为变化；ABI 与结构体布局；
头文件与库版本错配。`G3 问题指南` 应单列「链接期 / 运行期」两类。

### 3.2 Go

| 域 | 现状 | 该补什么 |
|---|---|---|
| R2 | `go.mod` / `go.sum` | `GOTOOLCHAIN=local`、`GOFLAGS`、module proxy 的可复现说明 |
| R3 | 单二进制 | `CGO_ENABLED=0` 静态产物与 runtime 镜像配合；交叉编译矩阵 |
| R4 | 无 | 语义导入版本（`/v2`）规则；`go.mod` 变更即兼容声明 |
| R5 | `go.sum` 已是校验和 | 演示 `go list -m all` 作为依赖清单 |
| R7 | 无 | `context` 超时传播、优雅关闭、`pprof` 与结构化日志（slog） |
| R1 | 版本真本 `VERSION` / `shared/release`（全仓级） | module 主版本（`/v2`）与 git tag `v*` 的对应约定写进发版流程 |
| R6 | 无 | 二进制替换回滚演示：从上一版本 tag 取旧产物跑通 |

**语言特有坑**：goroutine 泄漏、channel 死锁、隐式接口满足、逃逸分析导致的性能偏差。

### 3.3 Rust

| 域 | 现状 | 该补什么 |
|---|---|---|
| R2 | `Cargo.toml` / `Cargo.lock` | 锁文件必须入库；toolchain pin；离线构建 |
| R3 | `target/release/` 产物 | release profile（LTO / strip / panic=abort）对产物与诊断的影响 |
| R4 | 无 | crate 版本与 SemVer（0.x 的兼容语义不同）、feature flag 的兼容性责任 |
| R5 | 依赖树 | `cargo tree` / `cargo deny` 类清单与许可证检查 |
| R7 | 无 | `Result` 错误分类、`unwrap` 治理、panic hook、优雅退出 |
| R1 | 版本真本 `VERSION` / `shared/release`（全仓级） | `Cargo.toml` 版本与仓库 `VERSION` 的同步策略（单一来源） |
| R6 | 无 | `target/release` 产物替换回滚演示 |

**语言特有坑**：所有权/借用编译错误阅读、生命周期标注、异步运行时选择、
feature unification 导致构建结果随依赖变化。

### 3.4 Shell

| 域 | 现状 | 该补什么 |
|---|---|---|
| R2 | 脚本即源码，`bats` / `shellcheck` / `shfmt` | shebang 与 POSIX/bash 方言边界；外部命令版本假设 |
| R3 | 无制品概念 | 「发布」= 分发脚本 + 校验和；明确这一点而不是硬套包管理 |
| R5 | 无 | 列出脚本依赖的外部命令清单与最低版本 |
| R6 | 无 | **幂等性**是 Shell 的回滚：重复执行不产生副作用 |
| R7 | 无 | `set -euo pipefail` 的真实语义、trap 清理、信号与子进程 |
| R1 | 版本真本 `VERSION`（全仓级） | 脚本分发时的版本标注（`--version` 输出或版本变量） |
| R4 | CHANGELOG 由 `shared/release` 生成（全仓级） | 脚本对外接口（参数、输出格式）变更在 CHANGELOG 显式登记 |

**语言特有坑**：quoting / word splitting、`set -e` 在管道与函数里的失效、
环境变量未设置、`mktemp` 清理。这类问题最适合 G3 按「现象 → 三条检查 → 定位命令」写。

## 4. 与现有工程的可挂载点

将来实施时，增强项应挂在既有位置，避免另起一套：

| 增强项 | 挂在哪 | 备注 |
|---|---|---|
| R1 版本 | `VERSION` / `shared/release/` | 已有工具；`Q-R-01` 已裁定**不立项** `release.yml`，只保留流程文档（见 §6） |
| R2 可复现 | `images/versions.env` / 各 `Dockerfile` | 遵守 `check-version-truth.sh` |
| R3 制品 | `images.yml` 的 `sha-<commit>` tag | 已有不可变 tag，补 digest 记录与留存策略 |
| R4 变更 | `shared/release` 生成的 CHANGELOG | 补 breaking change 段规范 |
| R5 供应链 | 各语言依赖锁文件 | 统一成一个「依赖清单」文档 |
| R6 回滚 | `docs/` 新增 rollback runbook | 需演练记录，不是写份文档就算 |
| R7 运行时 | 各 `<lang>/project/` | 健康检查 / 优雅退出 / 结构化日志 |

## 5. 本轮不做什么

- 不新建 `release.yml`、不改 `ci.yml` / `images.yml`
- 不给毕业项目加健康检查或日志代码
- 不引入 SBOM / 签名工具、不发新版本
- 全部条目以 `Q-R*` 编号落在 [40-问题清单](40-问题清单.md)，按 [41-里程碑拆分](41-里程碑拆分.md) 排期
