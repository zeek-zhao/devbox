# 86 度量口径（仓库资产侧六指标）

> 对应任务卡 `M12-M-01`（#343）。本文定义**仓库资产侧**的六个度量口径（D-1 到 D-6）：
> 用例总数、E 类覆盖、exempt 完整率、E 类通过率、CI 时长分位数、flake rate 采集。
> 与既有规范分工严格：**flake rate 的公式真本是 [78-CI失败分类规范](78-CI失败分类规范.md)（#272）§3**，
> 本文只给采集命令，不重复定义；**verifier trace schema 与执行质量四指标（M-1..M-4）真本是
> [80-M12度量规范](80-M12度量规范.md)（#275）**，本文不涉足。两条共同的度量纪律同样生效：
> 数字只许来自可复跑的证据（[80](80-M12度量规范.md) §1），拿不到写 `UNVERIFIED` 不许填 0（[80](80-M12度量规范.md) §6）。

## 2. 什么算一次样本

所有六指标共用同一样本定义，避免「各指标各数各的」：

- **CI 侧样本** = 一次 `push` 触发的 GitHub Actions run 中**单个 job 的最终结论**。
  run 级结论是 job 结论的聚合，不单独算样本；`skipped` 的 job 不算样本。
- **本地侧样本** = 一次 `TAG=latest scripts/run-example.sh <track> <ID>` 调用的最终结论
  （PASS / FAIL）。
- **rerun 语义**：遵 [78](78-CI失败分类规范.md) §3——rerun 通过 ≠ flaky 也 ≠ 稳定；样本一律取
  **首次结论**，rerun 结论只作三分类证据（`infra_transient` / `real_regression` / `flaky_test`），
  不进入通过率分母的翻转。
- **观察窗口**：报告必须声明窗口（如「最近 N 次 push run」或起止日期），窗口外样本不计入。

## 3. 六个指标（公式 / 数据源 / 采集命令 / 判读阈值）

### D-1 用例总数

- **公式**：`Σ 各轨 examples 下 run.sh 数`（`db` 轨同口径，`shared` 顶层不在 9 轨口径内）。
- **数据源**：仓库工作树；**口径真本** [ROADMAP](ROADMAP.md)（794 = 存量 659 + E 类 135）。
- **采集命令**：
  ```bash
  find c cpp go java python rust shell vue db -path "*/examples/*" -name run.sh | wc -l
  ```
- **判读阈值**：与 ROADMAP 口径一致即绿；偏离即红（回写口径归 M11-INT 串行，本文只报差值）。

### D-2 每轨 E 类覆盖数

- **公式**：`| ls <track>/examples/E-* |`，逐轨统计。
- **数据源**：仓库工作树。
- **采集命令**：
  ```bash
  for t in c cpp go java python rust shell vue db; do
    printf "%s %s\n" "$t" "$(ls -d "$t"/examples/E-* 2>/dev/null | wc -l)"
  done
  ```
- **判读阈值**：每轨 ≥ 15；低于 15 即红。

### D-3 exempt 理由完整率

- **公式**：`有非空豁免理由的 E 例数 / E 例总数`。豁免声明契约：每例 `README.md` 内
  `coverage: exempt <理由>`（[coverage-check.sh](../scripts/coverage-check.sh) 词表：
  covered / pending / exempt，exempt 理由必填）。
- **数据源**：各 E 例 `README.md`。
- **采集命令**：
  ```bash
  grep -rl 'coverage: exempt' */examples/E-*/README.md | wc -l   # 分子
  ls -d */examples/E-* | wc -l                                   # 分母
  ```
- **判读阈值**：100%（M11 拍板 Q6：每例必写）；<100% 即红，逐例补理由。

### D-4 E 类示例通过率

- **公式**：`结论为 PASS 的 E 类样本数 / 执行的 E 类样本数`（样本定义见 §2）。
- **数据源**：CI run 的 `用例-<track>` job 结论（E 例随全轨矩阵执行），或本地逐例回放。
- **采集命令**（CI 侧，取某 run 的 9 个用例 job 结论）：
  ```bash
  curl -s "https://api.github.com/repos/zeek-zhao/devbox/actions/runs/<run_id>/jobs?per_page=40" \
    | python3 -c "import json,sys; d=json.load(sys.stdin); \
      [print(j['name'], j['conclusion']) for j in d['jobs'] if j['name'].startswith('用例-')]"
  ```
  本地单例回放：`TAG=latest scripts/run-example.sh <track> <ID>`。
- **判读阈值**：100%（E 类是错误处理回归基准，任何 FAIL 都要先过 [78](78-CI失败分类规范.md)
  三分类：`infra_transient` 不计入通过率分母翻转，`real_regression` 即红）。

### D-5 CI 时长 p75 / p90

- **公式**：窗口内 `push` 触发、`completed` 的 run 的执行时长
  （`run_started_at` 到 `updated_at`，不含排队）的第 75 / 90 百分位；`cancelled` 不计入。
- **数据源**：GitHub Actions runs API（`GET /repos/zeek-zhao/devbox/actions/runs`）。
- **采集命令**：
  ```bash
  curl -s "https://api.github.com/repos/zeek-zhao/devbox/actions/runs?per_page=40" | python3 -c "
  import json,sys; from datetime import datetime
  rs=[r for r in json.load(sys.stdin)['workflow_runs'] if r['event']=='push' and r['status']=='completed']
  d=sorted((datetime.fromisoformat((r.get('run_started_at') or r['created_at']).replace('Z','+00:00'))
            ,datetime.fromisoformat(r['updated_at'].replace('Z','+00:00'))) and
           (datetime.fromisoformat(r['updated_at'].replace('Z','+00:00'))
           -datetime.fromisoformat((r.get('run_started_at') or r['created_at']).replace('Z','+00:00'))).total_seconds()/60 for r in rs)
  n=len(d); print(n, 'median', d[n//2], 'p75', d[int(.75*(n-1))], 'p90', d[int(.90*(n-1))])"
  ```
- **判读阈值**：无硬上限；判读规则——p75 超过基线的 2 倍视为劣化信号，先按
  [78](78-CI失败分类规范.md) 取证再谈优化（优化动作归 `#264` 人工批次）。

### D-6 flake rate（采集侧）

- **公式**：**不在此定义**——唯一真本 [78](78-CI失败分类规范.md) §3：
  `首次结论为 infra_transient 的运行数 / 观察窗口内 push 触发的 CI 运行数`，报告须附三分类分布。
- **数据源**：窗口内 push run 列表 + 逐失败 run 的取证结论（两跳日志下载按
  [87-CI失败取证规范](87-CI失败取证规范.md)，自动分类可用
  `scripts/classify-ci-failure.sh --log <日志>`）。
- **采集命令**（run 清单侧）：
  ```bash
  curl -s "https://api.github.com/repos/zeek-zhao/devbox/actions/runs?per_page=40" \
    | python3 -c "import json,sys; d=json.load(sys.stdin); \
      [print(r['run_number'], r['head_sha'][:7], r['conclusion']) \
       for r in d['workflow_runs'] if r['event']=='push']"
  ```
  失败 run 逐个取证后按 [78](78-CI失败分类规范.md) 公式计算。
- **判读阈值**：遵 [78](78-CI失败分类规范.md)；窗口 < 5 次时只报绝对数并标 `small-sample`，
  不报比率（小窗口比率波动无意义）。

## 5. UNVERIFIED 纪律

- 每次报告逐指标带「数据出处 + 窗口」；取不到的写 `UNVERIFIED` 并在 trace 的 `unverified[]`
  登记原因（[80](80-M12度量规范.md) §6 同款纪律）；
- 本文六指标的数据源全部落在仓库工作树或公开 API 上，**不存在天然取不到的指标**；
  若某次采集时 API 不可用，该指标当次写 `UNVERIFIED`，下窗口补采；
- 连续两个窗口 `UNVERIFIED` 必须附补数计划（[80](80-M12度量规范.md) §6）。

## 6. 明确不做

- 不搭监控平台、不写告警规则（卡面约定）；
- 不采 DORA 四指标（§1，Q-R-08）；
- 不重定义 flake rate 公式（归 [78](78-CI失败分类规范.md)）、不定义 trace schema（归
  [80](80-M12度量规范.md)）；
- 不改门禁文件、不加 CI 步骤；度量全部是离线采集命令，报告落点为卡评论 / 收口报告
  （`#277` GATE 卡消费）。
