# 多维度语言学习模型

> 目的：把「学一门语言」从**语法 + 工程**两维，扩展到**真实工作岗位上真正被考核的维度**。
> 本文定义维度与分级，不新增用例；落点见 [11-知识点清单增强规范](11-知识点清单增强规范.md)。

## 0. 正式口径声明（`Q-D-01` 定案，2026-11-04）

**D1–D8 是本仓库的正式能力口径，不是参考资料。** 具体含义：

1. 每门语言的指南、任务卡、验收判据都要标注覆盖哪几个维度与目标刻度（P0–P4），
   见 [11](11-知识点清单增强规范.md) §2.1 的 `dimensions` / `level` 字段；
2. 排期按**维度**而不是按语言排，避免 9 门语言重复造同一套指南
   （[41](41-里程碑拆分.md) 的 M8/M9 就是这么切的）；
3. 「学完一门语言」的判定以 §3 的刻度为准，不接受「已补充文档」「看过一遍」这类
   没有判据的说法；
4. 现有 659 个用例主要覆盖 D1–D4，D5–D8 的缺口由指南层与 [20](20-开发发布增强.md)
   承接——**这是口径，不是完成度声明**，不许把「有维度」写成「有能力」。

边界由 §8（`Q-D-05`）锁定：**只追求可在一个容器里演示，不搭生产级平台**。
`Q-D-01` 与 `Q-D-05` 成对生效，缺一条都会让 M9 的范围失控。

## 1. 为什么两维不够

现有工程的用例体系是 L1 语言特性 / L2 工程能力 / L3 专题 / L4 设计模式，

> **数量判据（2026-11-13 `#396` 起）**：每条学习轨的知识点合计应在 **70–80**；低于 70 视为覆盖缺口，需补例或由维护者定案。当前：db 77 / c 77 / cpp 76 / go 76 / java 73 / python 73 / rust 73 / vue 73 / shell 70（补齐前 53）。
这套分层把「写出来」和「写对」覆盖了，但真实工作里让新人卡住的往往不是这两件事：

| 真实场景 | 现有体系能答吗 | 缺的是 |
|---|---|---|
| 服务在本地跑得好，上线后半夜挂了没人知道 | ❌ | 可观测性、告警、SLO |
| 依赖升级后行为变了，回滚又回不去 | ❌ | 版本策略、制品不可变、回滚演练 |
| 一个 bug 复现不了，只能靠猜 | ❌ | 系统化调试方法与工具链 |
| 代码能跑，但别人 review 时说「这不是 Go 的写法」 | 部分 | 惯用法（idiom）与反模式 |
| 同样的功能，为什么选这个库不选那个 | ❌ | 生态判断、社区与历史（arcana） |
| 要发版了，不知道该谁签字、出问题找谁 | ❌ | 发布流程、runbook、值班 |

结论：**「会用语法」只是入场券，「能交付、能运维、能被接手」才是工作能力。**

## 2. 八个维度（D1–D8）

参考公开的资深工程师能力模型（Syntax / Libraries / Tools / Configuration / Patterns /
Community / Arcana 七维）、生产就绪清单（可靠性 / 可观测性 / 安全 / 性能 / 运维）
与发布工程方法论，结合本工程实际，收敛为 8 维：

| 编号 | 维度 | 一句话定义 | 典型证据（能拿出来的东西） |
|---|---|---|---|
| **D1** | 语法与语义 | 能表达逻辑，且知道语义边界（未定义行为、所有权、GC） | 用例、编译器警告零告警 |
| **D2** | 生态与惯用法 | 知道标准库/主流库**有什么**，并写出该语言社区认可的写法 | 代码评审记录、重构前后对比 |
| **D3** | 工具链与配置 | 构建、格式化、lint、依赖、调试器、环境变量怎么配 | 一条命令从零到可跑；`fmt --check` 通过 |
| **D4** | 质量与测试 | 单元/集成/契约测试、边界与失败注入、覆盖率的可信度 | 测试金字塔、故意删断言能变红 |
| **D5** | 诊断与问题定位 | **出问题时**的方法论：假设—验证—定位，日志/指标/追踪 | 一份真实 bug 的排查记录 |
| **D6** | 运行时与生产就绪 | 健康检查、优雅退出、超时/重试/熔断、资源与性能基线、安全 | 生产就绪检查表逐项有结论 |
| **D7** | 开发发布与供应链 | 版本、变更日志、制品不可变、SBOM/签名、灰度/回滚、DORA | 可复现的发版记录 + 回滚演练记录 |
| **D8** | 协作与职业实践 | 代码评审、文档、技术决策记录（ADR）、知识传递、成本意识 | ADR、runbook、可交接的文档 |

### 维度之间的关系

```
D1 语法 ── D2 惯用法 ── D3 工具链        「写得出来」
      └──── D4 质量 ────┘                「写得对」
D5 诊断 ←── 上面全部                      「坏了能修」
D6 运行时 ── D7 发布 ── D8 协作           「能上线、能被接手」
```

**D5 是分水岭**：前四维都是「顺境能力」，D5 开始是「逆境能力」。
现有 659 个用例几乎全在顺境——每条 `run.sh` 都有确定输入与 `expected.txt`，
这恰恰是真实工作里最不常见的情形。

## 3. 五级能力刻度（可验收）

每个维度按 5 级判定，避免「学过」这种无法验证的说法：

| 级别 | 名称 | 判定标准 | 对应产物 |
|---|---|---|---|
| **P0** | 知道 | 能说清概念与适用边界 | 指南里的「什么时候用」 |
| **P1** | 会跑 | 在 devbox 镜像里跑通给定用例 | 用例 PASS |
| **P2** | 会用 | 换一个输入/场景仍能写对，能解释选择 | 变体练习、评审记录 |
| **P3** | 能交付 | 输出可发布、可回滚、有文档的制品 | 发版记录、runbook |
| **P4** | 能负责 | 出故障能定位并复盘，能教别人、能定规范 | 复盘、ADR、规范文档 |

> 现有工程整体处于 **P1–P2**（用例全绿、格式化达标），
> D6/D7/D8 基本在 **P0 甚至空白**。本轮文档的目标是把 P0→P2 的路径写清楚，
> **不假装已经做到 P3/P4**。

## 4. 与现有 L1–L4 的映射

| 现有层 | 主要覆盖 | 本轮要补的维度 |
|---|---|---|
| L1 语言特性 | D1、少量 D2 | D2 惯用法、D3 工具链速查 |
| L2 工程能力 | D3、D4 | D5 诊断方法论、D6 运行时 |
| L3 专题 | D1/D2 深入 | D5、D6 的场景化疑难解答 |
| L4 设计模式 | D2 | D8 技术决策（什么时候**不该**用模式） |
| 毕业项目 | D3、D4 | **D6 / D7 / D8 全缺**：项目能构建，但没有发布与运维语义 |

**关键落差**：毕业项目现在是「能编译能跑的练习」，
还没有「能被部署、被监控、被回滚」的属性。这正是 [20-开发发布增强](20-开发发布增强.md) 要补的。

## 5. 「站在实际工作角度」具体指什么

把抽象维度翻译成岗位里天天发生的事：

1. **接手别人的代码**：先读什么、怎么在本地复现、怎么确认改动没踩坑 → D3/D8
2. **改一个不熟悉模块**：如何靠测试与类型系统给自己兜底 → D4
3. **线上报警**：从告警到根因的最短路径，日志/指标/追踪各看什么 → D5/D6
4. **发版**：版本号怎么定、谁批准、制品从哪来、怎么回滚 → D7
5. **技术选型**：写 ADR，把「为什么不用另一个方案」留下来 → D8
6. **带人 / 交接**：runbook、FAQ、常见问题清单，让下一个人不必重踩 → D8

这六件事**没有一件是语法题**，但构成了绝大部分工作时间。

## 7. 本模型的用法

- 写指南时：每篇指南在开头标注覆盖哪几个维度、目标是 P几（见 [11](11-知识点清单增强规范.md)）
- 排期时：按维度而不是按语言排，避免 9 门语言各自重复造同一套指南
- 验收时：用 §3 的刻度判定，不接受「已补充文档」这种没有判据的说法
- 写卡时：`dimension` / `level` 是 [60-AI工作指南](60-AI工作指南.md) §4 的必填字段

## 8. 能力边界（`Q-D-05` 定案，2026-11-04）

**本仓库是学习仓库，只追求「可在一个容器里演示」，不搭生产级平台。**

| | 做 | 不做 |
|---|---|---|
| D6 运行时 | 讲清健康检查 / 优雅退出 / 超时重试的**概念**，用一个容器内可复现的最小演示 | 真实流量、SLO / error budget、告警值班体系 |
| D7 发布 | 版本号、不可变 tag、CHANGELOG、依赖清单、一次可复现的发版记录 | 生产级发布平台、灰度基础设施、完整 SLSA 供应链 |
| D5 诊断 | 一份真实 bug 的排查记录、可复现现象 + 三条检查 + 定位命令 | 全链路追踪平台、日志中心 |

**为什么必须写死这条**：D6/D7 的公开资料（生产就绪清单、发布工程、SLO、
混沌工程）可以无限展开，不设边界就会把「学语言」变成「搭一套 SRE 平台」，
与初衷偏离。[20](20-开发发布增强.md) §1 的「诚实边界」此前是**建议**，
现在升级为**正式约束**；[40](40-问题清单.md) §3.1 的公开资料候选项
（如 SLO / error budget 建议不纳入、成本治理建议不纳入）按这条边界裁决。

**判定一句话**：一项增强如果不能在**一个 devbox 容器里**让学习者亲手跑出结果，
就不属于本仓库范围——记为「知道」级 P0 概念，或明确不纳入，不许挂着当待办。
