## 3. 「限时完成」的实际情况与定案（重点）

### 3.1 结论：远端无显式时限，本地定案「一星期」

**远端事实**（`Q-S-01` 的出发点）：

- **快照时刻**唯一里程碑 `v0.2.0` 的 `due_on` = `null`（现已设，见下）
- 全部 issue 均无到期日（GitHub issue 本身也无 `due_date` 值）
- 因此快照时刻**不存在「逾期」概念**，也无法回答「这张卡该什么时候完成」

**2026-11-04 定案（Q-S-01 / Q-S-02）**：

| 对象 | 口径 |
|---|---|
| `v0.2.0` | 建议 `due_on` = **2026-11-11**（快照日 + 7 天） |
| M6–M10 | 每个里程碑 **7 天窗口** |
| `needs-human` / `decision` 卡 | 同样 7 天，**到期只标记提醒，不自动关** |
| 到期处理 | 不延期、不静默关闭；写一条说明（卡在哪、谁来做、下一个检查点） |

语义是**检查节拍，不是考核指标**：学习仓库设硬截止容易失真（没人催、也不代表真逾期），
所以每 7 天看一次「卡住的是不是自动化的边界」。硬关口不因时限到而放行。

> **已落地**：2026-11-04 批量建单时把 `due_on` 一并设好（见 §2）。
> GitHub issue 没有 `due_date` 字段，因此「每张卡的时间」写进卡正文的**检查点**，
> 与所属里程碑的窗口一致；`needs-human` / `decision` 卡同样 7 天，到期只标记提醒。
