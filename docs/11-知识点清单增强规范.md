# 知识点清单增强规范（指南层）

> 现有 `<lang>/docs/知识点清单.md` 是**用例 ID 清单**，只回答「练什么」。
> 本文定义要补的**指南层**：五类文档，回答「怎么用 / 怎么开发 / 出问题怎么办 / 用什么工具 / 疑问去哪查」。
> 参考 `D:\zeek\work\repo\sample\` 各语言 sample 的指南体系，但不复制其内容。
>
> **2026-11-04 `Q-G-03` 定案**：五类模板**定稿**，并采纳 §7 的 9 条优化。
> 本文件自此是模板真本；后续写指南按本文执行，不再逐篇讨论结构。
>
> **2026-11-06 第九轮翻转**：§3 挂接方式翻转为 **A+C 方案**（清单只放索引与反查表，
> 详细正文外链独立文档）；依据见 Obsidian 需求笔记《知识点清单增强》§5 / §8，
> 落地文本见 §3。

## 1. 五类指南（缺一不可）

| 类 | 文件名 | 一句话职责 | 对应维度 | sample 里的范本 |
|---|---|---|---|---|
| **G1 实践指南** | `实践指南.md` | 把知识点放进**真实任务**里：什么时候用、不用会怎样、怎么验 | D2 D8 | `XX最佳实践.md`、`XX完全指南.md` |
| **G2 开发指南** | `开发指南.md` | 从零到能改：环境、目录、构建、调试、提交、评审的**完整动线** | D3 D4 D8 | `XX开发指南.md` |
| **G3 问题指南** | `问题指南.md` | 按**问题域**（不是语法域）组织疑难：现象 → 假设 → 定位 → 修复 → 预防 | D5 | `XX问题指南.md` |
| **G4 工具指南** | `工具指南.md` | 工具清单、安装/调用、参数速查、选型对比、常见误用 | D3 D5 | `XX调试技术与工具.md`、`tools.md` |
| **G5 疑难解答** | `FAQ.md` | 高频短问答 + 「查不到时去哪查」，带可检索的关键词 | D2 D5 D8 | `FAQ.md`、`MAINTENANCE_GUIDE.md`、`USER_GUIDE.md` |

### 为什么是这五类而不是「一份大百科」

sample 里 C++/Go/Java 各有「完全指南 / 开发指南 / 最佳实践 / 问题指南 / 调试工具」多份，
是因为它们按**读者意图**切分了：想学、想做、卡住了、要查命令、有个小疑问——
这五种意图不会同时发生。合成一份大文档的结果是查找成本极高，最后没人看。

**G3 与 G5 的区别**（最容易混）：

| | G3 问题指南 | G5 FAQ |
|---|---|---|
| 组织方式 | 按问题域（内存 / 并发 / 构建 / 部署） | 按提问频率，一问一答 |
| 长度 | 一个域 500–1500 字，含排查路径 | 一条 50–200 字 |
| 读者状态 | 正在排查一个具体故障 | 有个小疑问，想 10 秒内得到答案 |
| 必须有 | 可复现现象 + 定位命令 + 根因 | 答案 + 指向 G3/G4 的链接 |

## 2. 统一模板（定稿版）

### 2.1 frontmatter 七字段（全必填）

```markdown
---
track: cpp                    # 轨道名，与目录名一致
guide: G2                     # G1..G5
dimensions: [D3, D4, D8]      # 见 10-多维度学习模型（正式口径）
level: P2                     # 目标达到 P0..P4
status: draft                 # draft | reviewed | verified，判据见 §7.4
links: [知识点清单.md, FAQ.md] # 同目录文档指针，相对路径
examples: [L2-003, L3-011]    # 本篇引用的真实用例 ID，至少 1 个
---
```

> `examples` 是 `Q-G-03` 优化 O1 新增的**第七字段**：
> 原 §5 的验收写「每篇至少引用 1 个真实用例 ID」，却只靠正文 grep，
> 既脆弱又无法区分「正文提到」与「真正在讲」。改成显式字段后可机器校验。
> `links` 与 `examples` 分工：**前者指向文档，后者指向用例**。

### 2.2 各类的固定章节（三档）

章节分 **必填 / 条件必填 / 选填** 三档：27 篇最小集阶段只要求「必填」齐，
避免 G1/G3 因缺真实素材而硬套出空壳（优化 O2）。

**G1 实践指南**
```
[必填] 1. 适用边界（什么时候用 / 什么时候别用）
[必填] 2. 最小可运行示例（指向具体用例 ID，不重复贴代码）
[必填] 3. 惯用法与反模式对照表（含 ≥1 个可复现反例，见 O5）
[条件] 4. 真实工作中的变体（≥2 个；无真实素材时写「待补」并说明原因，不许编）
[条件] 5. 评审清单（review 时该问的 3–5 个问题）
```

**G2 开发指南**
```
[必填] 1. 环境与启动（镜像 tag / 版本号来源 = images/versions.env）
[必填] 2. 目录结构与各文件职责
[必填] 3. 一条命令跑通（格式见 §4「命令契约」，含失败时先看哪里）
[必填] 4. 改动循环：改 → 格式化 → lint → 测试 → 提交
[选填] 5. 调试入口（指向 G4）
[必填] 6. T0 通用内容的链接（见 §3，不复制通用部分）
```

**G3 问题指南**（每个问题域一节，节内结构统一）
```
## <问题域>
[必填] ### 典型现象            # 必须可观察，不写「程序出错」
[必填] ### 先做的三个检查        # 成本从低到高
[必填] ### 定位命令 / 工具       # 指向 G4 对应条目
[必填] ### 根因分类表           # 现象 → 可能根因 → 验证方法
[必填] ### 修复与预防           # 预防要落成测试或 lint 规则
[必填] ### 相关用例 ID          # 与 frontmatter 的 examples 一致
```

**G4 工具指南**
```
[必填] 1. 工具全景表（工具 / 用途 / 本工程是否预装 / 版本来源）
[必填] 2. 每工具一节：装在哪、怎么调、常用参数速查
[条件] 3. 选型对比（同类工具为什么选这个；只有一种工具时写「不适用：无同类」）
[必填] 4. 常见误用（≥2 条）
```

**G5 FAQ**
```
[必填] 按主题分组，每条：
### Q: <原话式提问，带关键词>
A: <先给结论，再给一步命令，最后给「详见 G3 §x / G4 §y」>
[必填] 查不到时去哪查（指向 [ROADMAP](ROADMAP.md) KI 段 / 上游文档 / issue 搜索）
```

## 3. 与知识点清单的挂接方式（A+C 方案）

> **2026-11-06 第九轮翻转**：本节由「双向指针挂接」翻转为 **A+C 方案**——
> 清单只放**索引与反查表**，详细正文外链独立文档。决策过程与需求原文见
> Obsidian 需求笔记《知识点清单增强》§5（方案对比）/ §8（第九轮翻转记录）；
> 本仓库内的落地约定即本节现行文本，取代 2026-11-04 定稿时的双向指针方案。

清单文件（`<lang>/docs/知识点清单.md`）只承担两件事：

- **索引（方案 A）**：每行 = 用例 ID + 一句话考点 + 可观察判据，定位「练什么」，
  不展开正文；
- **反查表（方案 C）**：以用例 ID 为键，反查讲解正文所在的独立指南文档与关联 lab
  （反查字段契约见 [INDEX-by-example](INDEX-by-example.md)，文档定位见
  [84-文档地图](84-文档地图.md)）。

详细正文一律写进**独立指南文档**（五类指南见 §1），清单行只留指针：

- 指南里引用用例：写 `见 L2-003`，并登记进 frontmatter 的 `examples`，不复制代码；
- 清单行指向正文：行的「指南节 / 排查命令 / 判据」列写明去哪篇指南哪一节，
  正文改动只落在指南文件，清单不随之膨胀；
- **否决方案 B（清单内联详细正文）**：会把清单胀成又一份语法书，违反 §4 契约 1；
  已交付的 E 段（M11-DOC 批次）就是 A+C 的实例——行内放排查命令、判据、
  指南节、lab 指针，正文在指南与 lab 文件里。
- **T0 单一真本**（`Q-G-01` 定案）：跨语言通用内容（runner 用法、格式化/lint、
  CI 红灯定位、提交身份、门禁、PR 约定、发版回滚通用流程）集中在
  `docs/13-通用开发指南.md` 一份；各语言 G2 **只写本轨道差异并链接过去**，不复制。
- **单一真本**：版本号只来自 `images/versions.env`，命令只来自实际脚本，
  指南里禁止出现手写的版本常量，否则 `scripts/check-version-truth.sh` 会红。

## 4. 写法契约（防止写成又一份语法书）

1. **禁止长篇语法讲解**：语法归 L1 用例，指南只讲「何时 / 为何 / 出错怎么办」。
2. **每条结论必须可验证**：给得出命令、文件路径或用例 ID，不写「通常」「一般来说」。
3. **命令契约**（优化 O3）：G2/G4 里的用例命令统一写成
   `TAG=latest scripts/run-example.sh <track> <ID>`：
   - runner 读 `TAG`，CI 传 `IMAGE_TAG`，两者是**同一个值的两个名字**（真实踩过的坑：
     名字不一致导致 6 个用例 job 全红，而本地各跑各的都不报错）；
   - **禁止**在指南里写 `devbox-cpp:local` 这类硬编码 tag；本地调试要说明
     「宿主已有本地镜像时把 `TAG` 换成 `local`」；
   - 命令以本工程为准（`scripts/run-example.sh`、`make fmt`、`<lang>/project/build.sh`），
     不引外部教程里的通用命令。
4. **版本引用契约**（优化 O4）：需要写版本时写 `images/versions.env` 里的变量名
   （如 `${GO_VERSION}`）并注明真本，**不写字面量**；这样改版本不会让指南集体过期。
5. **反例是必须项且可执行**（优化 O5）：G1/G3 每节至少一个「错误做法 + 可复现命令 + 后果」，
   不接受只有文字描述的「反例」。
6. **不适用要声明**（优化 O6）：某章节对本轨道不适用，写 `不适用：<具体理由>`，
   不许留空、不许悄悄删章节。这与 M8「不许把没写记成不适用」是同一枚硬币的两面。
7. **公开仓纪律**：不写内网地址、内部主机名、内部账号；凭证一律用占位符，
   与 `SECURITY.md` / [ROADMAP](ROADMAP.md) 的既有声明一致。
8. **状态诚实**：`status: draft` 的指南不许在 README 里被写成「已完成」；
   状态流转判据见 §7.4。

## 7. `Q-G-03` 模板优化项（9 条，已并入上文）

> 用户要求「看看有优化的地方不」。逐条核对 sample 指南体系、公开工程方法论与
> 本工程实际脚本后，得到以下 9 条。**全部已并入 §2–§5**，此处集中留痕便于评审。

| # | 优化 | 解决什么 | 落点 |
|---|---|---|---|
| **O1** | frontmatter 加 `examples` 第七字段 | 「每篇至少引用 1 个真实用例 ID」原本只靠正文 grep，无法机器校验 | §2.1 |
| **O2** | 章节分「必填 / 条件必填 / 选填」 | 27 篇最小集阶段 G1/G3 缺真实素材，硬套全模板会产出空壳 | §2.2 |

| **O4** | 版本引用写变量名、不写字面量 | 指南里写死版本，升级时集体过期，且与 `check-version-truth.sh` 冲突 | §4.4 |
| **O5** | 反例必须可执行（含复现命令） | 「反例」容易退化成一句文字描述，教学价值落空 | §4.5 |

### 7.1 状态机（O7，顺带定案 `Q-G-09`）

| 状态 | 谁改 | 判据 |
|---|---|---|
| `draft` | 起草者 | 文件存在、七字段齐、必填章节齐 |
| `reviewed` | **人工**抽读 | 至少一人读过并确认「有教学价值、无事实错误、命令与工程一致」 |
| `verified` | 起草者 + 人工确认 | 命令在对应镜像真跑过 + 通过 §7.3 的反向测试 |

> `status` 只能单向推进；回退要在 PR 里写明原因。`verified` 不许自评自改。

### 7.2 G3 真实排查素材池（O8，顺带给出 `Q-G-10` 默认）

素材**只允许**来自以下三类，禁止编造「典型现象」：

1. **本仓库已登记的已知问题**：[ROADMAP](ROADMAP.md) 的 `KI-06/07/08/09`、
   已解决的 `KI-03/04/05`、以及 `#184`（`:latest` 并发污染）等历史 bug；
2. **可复现实验**：在对应镜像里人为构造（如故意删一个环境变量、故意用错 tag），
   记录复现命令与真实报错；
3. **本轮发现的口径不一致**：如 `Q-S-08`（Dockerfile 注释与实际安装包不符）、
   `Q-S-07`（门禁注释里的旧数字）——这类「文档与代码漂移」本身就是极好的 D5 教学素材。

> 每篇 G3 至少 1 个素材来自本池，并在节内标注来源编号；M8-02 负责把池子整理成清单。

### 7.3 评审清单与反向测试（O9）

提交一篇指南，评审逐条打勾（**任一条否即打回**）：

- [ ] frontmatter 七字段齐，`examples` 的 ID 真实存在
- [ ] 必填章节齐；条件/选填章节要么写了、要么写了「不适用 + 理由」
- [ ] 没有硬编码版本号 / 镜像 tag / 内网地址 / 凭证
- [ ] 命令符合 §4.3 的命令契约，且在当前镜像真跑过
- [ ] G1/G3 有可执行反例；G3 有「现象 + 三检查 + 定位命令 + 根因表」
- [ ] T0 通用内容是链接，不是复制
- [ ] 状态与事实相符（`draft` 没被写成已完成）
- [ ] 公开仓可读：没有维护者私有路径、账号、主机信息

**反向测试协议**（M6-06）：故意破坏一篇的 frontmatter（删 `examples`）、
一篇 G3 的「定位命令」、一篇 G2 的命令契约（改成硬编码 tag），
评审清单或后续 `check-guides.sh` 必须能发现。**发现不了就是验收机制失效**，
不是「这次没破坏到位」。

### 7.4 与 `Q-G-01` / `Q-G-02` 的衔接

- T0 通用骨架 → `docs/13-通用开发指南.md` 单文件（O2 的「条件必填」多半靠它承接）
- 27 篇最小集 = 9 轨道 × G2/G4/G5；M6 的 C++ 全量 5 篇含 G1/G3，
  所以 M6+M7 合计 **29 篇文件**（其中 27 篇属最小集、2 篇是 C++ 的 G1/G3），
  G1/G3 其余 16 篇留 M8。这个口径写进 [12](12-语言指南覆盖矩阵.md) §5，别再算成 24 或 45。
