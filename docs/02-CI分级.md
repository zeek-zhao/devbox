# CI 分级：PR 不跑，main 跑快的，tag 跑全的

> 一句话：**PR 阶段零流水线；`push main` 只跑六项静态门禁（预算 180 秒）；
> `push tag v*` 才跑全量用例 + 镜像重建。**

## 为什么改

改造前是「每个 PR 都跑一遍全量」：8 门语言矩阵 + 608 个用例 + shared 自测。
实测一轮墙钟约 **583 秒**（go 一门就 544 秒）。并行派 N 张卡时，
这 N 份额度几乎同时在烧，而其中绝大多数提交还只是中间状态。

全量校验真正要回答的问题是「这批改动能不能进 main」——
这个问题**在合并那一刻问一次**就够了，不需要在每次 push 分支时问 N 次。

## 三档

| 档 | 触发 | 跑什么 | 预算 |
|---|---|---|---|
| —— | `pull_request` | **什么都不跑** | —— |
| fast | `push main` / `dev`、手动 | 静态检查、COVERAGE、镜像探测、8 门格式化、shared 自测、release 自测 | **180 秒** |
| full | `push tag v*`、手动 | 上面全部 + 全量用例矩阵 + 镜像重建 + 体积预算 + VERSION/tag 一致 | 不设上限 |

对应文件：

- `.github/workflows/ci.yml` —— fast 档
- `.github/workflows/full.yml` —— full 档（镜像部分 `uses:` 复用 `images.yml`，不复制那 200 行）
- `.github/workflows/images.yml` —— 镜像构建；`push main` 且 `paths: images/**` 时也跑

## fast 档为什么是这六项

| 门禁 | 挡住了什么 | 为什么必须留 |
|---|---|---|
| 静态检查 | shellcheck、用例缺 `run.sh`、Dockerfile 写死版本、文档命令失效 | 都是秒级，且一旦漏了要几周后才发现 |
| COVERAGE | 覆盖表与 `examples/` 不同步 | 9 秒 |
| 镜像探测 | 「镜像还没建」被误报成「格式不达标」 | 6 秒，纯粹让红的原因可读 |
| 8 门格式化 | 并行派卡最常见的漂移：两张卡各改一半，合起来不达标 | 便宜，丢了格式会慢慢烂掉 |
| shared 自测 | 工具箱回归 | 35 秒 |
| release 工具自测 | 打 tag / 生成 CHANGELOG 这条链路回归（零依赖，不起容器） | 10 秒 |

**不含用例矩阵**：它已经在 `scripts/pre-merge.sh` 里跑过了（见下），
main 上再跑一遍只是重复确认，而它一门就要 544 秒。

## 合并前总闸：`scripts/pre-merge.sh`

PR 阶段不跑 CI，所以「分支能不能合」必须在本地一次性验完。
这个脚本等价于把 fast + full 两档都跑一遍，但只烧一次机器时间。

```bash
# 演练：只合并 + 校验，不推
bash scripts/pre-merge.sh --branches feat/a feat/b

# 绿了直接推 main
bash scripts/pre-merge.sh --branches feat/a feat/b --push

# 只改文档时跳过用例矩阵
bash scripts/pre-merge.sh --from-file /tmp/plan.txt --skip-examples --push

# 本批改了 db/ 时会自动带上 db 轨道；没改 db/ 但想手动跑一次就加 --with-db
bash scripts/pre-merge.sh --branches feat/db-x --with-db
```

它做的事：

1. 从 `origin/main` 开一个临时 worktree，按给定顺序**逐个 squash 合并**
   （身份固定 `zeek.zhao <zeek.zhao@foxmail.com>`，不用 API 合并）
2. 门禁文件比对（清单读 **base 分支**的版本，防止「先把自己加进白名单再改门禁」）
3. 版本真本、文档命令、覆盖表、shared 索引、shared 自测
4. 8 门格式化 `--check`
5. 每门语言的**全部**用例
6. 全绿才 `git push origin HEAD:main`

> **db 轨道默认按需跑**：它的 compose 项目名固定为 `devbox-db`，栈是独占的。
> 在临时 worktree 里起它会顶掉别的 worktree 正在用的那套，所以只在
> 「本批 diff 里出现 `db/`」或显式 `--with-db` 时才跑，其余情况打印 `[SKIP]`。

冲突默认**停下来**，不自动解。要自动解必须显式 `--auto-resolve`，
它用的是「分支是否真改过该文件」判据，并把每个文件的取边决定逐条打印。

> 为什么默认不自动解：本项目踩过一次 —— 冲突全部取 `ours`，21 个 PR 都报
> 合并成功、退出码 0，但 77 个 db 用例被静默退回成 8 行骨架，
> 而骨架自己也能跑通。全量用例**不会**发现这种退化。

## 打 tag 之前

```bash
# 1) 版本号真本
cat VERSION          # 必须是 0.1.0 这类形态
# 2) 演练 full 档（workflow_dispatch 手动触发一次）
gh workflow run full.yml
# 3) 真打
git tag "v$(cat VERSION)" && git push origin "v$(cat VERSION)"
```

`full.yml` 会校验 `VERSION` 与 tag 逐字一致（去掉 `v` 前缀）。
少这一条，tag 上的版本号和仓库里写的版本号可以永久不一致而没人发现。

## 预算怎么守

- 每个 fast 档 job 都有 `timeout-minutes: 3` —— 这是**硬**的，超了直接失败。
- 另有 `wallclock` job 读 runner 上的真实时间戳（含排队），超 180 秒**只发 `::warning::`**，不判红。

硬红会让「runner 慢一点」变成「代码有问题」，噪音盖过信号；
而 timeout 已经在兜底了，所以守卫只负责「让预算漂移看得见」。

## 加新语言时要改哪里

只有两处，且都不在 CI 里：

1. `images/lang-images.tsv` —— 语言 → 镜像层映射（C 复用 `devbox-cpp` 就是靠它）
2. `ci.yml` / `full.yml` 的 matrix `lang:` 列表

漏了第 1 条会拉错镜像；漏了第 2 条不会报错，只是那门语言**静默不跑**。
