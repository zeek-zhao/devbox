# 错误码与错误结构

> 本文回答一个问题：**错误离开产生它的模块时，应该长什么样**。
> 模型层「为什么」见 [81-错误处理四模型与分类法](81-错误处理四模型与分类法.md)；
> 逐轨怎么写进代码见各轨 `docs/错误处理指南.md`。
> 结构参照 RFC 9457（Problem Details for HTTP APIs）的取舍原则：
> **字段少而稳定，机器可判，人可读**。

## 1. 为什么需要统一结构

每个模块自造错误格式，排查时就要写 N 个解析器；结构统一后，
「分类 → 重试/上报/拒绝」的决策可以做成一处通用逻辑
（分类动作表见 [81 §3](81-错误处理四模型与分类法.md)）。

统一结构**不是**统一措辞：各轨内部表达自由（Go 的 error、Java 的异常链、SQLSTATE），
约束只发生在**边界**——错误要交给另一个进程、另一个团队、另一个调用方的那一刻。

## 2. 统一错误对象字段表

跨边界错误对象按下表定义（RFC 9457 风格，字段名用小写下划线）：

| 字段 | 类型 | 必填 | 示例 | 约束 |
|---|---|---|---|---|
| `code` | string | 是 | `DB_DEADLOCK_RETRY_EXCEEDED` | §3 的分段码，全大写下划线，可在文档中检索到 |
| `category` | string | 是 | `transient` | 五分类枚举：transient / permanent / validation / business / system（见 81 §3） |
| `message` | string | 是 | `deadlock retry exceeded after 3 attempts` | 面向人的单句描述；**不含**内部实现细节（路径、异常类名、SQL 原文） |
| `retryable` | bool | 是 | `true` | 与 `category` 一致：仅 transient 为 true；机器据此决策 |
| `detail` | object | 否 | `{"attempts": 3, "wait_ms": 900}` | 结构化补充；键名稳定可检索，值不含敏感原文 |
| `cause_ref` | string | 否 | `E-003-deadlock-retry#expected.txt:2` | 指向仓库内可核对的证据位置；生产系统指向日志/trace ID |

判据：**机器只依赖 `code` / `category` / `retryable` 三个字段做决策**；
`message` / `detail` 只给人看。人不依赖的字段允许缺省，机器依赖的字段缺省即契约破坏。

## 3. 错误码分段与 9 轨落点

码格式：`<域>_<对象>_<情形>`，域即轨道名。**每一个 E 例（E-001..E-015）都在制造
本轨的码**，其中 E-009（边界翻译题）是码结构落点的标准考场：

| 轨道 | E-009 题目 | 内部原始形态 | 出门码（`<域>_<对象>_<情形>`） |
|---|---|---|---|
| c | [E-009-errno-boundary](../c/examples/E-009-errno-boundary/README.md) | `errno == EACCES` | `C_FILE_ACCESS_DENIED`（errno 在边界翻译，不外透 `EACCES` 字面量） |
| cpp | [E-009-leak-guard](../cpp/examples/E-009-leak-guard/README.md) | 异常路径上的资源泄漏 | `CPP_RESOURCE_LEAK_GUARD`（守卫失败即 system 类，快速失败） |
| go | [E-009-errno-boundary](../go/examples/E-009-errno-boundary/README.md) | `syscall.Errno` | `GO_SYSCALL_TRANSLATED`（os 包错误在边界译成应用码） |
| rust | [E-009-iterator-error-flow](../rust/examples/E-009-iterator-error-flow/README.md) | 迭代中首个 `Err` | `RUST_ITER_STOPPED_AT`（`collect::<Result>()` 停在哪一步，码里带位置） |
| shell | [E-009-tool-code-boundary](../shell/examples/E-009-tool-code-boundary/README.md) | 外部命令退出码 | `SHELL_TOOL_EXIT_N`（外部工具退出码翻译后出门，不裸透） |
| python | [E-009-error-aggregation](../python/examples/E-009-error-aggregation/README.md) | 多个校验异常 | `PY_VALIDATION_BATCH`（聚合报告一次出门，码相同、detail 分条） |
| java | [E-009-assert-contract](../java/examples/E-009-assert-contract/README.md) | 断言失败 | `JAVA_ASSERT_CONTRACT`（断言只管内部契约，出门换 validation 码） |
| vue | [E-009-async-boundary](../vue/examples/E-009-async-boundary/README.md) | Promise rejection | `VUE_ASYNC_UNHANDLED`（异步边界漏接，rejection 出门统一成该码） |
| db | [E-009-charset-mojibake](../db/examples/E-009-charset-mojibake/README.md) | SQLSTATE + 乱码 | `DB_CHARSET_MISMATCH`（连接/表/数据三处 charset 不一致，翻译成人话再出门） |

> 表格判据：左列 9 行 = 9 轨；右列码都能在对应 E 例的 README/expected.txt 里核对到
> 同一情形（码值是文档约定，E 例可执行验证的是**情形**本身）。

## 4. 正反例：为什么不能透内部异常原文

### 4.1 正例：翻译后出门

内部 db 死锁重试耗尽。出门的是：

```json
{
  "code": "DB_DEADLOCK_RETRY_EXCEEDED",
  "category": "transient",
  "message": "deadlock retry exceeded after 3 attempts",
  "retryable": true,
  "detail": { "attempts": 3, "wait_ms": 900 },
  "cause_ref": "E-003-deadlock-retry"
}
```

调用方拿到 `retryable=true` 就能退避重试，不需要懂 SQLSTATE；
`cause_ref` 指回仓库内 [db E-003](../db/examples/E-003-deadlock-retry/README.md) 的可核对证据。
完整重试动线见该例 README 与 `db/docs/排查手册.md`。

### 4.2 反例：透原文（并说明为什么不行）

```json
{
  "error": "psycopg2.errors.DeadlockDetected: deadlock detected\nDETAIL:  Process 14283 waits for ShareLock on transaction 8812; blocked by process 14281.\n    at /app/db/conn.py:47 in _execute"
}
```

三宗罪，逐条对应契约字段：

1. **机器不可判**——调用方要对 `psycopg2.errors.` 做字符串匹配才能决策，
   换个驱动（Java 侧同库）决策代码就废。`category`/`retryable` 字段就是为消灭这种匹配而设。
2. **泄内部**——文件路径 `/app/db/conn.py:47`、进程号、事务号是内部实现细节；
   message 的约束（§2 表）明确禁止。攻击者可用它定位代码结构，排查者会被引到错误的层。
3. **分类错位**——原文看起来吓人，但它仍是 transient（重试能过，见 81 §3 边界判据）；
   不带 `category` 的原文会把「重试一次就好」的错报成事故。

> 本例情形可在 [db E-003](../db/examples/E-003-deadlock-retry/README.md) 本地复现：
> 两个会话互锁后，把驱动原文直接透出与翻译后出门对比。
