## 0. 七域一览

| 域 | 一句话结论 |
|---|---|
| R1 版本语义 | 版本工具与门禁齐备；缺真正生成过的 CHANGELOG 与发布 runbook |
| R2 可复现构建 | 版本单一真本 + 门禁已有；「两次构建产物一致」无任何校验 |
| R3 制品与不可变 | `sha-<commit>` 不可变 tag 已有；digest 留存与发版制品空缺 |
| R4 变更与兼容 | 工具已按 SemVer 处理 breaking change；规范未成文、CHANGELOG 不存在 |
| R5 供应链 | 依赖版本 + 校验和真本已有；产物级依赖清单 / SBOM 空缺 |
| R6 部署与回滚 | 除 runtime 镜像与 Compose 栈外基本空白；演练记录为零 |
| R7 运行时就绪 | 有能跑的 runtime 镜像与 hello 冒烟；健康检查等演示为零 |

## R1 版本语义

> 定义（沿用 [20](20-开发发布增强.md) §2）：SemVer 版本号 + tag + CHANGELOG；
> 验收判据是「能从 commit 推导出下一个版本号」。

### 最小可演示产物

- **已有**：`VERSION`——项目版本单一真本（单行 plain 文本，当前值见文件本身）。
- **已有**：`shared/release/`——`@zeek/release` 版本管理工具，一条链做完
  Conventional Commits 解析（`src/commits.js`）→ 算版本（`src/bump.js`）→
  渲染 CHANGELOG（`src/changelog.js`）→ 打 tag / 提交（`src/git.js`），
  含六条安全默认（`shared/release/README.md`：默认 dry-run、脏树拒跑、
  保护分支默认拒绝、版本白名单、不自动 push、不联网）。
- **已有**：`shared/release/release.config.js`——`versionFiles` 白名单只认
  `package.json` 与 `VERSION`，永不把 `GO_VERSION` 这类依赖版本当项目版本 bump。
- **已有**：`.github/workflows/ci.yml` `static` job——`push tag v*` 时逐字校验
  `VERSION` 与 tag 一致，不一致硬失败。
- **已有**：git tag `v0.1.0`（仓库第一个正式版，2026-11-01，见 [30](30-GitHub现状与时限.md)）。
- **该补**：仓库根 `CHANGELOG.md` 不存在——工具支持生成，但从未真正 `--write` 过一次。
- **该补**：发布 runbook（go/no-go 记录）没有独立文档；是否新建独立 `release.yml`
  是 `Q-R-01`，**待 M9-GATE（#224）拍板**。

### 可判定验收判据

- 命令：`cd shared/release && node --test test/*.test.js`——工具自测全绿，
  证明「解析 → 算版本 → 渲染」链路可用（CI 的 `release` job 跑的就是它）。
- 人工判据：在仓库根跑 `npx @zeek/release`（默认 dry-run、不改任何文件），
  输出能从当前 commit 历史推导出下一个版本号与计划列表。

## R2 可复现构建

> 定义（沿用 [20](20-开发发布增强.md) §2）：固定依赖 + 固定基础镜像 + 一条构建命令；
> 验收判据是「同 commit 两次构建产物一致」。

### 最小可演示产物

- **已有**：`images/versions.env`——依赖版本单一真本（工具链版本、镜像 tag、
  校验和都只在这里写一次；本文引用版本一律只写变量名，不写死数值）。
- **已有**：`scripts/check-version-truth.sh`——校验所有 `images/*/Dockerfile` 的
  `ARG` 默认值与真本逐字一致，并拦「Dockerfile 里写死镜像 tag / 补丁号」。
- **已有**：跨镜像引用固定 tag——语言镜像父层用
  `BASE_IMAGE=$REGISTRY/devbox-tool:sha-<commit>`，禁止 `FROM tool:latest`
  （见 [01-镜像体系](01-镜像体系.md) §4）。
- **已有**：`.github/workflows/images.yml`——push 到 main 后权威构建，产物 tag
  只由本次 commit 决定。
- **该补**：「同 commit 两次构建产物一致」目前没有任何校验——CI 不比对两次构建的
  digest，可复现性只是设计意图，不是被验证的事实。
- **该补**：各语言项目内「固定依赖 + 一条构建命令」的复现说明尚未成文
  （属 [20](20-开发发布增强.md) §3 的 9 张语言表，M9-03 / #212 产出，不在本卡）。

### 可判定验收判据

- 命令：`bash scripts/check-version-truth.sh`——输出「版本真本与 Dockerfile ARG
  默认值一致」即通过（CI `static` job 同款）。
- 人工判据：同一 commit 重跑 `images.yml` 构建两次，对比产物 digest 是否一致
  （当前预期：构建缓存与 apt 源漂移可能导致不一致，需实测后记录）。

## R3 制品与不可变

> 定义（沿用 [20](20-开发发布增强.md) §2）：带 digest 的制品 + 版本化 tag；
> 验收判据是「同一版本重跑不会覆盖已有制品」。

### 最小可演示产物

- **已有**：`.github/workflows/images.yml` 顶部 `IMAGE_TAG: sha-${{ github.sha }}`——
  全部镜像推 `sha-<commit>` 不可变 tag。
- **已有**：PR 只推 sha 不推 `:latest`——`#184` 修复的并发污染问题，
  已知限制登记为 [ROADMAP](ROADMAP.md) `KI-08`。
- **已有**：git tag `v0.1.0` + tag 触发时 `VERSION` 一致性门禁（R1 已列）。
- **该补**：没有任何 digest 记录与制品留存策略——`sha-<commit>` tag 存在，
  但「这个 tag 对应哪个 digest」无处可查。
- **该补**：除镜像与 git tag 外没有其他发版制品（无 GitHub Release 步骤、
  无独立 `release.yml`）；要补到什么程度（digest / provenance / SBOM / 签名）
  是 `Q-R-02`，**待 M9-GATE（#224）拍板**。

### 可判定验收判据

- 人工判据：在镜像 registry 上查同一 `sha-<commit>` tag 的 digest——同 commit
  重推不应改变 digest（需留一次实测记录，当前未实测）。
- 辅助命令：`grep -n "IMAGE_TAG: sha-" .github/workflows/images.yml`——确认
  不可变 tag 约定真实存在于工作流定义。

## R4 变更与兼容

> 定义（沿用 [20](20-开发发布增强.md) §2）：CHANGELOG 含 breaking change 段；
> 验收判据是「breaking change 时版本号按 SemVer 递增」。

### 最小可演示产物

- **已有**：`shared/release/src/commits.js`——识别 `feat!:` / `fix!:` 与
  `BREAKING CHANGE:` footer 两种 breaking 标记。
- **已有**：`shared/release/src/bump.js`——breaking 时按 SemVer 递增：
  1.x 走 major、0.x 走 minor（0.x 兼容性只承诺到 minor 线）。
- **已有**：`shared/release/src/changelog.js`——渲染「⚠️ Breaking Changes」分节。
- **已有**：`shared/release/test/bump.test.js`、`test/changelog.test.js`——
  `breaking -> major` 等行为有测试钉住。
- **该补**：仓库根 `CHANGELOG.md` 不存在（同 R1），breaking change 段从未在
  真实 CHANGELOG 里出现过。
- **该补**：「CHANGELOG 强制 breaking change 段」是 `Q-R-07`，**待 M9-GATE（#224）拍板**。
- **该补**：各语言轨道无兼容声明实践（Go `/v2`、Python `~=`、Rust 0.x 语义等）——
  属 M9-03 / #212 的语言表。

### 可判定验收判据

- 命令：`cd shared/release && node --test test/bump.test.js test/changelog.test.js`。
- 人工判据：构造一条 `feat!:` 提交后 dry-run，输出显示 1.x 递增 major、
  0.x 递增 minor，且计划列表含 breaking 条目。

## R5 供应链

> 定义（沿用 [20](20-开发发布增强.md) §2）：依赖清单 / SBOM / 校验和；
> 验收判据是「能列出产物里所有直接依赖」。

### 最小可演示产物

- **已有**：`images/versions.env`——所有直接下载的工具都带 SHA256 校验和
  （`GJF_SHA256` / `YQ_SHA256` / `ACTIONLINT_SHA256` / `GIT_FILTER_REPO_SHA256` /
  `NODE_SHA256` / `GO_SHA256`），install 脚本校验不符直接报错而非静默跳过。
- **已有**：`scripts/check-version-truth.sh`——版本与校验和的落点被门禁强制
  与真本一致。
- **该补**：「能列出产物里所有直接依赖」目前做不到——镜像层 apt 装了哪些运行时
  库没有清单；各语言用例的依赖树没有统一出口。
- **该补**：是否引入 SBOM 是 `Q-R-02`；依赖清单集中一份还是各语言自持是 `Q-R-06`；
  均**待 M9-GATE（#224）拍板**。按 `Q-D-05`，即使纳入也只到「一个容器里能跑出
  依赖列表」的尺度，不追完整 SLSA。

### 可判定验收判据

- 命令：`bash scripts/check-version-truth.sh`（校验和与版本真本的一致性）。
- 人工判据：当前**不满足**，如实记录：等 `Q-R-02` / `Q-R-06` 拍板后，用拍板选定的
  方式在容器内列出至少一个产物的全部直接依赖并留档。

## R6 部署与回滚

> 定义（沿用 [20](20-开发发布增强.md) §2）：部署记录 + 回滚脚本 + 演练记录；
> 验收判据是「回滚在演练环境真跑通过」。这是七域里「该补」最重的一域。

### 最小可演示产物

- **已有**：`images/runtime/Dockerfile`——最小运行时镜像，可作为部署演示的环境
  （注意口径：实际安装的是 `python3` 而非 `python3-minimal`，见 [40](40-问题清单.md) `Q-S-08`）。
- **已有**：`db/docker-compose.yml` Compose 栈——db 轨道的可起停环境，
  是「演练环境」的候选底座。
- **该补**：没有任何部署记录、回滚脚本、演练记录——「能回滚」目前只是假设。
  回滚 runbook 不存在；真演练还是只写 runbook 是 `Q-R-03`，**待 M9-GATE（#224）拍板**。
- **该补**：按 `Q-D-05`，即使拍板做演练，尺度也是「一个容器里演示
  旧版本 → 新版本 → 回退并留记录」，不是生产级发布平台。

### 可判定验收判据

- 人工判据：当前**不满足**，如实记录：在容器内真跑一次回滚并留下可复核的
  演练记录（命令、现场、结果）才算过——写一份文档不算过（[20](20-开发发布增强.md) §4 原口径）。

## R7 运行时就绪

> 定义（沿用 [20](20-开发发布增强.md) §2）：健康检查、优雅退出、结构化日志、超时；
> 验收判据是「故意杀进程不会留下半写状态」。

### 最小可演示产物

- **已有**：`images/runtime/Dockerfile`——部署用的最小运行时镜像（见 R6 口径说明）。
- **已有**：`.github/workflows/images.yml` 各语言 job 推送前**真跑 hello 用例**
  （smoke test）——证明镜像能跑，但这是「能启动」，不是「就绪」。
- **该补**：毕业项目没有健康检查 / 优雅退出 / 结构化日志 / 超时的任何演示代码
  或演示记录；加到什么程度是 `Q-R-04`，**待 M9-GATE（#224）拍板**。
- **该补**：按 `Q-D-05`，即使拍板纳入，D6 运行时项也只讲概念 + 容器内最小演示
  （故意 SIGTERM 看进程是否留下半写状态），不做真实流量 / SLO / 告警。

### 可判定验收判据

- 人工判据：当前**不满足**，如实记录：在容器内跑一个带清理逻辑的进程，
  `kill -TERM` 后确认无半写状态（临时文件已清理 / 输出完整落盘），
  现象与结论留档。
