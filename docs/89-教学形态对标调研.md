# 教学形态对标调研：本仓「跑正确代码」vs rustlings「改坏代码」

本文是一次**调研**，不是规范，也不是排期。目的是把一个定位问题摆到明面上：

> 本仓 794 个用例全部是「给你正确的代码，让你读 + 跑」。
> rustlings 一类仓库是「给你坏掉的代码，让你修」。
> 本仓要不要补「动手环节」？如果要，怎么补才不推翻现有的 794 个用例？

**本文不给结论**。结论由维护者读完 §6 的三条路径后拍板。

---

## 1. 本仓现状：正确代码 + 逐行 diff

### 1.1 三文件契约

`docs/13-通用开发指南.md:21-25` 定义的契约极简：

| 文件 | 要求 |
|---|---|
| `run.sh` | 必须存在；自己负责编译与运行，只往 stdout 打业务输出 |
| `expected.txt` | 期望输出；逐行精确，忽略行尾空白与首尾空行 |
| `README.md` | **考点说明** |

注意 `README.md` 那一列只有四个字：「考点说明」。契约**没有**规定 README 要写哪些段落——这本身就是 [399] 要解决的问题。

### 1.2 run.sh 的实际形态（go L1-002）

```bash
#!/usr/bin/env bash
set -euo pipefail

OUT="${TMPDIR:-/tmp}/devbox-go-L1-002-zero-values"
go build -o "$OUT" main.go
"$OUT"
```

三段：`go build` 编译 → `"$OUT"` 运行 → stdout 交给上层 diff。**代码是完整的、正确的，用户不需要改任何一行。**

### 1.3 expected.txt 的实际形态

```text
short declaration: 7
int zero: 0
bool zero: false
string zero: ""
pointer is nil: true
slice is nil: true
map is nil: true
struct zero: {Limit:0 Enabled:false}
initialized map value: 1
```

用户的学习动作是：**读 README 的考点 → 跑用例 → 看输出 → 理解为什么是这个输出**。

### 1.4 实测数据（2026-11-12，HEAD d5b340a）

| 指标 | 数值 | 采集命令 |
|---|---:|---|
| examples 目录总数 | **804** | `find */examples -mindepth 2 -maxdepth 2 -name run.sh \| wc -l` |
| 其中 E 类（错误处理） | **135** | `find */examples -mindepth 1 -maxdepth 1 -type d -name 'E-*' \| wc -l` |
| README 含 `## 考点` | 642 / 804 | 逐篇 `grep -q '^## 考点'` |
| README 含易错点段 | 550 / 804 | 同上 |
| README 含延伸段 | 360 / 804 | 同上 |
| README 含复现段 | 513 / 804 | 同上 |
| `main.*` 里 `TODO` / `FIXME` | **0** | `grep -rn '\bTODO\b\|\bFIXME\b' */examples/*/main.* \| grep -v TMPDIR \| wc -l` |
| E 类 README「反例」段含可执行代码块 | **0 / 135** | 见 §4.1 |
| 做了 `run_right` / `run_wrong` 真跑对照的用例 | **1** | 见 §4.2 |

结论：**全仓没有一个「让用户改代码」的用例**。

## 2. rustlings 的模型：坏代码 + 工具链报错

> 本节内容均从仓库原文抓取（2026-11-12），非二手转述。

### 2.1 结构

```
exercises/<NN_topic>/<name>.rs     ← 用户要改的坏代码
solutions/<NN_topic>/<name>.rs     ← 标准答案（用户先不看）
rustlings-macros/info.toml         ← hint 文本 + test 开关
```

三个目录各司其职：`exercises/` 是题面，`solutions/` 是解，`info.toml` 是提示。

### 2.2 题面原文：`exercises/01_variables/variables1.rs`

```rust
fn main() {
    // TODO: Add the missing keyword.
    x = 5;

    println!("x has the value {x}");
}
```

这文件**编译不过**。用户跑 `rustlings`，编译器直接报 `cannot find value 'x' in this scope`，用户补上 `let` 就好了。

### 2.3 答案原文：`solutions/01_variables/variables1.rs`

```rust
fn main() {
    // Declaring variables requires the `let` keyword.
    let x = 5;

    println!("x has the value {x}");
}
```

答案比题面多两样东西：一行注释解释「为什么要 `let`」，以及补上的 `let`。

### 2.4 hint 原文：`info.toml`

```toml
[[exercises]]
name = "variables1"
dir = "01_variables"
test = false
hint = """
The declaration in the `main` function is missing a keyword that is needed
in Rust to create a new variable binding."""
```

`variables2` 的 hint 更典型——**连续六个反问**，逐步把用户推向答案：

```toml
hint = """
The compiler message is saying that Rust can't infer the type that the
variable binding `x` has with what is given here.

What happens if you annotate the first line in the `main` function with a type
annotation?

What if you give `x` a value?

What if you do both?

What type should `x` be, anyway?

What if `x` is the same type as `10`? What if it's a different type?"""
```

### 2.5 需要真断言的题：`exercises/12_options/options1.rs`

有些题编译器不管，得靠测试。这类题在文件里内嵌 `#[cfg(test)] mod tests`：

```rust
fn maybe_ice_cream(hour_of_day: u16) -> Option<u16> {
    // TODO: Complete the function body.
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn check_ice_cream() {
        assert_eq!(maybe_ice_cream(0), Some(5));
        assert_eq!(maybe_ice_cream(9), Some(5));
        assert_eq!(maybe_ice_cream(18), Some(5));
        assert_eq!(maybe_ice_cream(22), Some(0));
        assert_eq!(maybe_ice_cream(23), Some(0));
        assert_eq!(maybe_ice_cream(24), None);
        assert_eq!(maybe_ice_cream(25), None);
    }
}
```

### 2.6 定位

仓库 README 第一行原文：

> Small exercises to get you used to reading and writing Rust code - _Recommended in parallel to reading [the official Rust book](https://doc.rust-lang.org/book)_ 📚️

**「与官方书平行阅读」**——它不是教材，是教材的练习册。这个定位很重要，见 §3.3。

### 2.7 规模

64.6k star / 436 contributors / 最新 v6.5.0 / 3,406 commits。每个语言主题约 90–100 道小题（15 个 topic 目录 × 数题）。

## 3. 两套模型的差异与各自盲区

### 3.1 对照表

| 维度 | rustlings | 本仓 devbox |
|---|---|---|
| 用户动作 | **改坏掉的代码** | **读 + 跑正确的代码** |
| 反馈来源 | **编译器 / 测试断言**（工具链） | **expected.txt 逐行 diff** |
| 一次学习闭环 | 报错 → 改 → 再编译 | 读考点 → 跑 → 看输出 → 理解 |
| 反馈的可信度 | 高（编译器不会撒谎） | 高（输出是实测的） |
| 反馈的**覆盖面** | 只覆盖能编译/能断言的 | 覆盖**能观察的一切**（日志、退出码、时序） |
| 覆盖深度 | 语法层为主 | 含 L2 工程 / L3 专题 / L4 设计模式 |
| 单题粒度 | 10–40 行 | 46–99 行（实测 E 类样本） |
| 「错误」在哪 | **在代码里**，用户要修 | **在 README 文字里**，用户只是读 |
| 定位 | 官方书的配套练习册 | 独立的多语言工程实践路线 |

### 3.2 各自盲区

**rustlings 的盲区**：编译器能检查的东西它才能教。多文件构建、CI 配置、sanitizer 报告、并发时序、内存模型、FFI 边界——这些**编译器和断言都管不了**，rustlings 天然覆盖不到。它的题都是单文件单函数的小题。

**本仓的盲区**：**用户从头到尾没写过一行代码**。看完 90 个用例，理解了 90 件事，但没有任何一次「自己动手然后被反馈」的经验。学习科学里这叫「没有 retrieval practice」——只读不练，长期留存率显著低于读+练。

### 3.3 关键判据：两套模型服务的是不同阶段

rustlings 自己把定位钉在「与书平行阅读」。这意味着它假设用户**在别处读到了知识**，它只负责**把知识练成肌肉记忆**。

本仓的 L2/L3 用例（多文件构建、CI、sanitizer、并发、内存模型、FFI）**不是肌肉记忆**，是**对系统性约束的理解**。这类内容做成改错题价值不高——「把 CI 配置改对」不是一道好题，「读懂 CI 为什么这么配」才是本仓在做的事。

**所以：本仓缺的不一定是「改错题」，缺的是「动手」。这两者不能划等号。**

## 4. 本仓已有的「错误示范」：两种形态，一种能用一种不能用

### 4.1 形态 A：README 文字描述（135 个，占 100%）

E 类用例的 README 有 `## 反例` 段，但**全部是纯文本**，没有一个可执行。

`c/examples/E-001-error-taxonomy/README.md` 的原文：

```markdown
## 反例

- 用魔法数字直接比较：`if (err == 3)` ——码的含义散落全仓，改一个码全场静默错。
- 类别与动作不匹配：对 `USAGE`（调用方 bug）重试三次——重试不会修好调用方的参数错误，
  只是把失败推迟并放大。
```

这两句话是**对的**，但读者**无法验证**。写「重试只是把失败推迟并放大」——真会放大吗？放大多少？没有代码跑过，读者只能选择相信。

实测：135 个 E 类 README 的反例段里，含反引号代码片段的有 104 个（那些是**行内引用**，如 `` `if (err == 3)` ``），含**真正可执行代码块**（```围栏）的有 **0 个**。

### 4.2 形态 B：`run_right` / `run_wrong` 真跑对照（**全仓仅 1 个**）

唯一的例外是 `shell/examples/E-007-cleanup-guarantee/main.sh`（56 行）。它把正确和错误两种写法都实现成函数，**都真跑一遍**：

```bash
run_right() {
  # trap EXIT 挂清理：无论从哪条路径退出，清理都会跑；业务退出码原样冒出。
  work_dir="$(mktemp -d "${TMPDIR:-/tmp}/devbox-e007-right.XXXXXX")"
  trap cleanup_ok EXIT
  task "$work_dir"          # 返回 3
}

run_wrong() {
  # 错误形态：业务失败被接住却忘了上抛，收尾清理成了最后一条命令，
  # 它自己的失败（退出码 1）顶替了业务退出码。
  work_dir="$(mktemp -d "${TMPDIR:-/tmp}/devbox-e007-wrong.XXXXXX")"
  local rc=0
  task "$work_dir" || rc=$?      # 接住了，但没上抛
  broken_final_cleanup           # 它自己必然失败（退出码 1）
}
```

`expected.txt` 如实记录两种输出：

```text
right-mode: business exit preserved: 3
wrong-mode: observed exit=1 (business 3 masked by cleanup)
```

**这比文字强在哪里**：文字说「清理自己的失败会顶替业务退出码」，读者可能觉得是理论问题；代码跑出 `observed exit=1 (business 3 masked by cleanup)`——业务本来是 3，观测到 1，**错误的后果被量化了**。

### 4.3 形态 B 为什么只有 1 个

不是技术做不到（E-007 证明了能做），而是**契约没要求**：`docs/13` 的 README 契约只有「考点说明」四个字，`scripts/check-error-examples.sh:98-104` 对 README 只检查两件事：

```bash
if [ ! -f "$d/README.md" ]; then
  echo "FAIL $t/$base: README.md 不存在"
  fail=1
elif ! grep -Eq 'coverage:[[:space:]]*exempt[[:space:]]+[^[:space:]]' "$d/README.md"; then
  echo "FAIL $t/$base: README.md 缺少非空 coverage: exempt 理由"
  fail=1
fi
```

**存在性 + exempt 声明**，就这两条。没有脚本检查 README 写了什么，更没有脚本检查反例跑没跑过。

## 5. 成本估算（若要推进）

以下估算基于 §1.4 与 §4 的实测数据，不是拍脑袋。

### 5.1 路径一：E-007 式（反例真跑，不改用户代码）

让 135 个 E 类用例各多一个「错误分支」，跑出来给读者看。

| 项 | 估算 | 依据 |
|---|---|---|
| 每例代码量 | +15–30 行 | E-007 的 `run_wrong` + `broken_final_cleanup` 合计约 15 行，加注释约 25 行 |
| 每例 expected.txt | +1–3 行 | 错误分支的输出 |
| 总量 | **135 例 × 20–30 行 ≈ 2700–4000 行** |  |
| 人力 | **1–2 天机械工作量 + 判据设计 1 天** | 难点不在写代码，在**定义「怎么算正确地错了」** |
| 门禁影响 | 需新增契约 + 检查脚本 | 否则第 136 个新 E 例又会退回纯文本 |

**判据设计为什么是难点**：E-007 的错误分支输出 `observed exit=1` 是**确定值**，可以逐行 diff。但「重试三次把失败放大」这类反例，输出可能是「耗时增加」或「日志变多」，**不一定有稳定的逐行文本**。这类反例要么改断言方式（退出码 / 正则），要么放弃。

### 5.2 路径二：rustlings 式（坏代码让用户改）

引入 `exercises/` + `solutions/` 双目录。

| 项 | 估算 | 依据 |
|---|---|---|
| 新增文件形态 | **1 种全新的目录契约** | `exercises/<id>/` 放坏代码，`solutions/<id>/` 放答案 |
| 每例代码量 | 20–50 行坏代码 + 同量答案 | rustlings 单题 10–40 行，本仓用例粒度更大 |
| 适用用例比例 | **L1 层为主**（约 300 个可用） | L2/L3/L4 的系统性约束不适合做成改错题（§3.3） |
| 总量 | **300 例 × 2 文件 ≈ 12000+ 行** | 且要重写，不能复用现有 794 个用例 |
| 人力 | **1–2 周** | 远大于路径一 |
| 与现有结构冲突 | **高** | 现有 794 个用例的 `run.sh` 契约是「跑正确代码」，新形态要另一套入口 |

### 5.3 路径三：不实施，只把差异写进文档

| 项 | 估算 |
|---|---|
| 成本 | 本文档即产出 |
| 收益 | 读者知道本仓的定位与盲区，可以自行搭配别处的练习 |
| 风险 | 无 |

### 5.4 三条路径的效率对比

| 路径 | 成本 | 补上的能力 | 是否推翻现有结构 |
|---|---|---|---|
| 路径一（E-007 式） | 2–3 天 | 「错误后果可观察」 | 否，只是加内容 |
| 路径二（rustlings 式） | 1–2 周 | 「用户动手写代码」 | **是**，新增文件形态 |
| 路径三（只写文档） | 0 | 读者知情 | 否 |

注意：**路径一补不上「动手」**——用户还是不改代码，只是从「看正确的输出」变成「看正确的输出 + 看错误的输出」。真正的「动手」只有路径二能给。

## 6. 待维护者拍板的问题

以下三个问题本文**不给答案**：

### Q-89-1：本仓要不要「动手环节」？

如果答案是要，只有路径二能给（路径一给的是「观察」不是「动手」）。
如果答案是不要，那本仓的定位就是「**可执行的知识库**」而非「练习册」，这个定位本身是成立的——rustlings 需要书，本仓不需要。

### Q-89-2：如果补「观察错误」，用 E-007 式还是保持纯文本？

纯文本的好处：成本 0，且**反例往往比正确代码更难写对**（一个没写好的反例，会让读者学到错的东西）。
E-007 式的好处：错误后果被量化，读者不用信任文字。

### Q-89-3：如果都不做，要不要在 README 或 `docs/13` 里明说「本仓用例是正确代码，无动手环节」？

现状是**没说**。读者看完 794 个用例可能以为自己「练过了」，实际只是「读过了」。一句说明成本极低。

---

## 7. 本文不做的事

- 不改 `run.sh` / `expected.txt` / `README.md` 的任何既有内容
- 不新增检查脚本（避免「为了调研先加门禁」）
- 不建排期、不改 ROADMAP / 看板口径
- 不评价 rustlings 与本文档的优劣——两者定位不同（§3.3）
