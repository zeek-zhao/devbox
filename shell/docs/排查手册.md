# Shell 排查手册（G3 · 按问题域排障）

> 本文只有一个主要承诺：**按症状查到排查命令与判据**。每个小节统一四件套：
> 典型现象（可观察）→ 排查命令（可执行）→ 判据（期望输出）→ 修复（可验证）。
> §2「错误处理」章的 15 节逐一对应 15 个 E 系示范用例 README 的 exempt 指向
> （`shell/docs/排查手册.md 错误处理章`）；索引速查见 [知识点清单](知识点清单.md) §E。
> 命令契约统一 `TAG=latest scripts/run-example.sh shell <ID>`（[工程参考](工程参考.md) §5）。

## 1. 怎么用这本手册

1. 按症状在 §2 定位小节（每节标题即问题域）；
2. 先跑「排查命令」拿到真实输出，与「判据」对照——判据行不出现，说明故障形态与本节不同，换节或走 §3 lab；
3. 按「修复」改，重跑同一命令验证判据转绿；
4. 修完跑门禁：`bash shell/project/build.sh`（bash -n + shellcheck 按 `${SHELLCHECK_SEVERITY}` 口径，[工程参考](工程参考.md) §3）。

## 2. 错误处理（E 系 15 例对应节）

### 2.1 退出码分类体系（E-001-error-taxonomy）

- **典型现象**：失败只以裸非零码往上传，脚本没有统一的「码 → 类别」体系；该走默认值的被整脚本报错，该停止的被重试三次。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-001-error-taxonomy`
- **判据**：5 个码各归唯一类别，末行 `taxonomy codes=5 usage=1 environment=2 internal=1`。
- **修复**：定义固定码表并声明类别语义（usage/environment/internal），失败一律以类别码上传；调用点按类别分流而不是猜裸码。

### 2.2 错误创建（E-002-error-create）

- **典型现象**：失败时诊断信息随手 `echo`——有时打到 stdout 混进业务输出，有时不带「发生在哪」，有时退回 0。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-002-error-create`
- **判据**：失败路径一条标准化诊断 `main.sh: validate-name: name is empty` + `rc=2`；成功路径只有 `rc=0` 且无诊断行。
- **修复**：统一 `script名: 函数名: 消息` 格式、走 stderr、`return` 类别码；成功路径不产诊断。

### 2.3 错误匹配（E-003-error-match）

- **典型现象**：`if ! cmd` 一刀切——探测未命中（预期分支）与探测本身损坏（真失败）混成同一种处理。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-003-error-match`
- **判据**：三种探测结果各自落到唯一分支：`rc=0 classified=hit action=use-result`、`rc=1 classified=no-match action=use-default`、`rc=2 classified=probe-broken action=stop`。
- **修复**：按码三分支——命中用结果、未命中走默认、其他码停下报真失败。

### 2.4 错误包装（E-004-error-wrap）

- **典型现象**：包装时换码（`return 1`）底层类别丢失；包装时吞码（`cmd || return 0`）失败被伪装成功；诊断只剩最外层一句。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-004-error-wrap`
- **判据**：stdout 报失败链 `chain: deploy -> download -> fetch-artifact` 与 `preserved exit code: 22`；stderr 上底层原始 `HTTP 404` + 两层包装上下文都在。
- **修复**：保码（`return $rc`）+ 附本层上下文 + 诊断原文随 stderr 上传，三样齐全才叫包装。

### 2.5 错误身份（E-005-error-identity）

- **典型现象**：某层 `|| return 0` 吞成 0、诊断文本被改写；调用方按身份（码+消息）匹配的处理分支从此永远命不中。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-005-error-identity`
- **判据**：inner/middle/entry 三层 `code=7 message=missing-config` 完全一致（`transparent chain: identity preserved`）；swallowed 层 `code=0`（`swallowing: identity broken (code 7 -> 0)`）。
- **修复**：透明传播——不改码、不改消息；需要本层语境时附加而不是替换（见 §2.6）。

### 2.6 错误上下文链（E-006-error-context）

- **典型现象**：fetch 说 connection refused、download 说 failed、deploy 说 error，排障时要手工对齐三段报错。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-006-error-context`
- **判据**：一条完整链 `context chain: deploy: download: fetch: connection refused (rc=7)` + `chain layers: 3`。
- **修复**：每层把「本层在做什么」前缀式拼入上下文（`层名: 上游链: 根因 (rc=N)`），顶层一句话就是完整现场。

### 2.7 清理保证（E-007-cleanup-guarantee）

- **典型现象**：清理把失败「修没了」——收尾清理本身失败或清理后 `exit 0`，业务失败被顶替，上层看到的既不是成功也不是业务错误；或失败路径跳过清理，下次运行撞脏状态。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-007-cleanup-guarantee`
- **判据**：`right-mode: business exit preserved: 3`；wrong-mode 对照 `observed exit=1 (business 3 masked by cleanup)`。
- **修复**：trap 收尾前保存业务退出码，清理动作自身的失败只记日志不覆盖，最后按业务码退出。

### 2.8 记录后重抛（E-008-error-reraise）

- **典型现象**：中间层写日志 `step failed rc=4` 后 `return 0`——日志里有记录、上层拿到成功，监控全绿而业务没发生。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-008-error-reraise`
- **判据**：`mode=reraise report=step failed rc=4 exit=4`；swallow 对照 `mode=swallow ... exit=0`。
- **修复**：记录（日志）与处理（改退出路径）是两件事——记录完必须以原码重抛；只有「决定就地消化」的错误才允许返回 0，且要有明确理由。

### 2.9 外部命令退出码边界翻译（E-009-tool-code-boundary）

- **典型现象**：`grep` 的 1（未命中，预期分支）被上层当成失败重试；`diff` 的 1（有差异，正是要写文件的理由）被当成错误退出；工具真坏了（2）反而和未命中混成一谈——工具语义泄漏成脚本语义。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-009-tool-code-boundary`
- **判据**：5 次调用各自给出 `raw=`（工具原始码）、`kind=`（翻译后语义类别）、`action=`（对应动作），如 `tool=diff raw=1 kind=differ action=write`。
- **修复**：在调用边界建「raw 码 → kind → action」翻译表，逐工具维护；脚本内只消费 kind/action，不再出现裸工具码。

### 2.10 重试与退避（E-010-retry-backoff）

- **典型现象**：不可重试的错误（参数非法）被反复重试，把限流放大成打挂下游；或无预算无退避，按固定频率原样重放同一时刻的故障。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-010-retry-backoff`
- **判据**：`retry success: attempts=3 waited=30ms`（指数退避累计 30ms 后第 3 次成功）；`retry non-retryable: attempts=1 waited=0ms`；`retry give-up: attempts=4 waited=70ms`。
- **修复**：先分类（可重试/不可重试），可重试按指数退避加预算上限，不可重试首次即停；预算耗尽明确报 give-up 而不是静默放弃。

### 2.11 超时与截止时间（E-011-timeout-deadline）

- **典型现象**：流水线挂在一步上不退不出；或挂起最终被外层杀掉，退出码是杀进程工具自己的 124，上层不知道发生了什么类别的事。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-011-timeout-deadline`
- **判据**：`fast task: rc=0 kind=completed`；`hung task: rc=3 kind=timeout`；`deadline enforced: true`。
- **修复**：有挂起风险的调用套 `timeout`，在边界把 124 翻译成脚本自己的超时类别码（§2.9 翻译表的一行），让上层拿到可分流的语义。

### 2.12 失败聚合（E-012-error-aggregate）

- **典型现象**：`set -e` 让首个失败即停，后面项根本没跑，一批 100 项要跑 100 轮；反过来 `|| true` 跑完全部又把失败全吞。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-012-error-aggregate`
- **判据**：逐项 `item=alpha status=ok` / `item=beta status=failed rc=3`；gamma 失败后 delta 照常执行；`aggregate failed=2 passed=2`、`batch exit: 1`、`failed list: beta(rc=3) gamma(rc=2)`。
- **修复**：聚合器模式——逐项记录结果、失败后继续、末行汇总与整体退出码、附完整失败清单，一次跑完一次修完。

### 2.13 失败可观测性（E-013-error-observability）

- **典型现象**：日志是自由文本，无法按 step/status/rc 聚合，「本周下载失败多少次、都是什么类别」答不出来；或诊断打满 stdout，下游把日志当数据处理。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-013-error-observability`
- **判据**：一行业务汇总 `deploy result: ok=3 failed=1` + 4 条 `step=... status=... rc=... reason=...` 结构化记录，失败行带码与原因类别（如 `step=download status=failed rc=3 reason=network`）。
- **修复**：每步产出结构化记录（成功失败都记，走 stderr），stdout 只留业务汇总；字段名固定，便于聚合。

### 2.14 前置校验快速失败（E-014-fail-fast）

- **典型现象**：缺一个必配项本应 0 秒被拦下，却盲跑到第 5 步才失败——文件写了、服务重启了，现场被污染、报错只说第 5 步失败。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-014-fail-fast`
- **判据**：`mode=fail-fast missing-env: rc=2 work_done=0`（指名缺失项，副作用为零）；env-ok 场景 `rc=0 work_done=1`；盲跑对照 `mode=blind: rc=3 work_done=0 (no validation at all)`。
- **修复**：脚本开工前一次性校验全部前置条件（环境变量、工具、路径），缺哪项指名哪项、以类别码退出；副作用只在全部通过后开始。

### 2.15 反模式对照（E-015-antipattern-compare）

- **典型现象**：四种坑——失败被 `|| true` / 无判定的 if 洗成成功；未加引号的带空格路径被分词；管道中间命令失败被吞（无 pipefail）；诊断信息混进管道数据。共性：**脚本还在跑、退出码还是 0**。
- **排查命令**：`TAG=latest scripts/run-example.sh shell E-015-antipattern-compare`
- **判据**：四组对照行，bad 侧即坏写法的真实现象：`antipattern=swallow-error bad=exit0 good=exit1`、`antipattern=unquoted-split bad=words=2 good=words=1`、`antipattern=pipe-middle-fail bad=exit0 good=exit1`、`antipattern=error-on-stdout bad=pipeline-lines=1 good=pipeline-lines=0`。
- **修复**：吞错处改为显式分类处理；变量引用加引号；`set -o pipefail` 让管道中段失败可见；诊断一律走 stderr，不污染管道数据。
