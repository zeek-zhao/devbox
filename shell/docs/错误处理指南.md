# Shell 错误处理指南（G1 · 操作指南）

> 本文只有一个主要承诺：**按本仓库口径，把一段 bash 的错误处理写对**的操作步骤。
> 每一步落到具体用例 ID，命令契约统一为 `TAG=latest scripts/run-example.sh shell <ID>`
> （见 [工程参考](工程参考.md) §5）。症状 → 命令 → 判据 → 修复的排查动作在
> [排查手册](排查手册.md)，本文不复述。语法基础归 [知识点清单](知识点清单.md) §2。

## 1. 适用边界（什么时候用 / 什么时候别用）

**用**：你在 `shell/examples/` 下写用例、或写带失败路径的部署/校验脚本，
需要决定「失败怎么表达、怎么传播、怎么报告」。本仓库口径：bash + std 工具
（grep/diff/timeout），lint 门禁按 `images/versions.env` 的 `${SHELLCHECK_SEVERITY}`
（warning）判红；不引入任何错误处理框架——shell 没有，靠约定。

**别用**：bash 语法学习（`set -e`/`trap` 基础归 [知识点清单](知识点清单.md) §2，
用例 `L1-004-set-e` 等）；正在排查一个已发生的故障时直接去
[排查手册](排查手册.md) 按症状查。

## 2. 最小动线：分类 → 创建 → 匹配 → 包装 → 传播 → 容错 → 观测

### 2.1 先建「码 → 类别」体系

操作：给脚本定义少量固定退出码并声明类别（usage=2、environment=3/4、internal=5
这类「码即类别」的约定表），失败一律以类别码上传，禁止裸 `exit 1` 满天飞——
否则每个调用点都在猜这个 1 是什么意思。演练：`E-001-error-taxonomy`
（判据 `taxonomy codes=5 usage=1 environment=2 internal=1`）。决策表在
[排查手册](排查手册.md) §2.1。

### 2.2 创建：一行标准化诊断 + 类别码

操作：错误发生时打一条 `script名: 函数名: 消息` 格式的诊断（走 stderr），
`return` 类别码；成功路径不产诊断行。禁止随手 `echo` 诊断混进 stdout、
禁止失败后忘写 `return` 退回 0。演练：`E-002-error-create`
（判据 `main.sh: validate-name: name is empty` + `rc=2`）。

### 2.3 匹配：按码分支，翻译工具码边界

操作分两处：

1. 探测类调用（文件在不在、配置有没有）按码三分支：命中 → 用结果；未命中 →
   走默认；其他码 → 探测本身损坏，停下。禁止 `if ! cmd` 一刀切。
   演练：`E-003-error-match`（判据 `rc=2 classified=probe-broken action=stop`）。
2. 外部工具退出码不是你的语义：在边界处把 `grep 0/1/2`、`diff 0/1` 翻译成
   kind（match/no-match/tool-broken…）+ action（use-result/use-default/stop…）。
   演练：`E-009-tool-code-boundary`（判据 `tool=diff raw=1 kind=differ action=write`）。
   选型规则见 [排查手册](排查手册.md) §2.3/§2.9。

### 2.4 包装：保码 + 附上下文

操作：底层失败往上传时，退出码原样保留（`return $rc`），同时把「本层在做什么」
拼进上下文链（`deploy: download: fetch: connection refused (rc=7)`）；
诊断原文随 stderr 走，包装层不重写不吞。三层铁律：不换码、不吞码、不改写消息。
演练：`E-004-error-wrap`（判据 `preserved exit code: 22`）、
`E-005-error-identity`（判据 `transparent chain: identity preserved`）、
`E-006-error-context`（判据 `chain layers: 3`）。规范见
[排查手册](排查手册.md) §2.4/§2.5/§2.6。

### 2.5 传播：记录≠处理，清理不顶替

操作两件套：

1. 记录后必须重抛：中间层可以写日志，但日志写完要 `return $rc` / `exit $rc`
   把原码传上去；`记录 + return 0` 是假成功（监控全绿、业务没发生）。
   演练：`E-008-error-reraise`（判据 `mode=reraise ... exit=4`）。
2. 清理保证：`trap` 收尾清理的失败不得顶替业务退出码——先保存业务码，
   清理后按业务码退出。演练：`E-007-cleanup-guarantee`
   （判据 `right-mode: business exit preserved: 3`）。口径见
   [排查手册](排查手册.md) §2.7/§2.8。

### 2.6 容错：重试 / 超时 / 聚合

操作：

1. 重试：错误先分可重试/不可重试；可重试按指数退避（10ms、20ms…）加预算上限；
   不可重试首次即停。演练：`E-010-retry-backoff`（判据 `retry give-up: attempts=4 waited=70ms`）。
2. 超时：挂起风险调用套 `timeout`，把工具码 124 翻译成脚本自己的超时类别码。
   演练：`E-011-timeout-deadline`（判据 `hung task: rc=3 kind=timeout`）。
3. 批量：失败聚合——逐项记录、失败后继续跑完、末行汇总 `failed=N` 与整体退出码、
   附完整失败清单；禁止 `set -e` 首败即停逼出 100 轮重跑，也禁止 `|| true` 全吞。
   演练：`E-012-error-aggregate`（判据 `failed list: beta(rc=3) gamma(rc=2)`）。

参数与选型口径见 [排查手册](排查手册.md) §2.10/§2.11/§2.12。

### 2.7 观测与治理：结构化记录 + fail-fast + 反模式自查

操作：每步写结构化记录（`step=/status=/rc=/reason=`，成功失败都记，走 stderr），
业务汇总走 stdout；脚本开头做前置校验（0 成本拦下缺配置，副作用计数为零）；
提交前对照四大反模式自查：吞错、未加引号分词、管道中段吞错、诊断混进管道数据——
共性是脚本还在跑、退出码还是 0。演练：`E-013-error-observability`
（判据 `step=download status=failed rc=3 reason=network`）、
`E-014-fail-fast`（判据 `mode=fail-fast missing-env: rc=2 work_done=0`）、
`E-015-antipattern-compare`（判据 `antipattern=pipe-middle-fail bad=exit0 good=exit1`）。
治理清单与反模式识别见 [排查手册](排查手册.md) §2.13/§2.14/§2.15。

## 3. 惯用法与反模式对照表

| 场景 | 惯用法（本仓库口径） | 反模式（可复现后果） |
|---|---|---|
| 错误上报 | 类别码 + `script: fn: msg` 一行 stderr 诊断 | 裸 `exit 1`；`echo` 诊断混 stdout（`E-002`） |
| 探测分支 | 按码三分支（命中/未命中/损坏） | `if ! cmd` 一刀切（`E-003`） |
| 包装 | 保码 + 上下文链，原文随 stderr | `return 1` 换码丢类别；`\|\| return 0` 吞码（`E-004/E-005`） |
| 中间层 | 记录后重抛原码 | 记录后 `return 0` 假成功（`E-008`） |
| 收尾 | 保存业务码，清理后按业务码退出 | 清理失败顶替业务码 / 清理后 `exit 0`（`E-007`） |
| 批量 | 聚合 + 失败清单 + 整体退出码 | `set -e` 首败即停或 `\|\| true` 全吞（`E-012`） |
| 管道 | `set -o pipefail`，诊断走 stderr | 管道中段失败被吞、诊断污染数据（`E-015`） |

## 4. 真实工作中的变体

- **码表随团队约定**：本仓库用 usage=2/environment=3/4/internal=5 的教学码表；
  真实项目常沿用 BSD sysexits.h。码值可不同，「码即类别、全脚本唯一」的纪律不变。
- **重试参数配置化**：`E-010` 把退避写死在演示里；真实工程由环境变量/配置下发，
  本仓库环境变量口径见 [工程参考](工程参考.md) §5，不引入配置框架。
- **进程级熔断/探活**：需要真实流量与 SLO，容器内演示不了，属
  [知识点清单](知识点清单.md)「明确不覆盖」范围。

## 5. 评审清单（review 时逐条问）

1. 退出码有码表吗？每个失败点返回的是类别码还是裸 1？
2. 诊断行格式统一（`script: fn: msg`）且走 stderr 吗？
3. 探测调用按码分了三分支吗？工具码在边界翻译了吗？
4. 包装层保码了吗？上下文链能从顶层一句话拼到底吗？
5. 有没有「记录后 return 0」？清理会顶替业务退出码吗？
6. 批量路径聚合了吗？失败清单和整体退出码都有吗？
7. `shellcheck -S warning`（`${SHELLCHECK_SEVERITY}` 口径）过了吗？
