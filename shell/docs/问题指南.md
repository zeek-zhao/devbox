## quoting 与 word splitting（未加引号的路径炸分词）

> 来源：类型 ②——可复现实验（下文输出为 `devbox-shell:latest` 容器实测）；
> 知识点 `KP-SH-L1-03`（用例 `L1-003-quoting-word-splitting`）、`KP-SH-L1-05`
> （`IFS`，用例 `L1-005-ifs-field-splitting`）、`KP-SH-L2-12`（NUL 安全传路径，
> 用例 `L2-012-null-delimited-paths`）。

### 典型现象

- 明明存在的文件，命令却说没有——实测路径 `/tmp/my dir/file.txt` 裸展开后
  `cat` 报两行错误：`cat: /tmp/my: No such file or directory`、
  `cat: dir/file.txt: No such file or directory`（路径在空格处被拆成两个参数）；
- 参数个数「莫名翻倍」：实测 `set -- $f` 得到 2 个位置参数，`set -- "$f"` 得到 1 个；
- 循环/`xargs` 处理文件列表时，含空格的文件名被拆成多条；
- 展开结果为空时裸展开「消失」，多出/缺少参数导致下游命令行为漂移。

### 先做的三个检查

1. 找裸展开：`grep -nE '(^|[^"'"'"'])\$[A-Za-z_{(|]' your_script.sh | grep -v '"'`
   ——重点是命令参数位置的 `$var` 与 `$(cmd)`；
2. 数参数：`set -- $f; echo $#` 对比 `set -- "$f"; echo $#`，个数不一致即分词实锤；
3. 用 shellcheck 过一遍：`shellcheck -s bash your_script.sh`——
   `SC2086`（Double quote to prevent globbing and word splitting）就是这类问题
   （实测输出见下「定位命令」）。

### 定位命令 / 工具

```bash
shellcheck -s bash your_script.sh                        # SC2086 / SC2046 / SC2089 都是分词族
shellcheck -s bash -S style your_script.sh               # 连 info 级也报（门禁默认会吞掉它们，见下）
TAG=latest scripts/run-example.sh shell L1-003-quoting-word-splitting   # 对照用例：两种写法同框验收
TAG=latest scripts/run-example.sh shell L2-012-null-delimited-paths     # 含空格/换行路径的安全传法
```

注意门禁盲区（实测）：`SC2086` 是 **info** 级，而仓库门禁阈值是
`images/versions.env` 的 `${SHELLCHECK_SEVERITY}`（warning）——实测
`shellcheck -s bash -S warning` 对含 `cat $f` 的脚本返回 0（不报）、
`-S style` 才返回 1。门禁绿 ≠ 没有分词隐患（素材池 `S-07` 同型）。
工具细节见 [工具指南.md](工具指南.md)。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 路径在空格处断开 | 未加引号的展开经历词分裂 | `set -- $f` 数参数（实测 2）对比 `set -- "$f"`（实测 1）；实测 `cat $f` 报 `cat: /tmp/my: No such file or directory` |
| 循环处理列表漏项/多项 | `for x in $(ls)`、`find | xargs` 按空白切 | 换 `find -print0 | xargs -0` 或 `while IFS= read -r -d ''`（用例 `L2-012-null-delimited-paths`） |
| `IFS` 改过后行为怪异 | 未引用展开 + 自定义 `IFS` 叠加分词 | 用例 `L1-005-ifs-field-splitting`；恢复默认 IFS 再对照 |
| 参数转发后边界丢失 | 用 `$*` 转发位置参数 | 改 `"$@"`（用例 `L1-019-array-at-star` 的验收点） |
| 空变量导致参数消失 | 未加引号 + `-u` 未开，空展开直接蒸发 | `set -u` + 引号双保险；`echo "[$v]"` 看边界 |

### 修复与预防

修复：所有展开加双引号——`"$f"`、`"$(cmd)"`、`"$@"`；遍历文件名改 NUL 安全
写法（`find -print0` + `xargs -0` / `read -d ''`）；列表数据用数组而不是字符串
再切分。实测修复后 `cat "$f"` 原样输出 `hello`、`set -- "$f"` 参数数为 1。

预防：脚本头 `set -euo pipefail`（用例 `L1-030-strict-mode` 的骨架）；本地自查
用 `shellcheck -s bash -S style`（比门禁阈值严，能抓 info 级 `SC2086`）；
评审时把「裸 `$` 展开」列为必查项——不能指望 warning 级门禁替你抓。

**反例（可执行）**

- 错误做法：`cat $f`（少一对引号）。
- 复现命令（实测，`devbox-shell:latest` 容器内原样输出）：

  ```bash
  docker run --rm "ghcr.io/zeek-zhao/devbox-shell:${TAG:-latest}" bash -c '
  mkdir -p "/tmp/my dir"; echo hello > "/tmp/my dir/file.txt"
  f="/tmp/my dir/file.txt"
  cat $f; echo rc=$?
  set -- $f; echo "unquoted args=$#"'
  ```

  实测输出：

  ```text
  cat: /tmp/my: No such file or directory
  cat: dir/file.txt: No such file or directory
  rc=1
  unquoted args=2
  ```

- 后果：一个路径变两个不存在的参数，命令以 1 退出；在批量删除/移动脚本里，
  同样的分词会让 `rm` 收到拆散的路径——错误类型从「读不到」升级成「删错东西」。

## `set -euo pipefail` 陷阱（管道吞错与条件上下文失效）

> 来源：类型 ②——可复现实验（`devbox-shell:latest` 容器实测，四组输出原样
> 记录，见下）；类型 ①——素材池 `S-07`（CI 全绿 ≠ 对：中间失败被吞、退出码
> 仍为 0 的「假绿」，与该已知限制同型）；知识点 `KP-SH-L1-21`
> （`L1-021-pipeline-pipefail`）、`KP-SH-L1-23`（`L1-023-functions-local-return`）、
> `KP-SH-L1-30`（`L1-030-strict-mode`）。

### 典型现象

- 「我明明 set -e 了，失败了怎么没停」——管道中间命令失败被吞：实测
  `set -e; false | true; echo survived` 照样打印 `survived-middle-failure`、
  整体退出码 0（bash 默认取管道最后一个命令的状态）；
- 加了 `pipefail` 反而「脚本全红」：实测 `set -euo pipefail; false | true`
  以 1 退出——不是脚本变脆了，是原本被吞的失败现形了；
- 函数在 `if`/`&&`/`||` 里调用时，函数内部的 `set -e` 整段失效：实测
  `f() { false; echo reached-after-false; }; if f; then ...` 输出
  `reached-after-false` 和 `branch-ok`——`false` 后面的代码照样执行；
- `local out=$(cmd)` 吞掉命令替换的失败：实测 `f2() { local out=$(false); ... }`
  脚本继续执行到结尾、退出码 0。

### 先做的三个检查

1. 脚本头三件套齐不齐：`head -5 your_script.sh | grep 'set'`——
   是 `set -euo pipefail` 还是只有 `set -e`（没有 `-o pipefail` 就会吞管道错）；
2. 失败的命令是不是在管道中间、条件上下文或 `local` 赋值里——这三处
   errexit 天然失效或被覆盖；
3. 单独复跑那一条管道/函数，看退出码：
   `bash -c 'set -o pipefail; <你的管道>; echo $?'`。

### 定位命令 / 工具

```bash
grep -n 'set -' your_script.sh                                   # 严格模式写法核对
shellcheck -s bash your_script.sh                                # SC2312 可提示管道加 pipefail；SC2155 提示 local 覆盖退出码
bash -c 'set -o pipefail; false | true; echo $?; '               # 管道真实状态复现（实测 1）
TAG=latest scripts/run-example.sh shell L1-021-pipeline-pipefail # 对照用例：管道状态两种口径同框
TAG=latest scripts/run-example.sh shell L1-030-strict-mode       # 对照用例：严格模式边界
TAG=latest scripts/run-example.sh shell L1-023-functions-local-return   # 对照用例：函数与 local
```

工具细节见 [工具指南.md](工具指南.md)；清理/防漏的兜底写法见
`L1-029-trap-mktemp`（trap 是 errexit 失效场景下的最后防线）。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 管道失败脚本不停 | 没开 `pipefail`，bash 默认取最后一个命令的状态 | 实测 `set -e; false | true` → 打印 survived、rc=0；开 `set -euo pipefail` 后同管道 rc=1 |
| 加 `pipefail` 后「全红」 | 原本被吞的中间失败现形 | 逐条管道单独复跑，找到真凶命令 |
| 函数里 `set -e` 失效 | 函数在 `if`/`&&`/`||` 中调用，进入条件上下文 | 实测 `if f` 时 `false` 后代码照跑；把函数移出条件上下文单独调用再对比 |
| `cmd` 失败但脚本继续 | `local out=$(cmd)` 用 `local` 的状态覆盖了命令替换的状态 | 实测 `local out=$(false)` 不退出；拆成两行 `local out; out=$(cmd)` 后立刻退出 |
| 显式允许失败的地方没豁免 | 严格模式下「预期失败」没写 `|| true` / `if` | 检查该行是否有显式处理；用例 `L1-030-strict-mode` 的条件分支写法 |

### 修复与预防

修复：管道要中间状态就开 `set -o pipefail`（或脚本头直接 `set -euo pipefail`）；
预期失败的命令显式写 `|| true` 或放进 `if`；函数体内对「允许失败」的命令同样
显式豁免，不要依赖 errexit 兜底；`local` 与命令替换拆成两行，让失败如实上抛。
预防：新脚本从 `L2-001-script-skeleton-usage` 的骨架起步（自带严格模式）；
评审把「管道中间命令」「条件上下文中的函数」「`local x=$(...)`」列为必查三项；
对「退出码 0 但行为不对」的假绿保持警惕——它与素材池 `S-07` 的教训同源：
绿只是判据执行了，不保证判据覆盖了你要的那件事。

**反例（可执行）**

- 错误做法：只写 `set -e`，管道中间命令失败指望脚本停下。
- 复现命令（实测，`devbox-shell:latest` 容器内原样输出）：

  ```bash
  docker run --rm "ghcr.io/zeek-zhao/devbox-shell:${TAG:-latest}" bash -c '
  bash -c "set -e; false | true; echo survived-middle-failure"; echo rc=$?
  bash -c "set -euo pipefail; false | true; echo survived-middle-failure"; echo rc=$?'
  ```

  实测输出：

  ```text
  survived-middle-failure
  rc=0
  rc=1
  ```

- 后果：发布/巡检脚本里，管道中间的校验命令失败被吞、脚本以 0 退出，
  CI 与告警全绿——失败被静默推进到下游。开 `pipefail` 后同一管道以 1 退出
  （第二行实测），失败第一次就现形。
