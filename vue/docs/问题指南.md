## 响应性陷阱（解构丢响应 / 依赖不更新）

> 来源：类型 ②——可复现实验（下文解构丢响应为 `devbox-vue:latest` 容器实测，
> 输出原样记录）；类型 ①——素材池 `S-07` 作旁证（「跑通了」不等于「教对了」：
> 响应性 bug 往往首帧渲染完全正常，只有更新传播断了才暴露，机器判据抓不到，
> 要靠断言更新的传播）；`S-01`/`S-06`（用例失败先排除镜像/环境故障）。

### 典型现象

- **界面某处不再更新，但无任何报错**——典型成因是解构 reactive/props 后用了
  解构值。实测对照（完整代码见 [实践指南.md](实践指南.md) §3 反例）：

  ```
  props.count=1 traced=1 destructured=0
  ```

  源头已更新（`props.count=1`）、正常跟踪的 effect 拿到新值（`traced=1`），
  解构出的原始值停在旧值（`destructured=0`），退出码还是 0——**静默失效**；
- 整体替换 reactive 对象后视图失联：`state = newObj` 断开了原 Proxy 的引用，
  旧订阅者还在盯旧对象；
- 传给子组件的 props 偶发不同步——父组件中途用了本地解构副本传参；
- 依赖没被收集：effect/watch 回调里只读了「当次快照值」而不是响应式属性
  （`L3-016-track-trigger-debug` 可直接观察 track/trigger）；
- 对 ref 忘写 `.value`（模板里会自动解包，JS 里不会）——读到 ref 对象本身。

### 先做的三个检查

1. 更新有没有真的发生：在源头属性上挂一个最小 `effect`，打印读数——
   源头都更新不了是数据问题；源头更新了而下游不更新才是响应链断了；
2. 找「断点」在哪一跳：从源头到视图逐跳核对，每跳拿到的**是不是响应式
   引用本身**（ref 对象/Proxy），还是被解构/展开成了原始值快照；
3. 通路与环境先排除：`TAG=latest scripts/run-example.sh vue L0-hello` 先绿，
   CI 与本地 `TAG`/`IMAGE_TAG` 值一致（`S-01`：两名不一致曾让 6 个用例 job
   全红而本地假绿）。

### 定位命令 / 工具

```bash

TAG=latest scripts/run-example.sh vue L3-016-track-trigger-debug

  "ghcr.io/zeek-zhao/devbox-vue:${TAG:-latest}" node props.js
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 更新后部分视图停旧值、无报错 | 解构 props/reactive 出原始值（实测见反例） | `toRefs` 后对照；或去掉解构直接 `props.x` 访问复测 |
| 整个对象换掉后视图失联 | `state = ...` 整体替换断开 Proxy | 改为替换属性或 `Object.assign`；ref 包对象后换 `.value` |
| watch/effect 不触发 | 回调里读的是快照值，依赖没被 track | `L3-016-track-trigger-debug`：确认 track 发生在读取响应式属性时 |
| 传给子组件不同步 | 父组件用本地解构副本作 props 源 | 沿数据流逐跳检查传的是引用还是快照 |
| JS 里拿到的是对象不是值 | 模板自动解包 vs JS 手动 `.value` 混淆 | 在 JS 上下文显式 `.value` |
| 大列表更新卡顿 | 深度代理整棵大对象 | `L3-014-shallow-markraw`：shallowRef/markRaw 收窄追踪范围 |

### 修复与预防

修复：恢复响应链——props 用 `toRefs(props)` 解构（`L1-026-to-refs-props`），
reactive 对象永不整体替换（换 `.value` 或改属性），跨边界一律传 ref/Proxy
引用而不是快照。
预防落成可执行判据：

- 响应式代码必须带「更新会传播」的断言（先改源头，再断言下游新值）——只断言
  首帧的用例抓不住这类 bug（`S-07`：跑通了不等于教对了）；
- lint/评审把「解构 props」「整体替换 reactive」列为点名项，出现必须写明理由；
- 大对象/第三方实例默认 shallow/markRaw（`L3-014-shallow-markraw`），除非确实
  需要深度追踪。

**反例（可执行）：解构 props 丢失响应性（实测）**

- 错误做法与复现命令：见 [实践指南.md](实践指南.md) §3 反例（同一实验，
  不重复贴码）——`node props.js` 退出码 0，输出
  `props.count=1 traced=1 destructured=0`。
- 后果：静默失效。它是 Vue 侧最危险的故障形态：没有 panic、没有编译错、
  首帧渲染完全正常，发现问题往往要等用户报「界面不刷新」。
  把解构换成 `const { count } = toRefs(props)` 再跑同一断言即
  `destructured=1`（`L1-026-to-refs-props` 的核心考点）。

## 构建与产物（env 内联 / 产物可复现检查）

> 来源：类型 ②——可复现实验（下文「未声明 env 变量内联为 undefined」为
> `devbox-vue:latest` 容器实测，vite prod 构建，构建输出与产物原文原样记录）；
> 类型 ①——素材池 `S-02`/`KI-08`（可变引用导致结果漂移，构建产物同理）、
> `S-07`（CI 全绿 ≠ 产物正确：构建成功不证明产物里的值是对的）；
> docs/20-开发发布增强.md Vue 行（构建产物与部署路径）。

### 典型现象

- **构建成功、退出码 0，但产物里未声明的 env 变量被静默内联为 `undefined`**
  （实测，完整输出见反例）——构建日志没有任何 warning，值错在产物里，
  运行时才表现为「配置丢了」；
- 同一源码两次构建产物不同：env 是构建期注入的（`VITE_DECLARED=...`），
  漏传一次，产物行为就变——且 diff 只能从 bundle 文本看出来；
- dev 正常、prod 白屏/行为异常：dev 模式 `import.meta.env` 是活对象，
  prod 里被静态替换，`DEV` 分支、运行时编译器有无（`L2-018-runtime-compiler`）
  都是构建期差异；
- CI 绿但产物错（`S-07` 同型）：用例只验证「构建能过」，没验证「产物内容
  对不对」——产物检查要单独做。

### 先做的三个检查

1. env 变量是否真的传到了构建进程：构建命令行上有没有显式
   `VITE_XXX=...`（CI 与本地各打一次，两个环境最常见差异就在这里）；
2. 产物里到底内联了什么：对 `dist/assets/*.js` 做文本检查——找变量值字面量
   或 `void 0`（实测见反例），不要猜；
3. 通路与环境先排除：`TAG=latest scripts/run-example.sh vue L0-hello` 先绿，
   镜像 tag 固定（`S-01`/`S-06`）。

### 定位命令 / 工具

```bash
# 产物内容检查：内联值直接 grep（本节实测即此形态）
grep -o "declared = [^;]*" dist/assets/*.js    # 应看到 "hello"
grep -o "missing  = [^;]*" dist/assets/*.js    # 未声明变量 → void 0

# env 配置的轨道内基准
TAG=latest scripts/run-example.sh vue L2-007-env-config

# 运行时编译器有无（dev/prod 构建差异的另一个经典点）
TAG=latest scripts/run-example.sh vue L2-018-runtime-compiler
```

产物分析与部署路径细节见 [工具指南.md](工具指南.md) 与 [开发指南.md](开发指南.md)。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 产物里配置值是 `undefined` | 变量名未加 `VITE_` 前缀 / 构建时未传 / 拼错（实测：`VITE_MISSING` → `void 0`） | 反例复现；grep 产物对照构建命令 |
| 两次构建产物行为不同 | env 构建期注入，两次输入不同（`S-02` 同型：引用了可变输入） | 记录构建命令；diff 两次产物文本 |
| dev 正常 prod 异常 | dev 是活对象、prod 是静态替换；或 runtime compiler 未打入 | `L2-018-runtime-compiler`；`grep -c "createApp"` 看编译器是否在产物里 |
| CI 绿但产物错 | 判据只覆盖「构建成功」（`S-07`） | 增加产物内容断言（见修复与预防） |
| 产物体积异常膨胀 | 非生产构建混入（未设 NODE_ENV / dev 依赖被打包） | 检查 build 命令与 `process.env.NODE_ENV` 注入 |

### 修复与预防

修复：把变量名补上 `VITE_` 前缀并在构建命令/CI 里显式传入；env 读取集中到
一个配置模块（`L2-007-env-config` 的模式），未声明的读取一眼可见。
预防落成可执行判据：

- prod 构建后跑**产物内容断言**：对关键配置项 grep 产物（本节定位命令即最小
  实现），断言失败即红——把「产物对不对」变成机器判据，而不是只看构建成功
  （`S-07` 的教训）；
- 构建命令进版本库（脚本/CI），env 显式传递；需要复现历史产物时固定镜像
  `TAG=sha-<commit-sha>`（`KI-08`）；
- dev/prod 差异点（env 静态替换、运行时编译器、NODE_ENV）逐项列清单，
  发布前过一遍（docs/20 Vue 行）。

**反例（可执行）：未声明的 env 变量在 prod 产物内联为 undefined（实测）**

- 构造：vite prod 构建一个小应用，`src/main.js` 打印两个 env——声明并传入的
  `VITE_DECLARED` 与未声明的 `VITE_MISSING`；构建命令只传前者。
- 复现命令（实测；构建输出 `✓ built in 92ms`，退出码 0）：

  ```bash
  docker run --rm -v /tmp/vueexp:/exp -w /exp/envapp \
    "ghcr.io/zeek-zhao/devbox-vue:${TAG:-latest}" \
    bash -c 'npm i -s vite@^7 && VITE_DECLARED=hello npx vite build && cat dist/assets/*.js'
  ```

- 后果（产物 `dist/assets/index-*.js` 原文，实测）：

  ```js
  console.log("declared =","hello");console.log("missing  =",void 0);
  ```

  构建零告警地成功：声明并传入的变量内联为字面量 `"hello"`，未声明的变量
  内联为 `void 0`（undefined）——错误在产物里，构建过程一声不吭。
  补上 `VITE_MISSING=...` 重新构建，同一 grep 即见真值，这就是「产物内容
  断言」的检查点。
