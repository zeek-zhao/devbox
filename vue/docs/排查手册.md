# Vue 排查手册（troubleshooting）

> 按「症状 → 排查命令 → 判据 → 修复」组织的手册。§2 是错误处理章，含
> §2.1–§2.15 共 15 节，逐节对应 `vue/examples/E-001..E-015`（各例 README 的
> `coverage: exempt` 注释指向本手册 §2 的对应节）。
> §3、§4 是路由章：响应性陷阱与构建产物问题的入口指向既有指南与 lab。
> 全部排查命令已于 2026-11-11 在 `devbox-vue:latest` 内真跑核对（15/15 PASS）；
> 写法纪律见 [docs/72-排障演练规范](../../docs/72-排障演练规范.md)（现象禁止编造，
> 只许来自真跑或已登记问题）。

## 1. 使用方法

1. 先在本手册按症状定位到节；每节给一条可直接执行/粘贴的排查命令与判据输出。
2. 判据不成立 → 按该节「修复」处理；判据成立但问题仍在 → 走该节给出的关联文档。
3. 「怎么写对」的设计问题走 [错误处理指南](错误处理指南.md)；镜像、版本、环境变量
   事实走 [工程参考](工程参考.md)。

## 2. 错误处理章（对应 E-001..E-015）

### 2.1 控制台一片红，不知道错误来自哪一层（E-001-error-taxonomy）

- 症状：「Vue 报错了」被当成一种错误处理：setup 抛错、render 函数抛错、
  异步 setup 的 Promise 拒绝混在一起猜。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-001-error-taxonomy`
- 判据：三行 `source=... error=... info=...`（setup / render / async 各归
  官方 `info` 位置类别），末行 `taxonomy sync=2 async=1 captured=3`。
- 修复：统一汇入口 `app.config.errorHandler`，分类挂在 `info` 字段上而不是
  解析消息文本；返回 false 停止默认告警，让分类成为唯一出口。详见
  E-001 README。

### 2.2 只有一句 invalid，不知道错在哪个字段（E-002-error-create）

- 症状：校验失败 `throw new Error('invalid')`：不知道该重试还是该改输入，
  日志里无法按错误类型聚合。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-002-error-create`
- 判据：`error=ValidationError code=E_REQUIRED field=name message=name is
  required`（及 E_RANGE/age），末行 `metadata fields=3 (code, field, message)`。
- 修复：领域错误类型（ValidationError）+ `code / field / message` 三元组：
  `code` 供上层分派（§2.3）、`field` 供表单定位控件、`name`/`instanceof`
  供身份匹配（§2.5）。详见 E-002 README。

### 2.3 catch 里解析消息文本，文案一改全失灵（E-003-error-match）

- 症状：`if (err.message.includes('network'))` 一坨 if/else：网络抖动被当
  成表单输入错误「修复」，输入错误被拿去重试。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-003-error-match`
- 判据：四行 `matched=... action=...`（E_NETWORK→retry、E_REQUIRED /
  E_RANGE→fix-input），未知错误落保守分支 `matched=plain-error action=report`。
- 修复：匹配对象是「身份」：`instanceof AppError` 分类型、`error.code` 分
  分支；分派表允许「不认识」（report），不允许「猜」。详见 E-003 README。

### 2.4 UI 只见 Unexpected token，不知哪个组件在加载什么（E-004-error-wrap）

- 症状：底层错误直接抛给上层，或全包成一句「加载失败」丢了根因——两层
  事故，同一个根因：包装时没带上原文。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-004-error-wrap`
- 判据：`wrapped=component Page: load card failed`、
  `cause level1=component Card: parse payload failed`、
  `cause level2=SyntaxError`、`cause is SyntaxError=true`、`chain depth=3`。
- 修复：包装 = 新错误带自己的上下文（哪个组件、在干什么）+ 原错误挂
  `cause`（ES2022 Error cause，不需要自定义包装类）。详见 E-004 README。

### 2.5 上游的类型分派全部落空（E-005-error-identity）

- 症状：composable 抛出的 ServiceError 被中间层 `new Error(err.message)`
  换成「长得像」的新 Error：instanceof 打断、code 抹掉、上报里出现两条
  「不同」的失败。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-005-error-identity`
- 判据：`identity through chain: same=true`、`code survives chain: E_DB_DOWN`；
  重包反例 `identity after rewrap: same=false`、`instanceof after rewrap: false`。
- 修复：中间层的职责是透传——不 catch、不重包、不改写，同一引用一路到底；
  需要加上下文时用 cause 包装（§2.4）而不是文本复制。详见 E-005 README。

### 2.6 同一句报错在页面上有五处来源（E-006-error-context）

- 症状：深层嵌套组件里 leaf 抛错，app 级 errorHandler 只收到一句
  leaf boom，不知道它经过了哪条组件链。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-006-error-context`
- 判据：`message=leaf boom`、`context path=Root > Mid > Leaf`、
  `path depth=3`。
- 修复：每层 `onErrorCaptured` 只做两件事：名字前置进 `err.context`、
  `return undefined` 放行；标注写在错误对象同一引用上，链不破坏类型。
  详见 E-006 README。

### 2.7 过期响应覆盖新结果 / 销毁后定时器还在跑（E-007-cleanup-guarantee）

- 症状：composable 里 watchEffect/订阅只注册不注销：查询条件变了旧响应
  回来覆盖新结果，组件销毁后定时器还在跑——前端内存泄漏与状态污染的
  头号来源。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-007-cleanup-guarantee`
- 判据：`runs=2 cleanups=1 (invalidation cleanup ran)`、
  `scope stopped: runs=2 cleanups=2`，末两行
  `cleanup on invalidation: true`、`cleanup on stop: true`。
- 修复：`watchEffect(onCleanup => ...)` 把清理注册和副作用注册写在同一处，
  两条清理路径（重新执行前、scope 停止时）框架保证都会调用；`effectScope.stop()`
  等价于组件卸载的聚合开关。详见 E-007 README。

### 2.8 app 级监控完全失明（E-008-error-reraise）

- 症状：中间层 `onErrorCaptured` 里「看了一眼就 return false」：错误从此
  消失——「处理过」和「吞掉」只差一个返回值。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-008-error-reraise`
- 判据：三行对照 `mode=swallow: parent-saw=true app-reports=0`（吞掉）、
  `mode=passthrough: parent-saw=true app-reports=1 first=leaf boom`、
  `mode=reraise: parent-saw=true app-reports=2 first=wrapped: leaf boom`。
- 修复：返回 false 的唯一正当理由是「这一层真的处理掉了」（降级/重试/
  兜底成功）；原样放行用 `return undefined`，错误对象原引用继续上抛。
  详见 E-008 README。

### 2.9 加了 onErrorCaptured 仍有静默失败（E-009-async-boundary）

- 症状：composable 里游离的 Promise（后台刷新、无主的 setTimeout 回调）
  不进任何 Vue 边界——漏 catch 就是 unhandledRejection。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-009-async-boundary`
- 判据：`sync render error: info=render function`、
  `async setup error: info=setup function`、
  `detached promise error: app-saw=false caught-by-catch=true`，末行
  `boundary covered=3 of 3 with explicit catch`。
- 修复：边界的能力范围以实测为准——errorHandler 覆盖组件树内同步 + 异步
  setup；游离 Promise 必须在发起处显式 catch。详见 E-009 README。

### 2.10 一失败就报错页 / 重试把限流打成打挂网关（E-010-retry-backoff）

- 症状：前端加载失败两个极端：要么一失败就放弃，要么对 4xx 参数错、配额
  超限这类永远修不好的失败无脑循环重试。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-010-retry-backoff`
- 判据：`retry success: attempts=3 waited=30ms result=payload`、
  `retry non-retryable: attempts=1 waited=0ms result=E_PERM`、
  `retry give-up: attempts=4 waited=70ms result=E_TRANSIENT`。
- 修复：重试决策挂在 `err.code === 'E_TRANSIENT'` 上；有限次数 + 指数退避
  （10ms 翻倍），预算写死在 `retry(max, baseMs, fn)` 签名可见处。详见
  E-010 README。

### 2.11 loading 永远挂着（E-011-timeout-deadline）

- 症状：接口不响应时 loading 态挂着不落三态，网络故障的恢复时间由对端
  决定。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-011-timeout-deadline`
- 判据：`load fast: result=data`、`load hung: result=E_TIMEOUT after 50ms`、
  `deadline conversions=1`。
- 修复：`Promise.race([load, deadline])` 把挂起的 Promise 变成有限时间的
  失败；截止结果用显式标记（timedOut: true）而不是 reject 一个裸 Error。
  详见 E-011 README。

### 2.12 仪表盘失败清单一次只显示一个（E-012-error-aggregate）

- 症状：并行拉 3 个数据源用 `Promise.all`：第一个失败打死整页，成功的
  数据被丢弃，修好一个又撞出下一个。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-012-error-aggregate`
- 判据：三行 `source=a/b/c status=fulfilled/rejected reason=...`，
  `aggregate ok=1 failed=2`、`failed reasons=E_OFFLINE,E_QUOTA`。
- 修复：`Promise.allSettled` 不短路：每个数据源的结局都保留；失败聚合不是
  吞掉——末行汇总 + reasons 清单交给上层决定降级策略（部分数据可用时
  渲染部分页面）。详见 E-012 README。

### 2.13 哪个组件失败率最高说不出来（E-013-error-observability）

- 症状：生产错误处理只有一句 `console.error(err)`：控制台关了什么都没
  留下，最基本的分桶统计做不了。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-013-error-observability`
- 判据：两行 `report component=Card/Page message=... info=...`，末行
  `reports=2 fields=3 (component, message, info)`。
- 修复：`app.config.errorHandler` 是全应用唯一的错误汇聚点，上报逻辑只写
  一份；上报记录是结构化三元组（component 来自组件 name 选项——所以组件
  必须命名；info 是 Vue 官方位置类别）。详见 E-013 README。

### 2.14 应用照常启动，用户点第一个按钮才炸（E-014-fail-fast）

- 症状：构建产物里的环境配置没注入：失败从「构建时 0 秒拦截」退化成
  「运行时用户眼前爆炸」，报错还只是 undefined 的间接症状。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-014-fail-fast`
- 判据：`env missing: created=false code=E_ENV_REQUIRED field=DEVBOX_API_URL`、
  `env ok: created=true`、`fail-fast checks=2`。
- 修复：校验集中在 `REQUIRED_ENV_KEYS` 清单 + 一个函数里，createApp 之前
  执行——缺一个配置就不创建应用；校验错误用结构化错误（E-002），CI/部署
  日志可 grep。生产 env 内联与产物在场检查见
  [T-001 WALKTHROUGH](../labs/T-001-props-reactivity-env/WALKTHROUGH.md)。
  详见 E-014 README。

### 2.15 界面「不动了」/ 父组件状态被无声改写 / 失败无记录（E-015-antipattern-compare）

- 症状：前端三大假绿：解构 reactive 后数据在变视图不变；子组件直接改
  props 破坏单向数据流；`catch(() => {})` 吞掉 Promise 失败——没有报错、
  没有崩溃，只有错误的行为。
- 排查命令：`TAG=latest bash scripts/run-example.sh vue E-015-antipattern-compare`
- 判据：三行对照 `antipattern=destructuring bad=1 good=2`、
  `antipattern=mutate-prop bad=parent=99 good=parent-with-copy=1`、
  `antipattern=swallowed-promise bad=recorded=0 good=recorded=1`。
- 修复：需要「拆出来的响应式」用 `toRefs` / `storeToRefs`；改 props 走
  emits 回父组件（或持有副本）；Promise 发起处显式 catch 记录。三组对照
  的演练复现见
  [T-001 WALKTHROUGH](../labs/T-001-props-reactivity-env/WALKTHROUGH.md)。
  详见 E-015 README。
