# C++ 问题指南（G3）

> 按问题域组织排查路径：现象 → 假设 → 定位 → 修复 → 预防。
> 素材纪律（《知识点清单增强规范》§7.2）：本篇素材只来自
> 类型 ① 本仓库已登记的已知问题（ROADMAP `KI-*`、历史 bug `#184`、规范 §4.3 记录的事故）、
> 类型 ② 可复现实验（在本轨道镜像里实测，复现命令与真实输出随节给出）、
> 类型 ③ 文档与代码的口径不一致。每节标注来源，禁止编造现象。
> 命令契约见规范 §4.3：用例一律 `TAG=latest scripts/run-example.sh cpp <ID>`。

## 镜像与标签（用例跑不起来）

> 来源：类型 ①——ROADMAP `KI-08`（镜像标签可变）、历史 bug `#184`（并发 PR 互推
> `:latest` 互相覆盖被测镜像）、规范 §4.3 记录的「TAG 与 IMAGE_TAG 名字不一致导致
> 6 个用例 job 全红」事故；类型 ②——下文反例为实测。

### 典型现象

- runner 输出 `FAIL`，stderr 含 `docker: Error response from daemon: manifest unknown`（实测可复现）；
- 本地用例全绿，CI 的 `examples` job 全红（或反之）；
- 同一分支两次 CI 结果不同——拉到的 `:latest` 在两次运行之间被换了内容。

### 先做的三个检查

1. 本地有没有这个 tag 的镜像：`docker images | grep devbox-cpp`；
2. 命令里的 `TAG`（或 CI 的 `IMAGE_TAG`）传了没有、值是什么——runner 的取值
   顺序是 `TAG` → `IMAGE_TAG` → `local`（真本 `scripts/run-example.sh`），漏传时
   会静默落到 `local`，本地没有 `local` 标签就会拉取失败；
3. CI 侧确认镜像 job（`probe`/`images`）本身是绿的——镜像没建时 `pull` 会红，
   与「代码有问题」是两回事（docs/02-流水线.md）。

### 定位命令 / 工具

```bash
TAG=latest scripts/run-example.sh cpp L0-hello             # 通路验证，1 秒
docker pull "ghcr.io/zeek-zhao/devbox-cpp:${TAG:-latest}"  # 直接验证 tag 可解析
```

工具细节见 [工具指南.md](工具指南.md)；tag 体系的取舍见 docs/ROADMAP.md `KI-08`。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| `manifest unknown` | tag 不存在（拼错/没推过/`latest` 未发布） | 换一个必不存在的 tag 复现同类报错（见反例）；再 pull 目标 tag |
| 本地绿 CI 红 | CI 用 `IMAGE_TAG`、本地用 `TAG`，两边值不同步 | 在 CI 日志里找 `IMAGE_TAG` 的值，与本地 `TAG` 对比 |
| 结果随时间漂移 | 依赖了可变的 `:latest`（`KI-08`） | 改用 `TAG=sha-<commit-sha>` 重跑，看结果是否稳定 |
| PR 上镜像互相覆盖 | PR 曾无条件推 `:latest`（`#184`，已修：PR 只推 sha 标签） | 读该 PR 的 workflow 日志，确认只推了 sha 标签 |

### 修复与预防

修复：tag 缺失先 `docker pull` / 触发镜像构建；要复现就固定 sha 标签。
预防：所有用例命令统一走 runner 并显式 `TAG=latest scripts/run-example.sh cpp <ID>`；
文档与配置禁止硬编码 tag 字面量；需要稳定结果一律 `sha-<commit>`。

**反例（可执行）**

- 错误做法：把某个 tag 字面量写死在文档/脚本里，等它失效。
- 复现命令（实测）：

  ```bash
  TAG=nosuchtag scripts/run-example.sh cpp L0-hello
  # FAIL；stderr：docker: Error response from daemon: manifest unknown.
  ```

- 后果：以非零退出；在真实事故（`#184`）里，这种失效发生在 CI 层面，症状与
  代码 bug 无法区分，烧掉一整轮 20–25 分钟的全量流水线。

## 用例三文件契约（MISSING / NO-RUNNER）

> 来源：类型 ②——可复现实验（下文 NO-RUNNER 为实测）；runner 契约的真本是
> `scripts/run-example.sh` 头注释，本文只转述不另立口径。

### 典型现象

- runner 输出 `cpp/<ID>  MISSING(<路径>)`——目录不存在或名字拼错；
- runner 输出 `cpp/<ID>  NO-RUNNER`——目录在但 `run.sh` 缺失（实测可复现）；
- 输出 `DIFF`——`run.sh` 的 stdout 与 `expected.txt` 逐行比对失败。

### 先做的三个检查

1. 目录名与 [知识点清单.md](知识点清单.md) 的建议用例 ID 逐字符核对
   （`ls cpp/examples | grep <ID>`）；层级前缀 `L0`–`L4`、三位序号、连字符都不能错；
2. 三件套是否齐：`ls cpp/examples/<ID>/`——`run.sh`、`expected.txt`、`README.md`；
3. `run.sh` 是否只往 stdout 打业务输出——编译告警、构建日志必须重定向到 stderr
   （真本 `scripts/run-example.sh` 头注释；`L2-002-cmake-targets` 的 `run.sh` 是现成范例）。

### 定位命令 / 工具

```bash
ls cpp/examples/ | grep <ID>            # 目录在不在、名字对不对
ls cpp/examples/<ID>/                   # 三件套齐不齐
TAG=latest scripts/run-example.sh cpp L0-hello   # 对照一个健康用例的输出形态
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| `MISSING` | 目录名拼错 / 用例还没建 | `ls cpp/examples/` 对照清单 |
| `NO-RUNNER` | `run.sh` 缺失或名字不对 | 见下方反例：移走 `run.sh` 后 runner 立即报 `NO-RUNNER` |
| `DIFF` | 行为变更没同步期望文件，或 stdout 混入非业务输出 | 用 `--keep` 进容器手工跑 `run.sh`，diff 两份输出 |
| CI 独有 `DIFF` | 本地有未跟踪/未提交的文件参与运行 | 干净检出后重跑 |

### 修复与预防

修复：补齐三件套；`expected.txt` 的更新规则（逐行精确、忽略行尾空白与首尾空行）
以 [用例编写规范.md](用例编写规范.md) 为准，`--update` 仅限新写用例。
预防：新用例先对照 `L0-hello`（最简）与 `L2-002-cmake-targets`（带构建）两个范例。

**反例（可执行）**

- 错误做法：以为目录在就能跑，不建 `run.sh`。
- 复现命令（实测；做完记得还原）：

  ```bash
  mv cpp/examples/L0-hello/run.sh /tmp/L0-run.sh.bak
  TAG=latest scripts/run-example.sh cpp L0-hello   # 输出 NO-RUNNER，rc=1
  mv /tmp/L0-run.sh.bak cpp/examples/L0-hello/run.sh
  ```

- 后果：runner 以非零退出，CI 的 `examples` job 红；「每例必须有 `run.sh`」是
  CI `static` job 的检查项（docs/02-流水线.md）。

## 格式化与门禁漂移（本地绿、CI 红）

> 来源：类型 ②——可复现实验（下文 fmt-check 报差异为实测）；类型 ①——规范 §4.3
> 记录的「本地各跑各的都不报错、CI 全红」事故模式；`images/versions.env` 真本注释
> 明确 `CLANG_FORMAT_MAJOR` 必须与 `CLANG_MAJOR` 同步（格式化规则随 LLVM 版本变）。

### 典型现象

- `bash scripts/fmt.sh --check --lang cpp` 输出「cpp 有差异」，末行提示「修法：make fmt」（实测）；
- 本地 fmt 通过、CI 的 `fmt` job 报差异——常见于格式化器版本失配
  （`${CLANG_FORMAT_MAJOR}` 与 `${CLANG_MAJOR}` 不同步）；
- 干净检出上重跑就红——本地有未提交的格式残留。

### 先做的三个检查

1. 本地工具链版本与真本一致吗：进镜像跑 `clang-format --version`，
   主版本号应与 `images/versions.env` 的 `${CLANG_FORMAT_MAJOR}` 相符；
2. 差异只在你改过的文件吗：`git status --short` + `git diff --stat`；
   格式化范围不含 `scripts/`、`images/` 与 `run.sh`（真本 `scripts/fmt.sh`）；
3. 干净检出能否复现：`git stash` 后重跑 `--check`，排除本机残留。

### 定位命令 / 工具

```bash
bash scripts/fmt.sh --check --lang cpp    # 只读；有差异 exit 1（CI 同款）
bash scripts/fmt.sh --list                # 打印 语言 -> 镜像层 -> 工具 映射，永不失败
make fmt                                  # 修法：就地格式化
TAG=latest scripts/run-example.sh cpp L1-001-references-pointers   # 格式化后回归受影响用例
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| `--check` 报「有差异」 | 改动后没跑 `make fmt` | `make fmt` 后重跑 `--check` |
| 本地过、CI 红 | 两边 clang-format 主版本不同（`${CLANG_FORMAT_MAJOR}` 失配 `${CLANG_MAJOR}`） | 比对两边 `clang-format --version` |
| 改 `.clang-format` 后全仓红 | 风格基线变更波及全部历史文件 | `git stash` 还原后看 `--check` 是否恢复绿 |
| 排版 PR 变成门禁变更 PR | 把 `run.sh`/`scripts/` 也格式化了（超出 fmt 范围） | 对照 `scripts/fmt.sh` 的范围注释 |

### 修复与预防

修复：`make fmt`（或 `bash scripts/fmt.sh --lang cpp`）后重跑受影响用例。
预防：格式化工具版本只随 `images/versions.env` 变（`${CLANG_FORMAT_MAJOR}` 与
`${CLANG_MAJOR}` 同步升级）；提交前把 `--check` 作为固定一步（CI 跑的就是它）。

**反例（可执行）**

- 错误做法：改完代码不跑 `--check`，指望 CI 替你格式化。
- 复现命令（实测；向 `L1-001-references-pointers` 注入一处缩进/空格违规后）：

  ```bash
  sed -i 's/^    int value = 7;/\t   int    value=7;/' cpp/examples/L1-001-references-pointers/main.cpp
  bash scripts/fmt.sh --check --lang cpp
  # 实测输出：cpp  有差异（clang-format …（LLVM 基线，见 .clang-format））……修法：make fmt
  git checkout -- cpp/examples/L1-001-references-pointers/main.cpp   # 还原
  ```

- 后果：PR 的 `fmt` job 必红；每门语言一个 fmt job，一处排版违规烧一整轮全量流水线。

## 断言失效与消毒器冲突（测试假绿、工具跑不起来）

> 来源：类型 ②——可复现实验（下文 `-DNDEBUG`、TSan+ASan 同开、LeakSanitizer
> 三例均为实测，真实输出随反例给出）；现象描述与 `L2-005-test-harness`、
> `L2-006-sanitizers` 的 README 口径一致。

### 典型现象

- 测试全绿但缺陷明明存在——典型于 `-DNDEBUG` 构建跑基于 `assert` 的测试（实测：断言被整个编译掉）；
- 编译报 `error: '-fsanitize=thread' is incompatible with '-fsanitize=address'`（实测原文）；
- 程序默认构建下「看起来正常」，开 ASan 才暴露越界/泄漏——`L2-006-sanitizers`
  的考点正是这个（故意构造的 heap-buffer-overflow 只有插桩后才报）。

### 先做的三个检查

1. 编译命令里有没有 `-DNDEBUG`（以及发布用的 `-O2`）？`assert` 语义依赖 `NDEBUG`
   宏，定义了它断言就不存在——比对用例 `run.sh` 与本地手工编译命令；
2. 一次只开一个 sanitizer：TSan 与 ASan/UBSan 需要分开构建
   （`L2-006-sanitizers` README 的「延伸」明确要求独立构建）；
3. 期望文件里是不是消毒器的「归一化」输出——ASan 报告含地址且以非零退出，
   直接透传会让输出不稳定（`L2-006-sanitizers` README「易错点」）。

### 定位命令 / 工具

```bash
TAG=latest scripts/run-example.sh cpp L2-005-test-harness   # 断言型测试基线（实测 PASS）
TAG=latest scripts/run-example.sh cpp L2-006-sanitizers     # ASan 检测演示（实测 PASS）
docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:${TAG:-latest}" bash -c \
  'g++ -fsanitize=address,thread -std=c++20 /tmp/x.cpp -o /tmp/x'
```

工具速查见 [工具指南.md](工具指南.md)；消毒器适用场景对比见该篇 §3。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 测试全绿但 bug 在 | `-DNDEBUG` 把 `assert` 编译掉了 | 见反例一：同一代码加不加 `-DNDEBUG` 行为相反 |
| 消毒器构建失败 | TSan 与 ASan 同开（编译器拒绝） | 见反例二：实测编译器报不兼容 |
| 默认构建正常、插桩后崩 | 缺陷一直存在，只是默认构建检测不到 | 用 ASan/UBSan 分开重建（`L2-006-sanitizers` 的做法） |
| 报告地址每次不同 | ASan 原始输出含地址 | 学 `L2-006-sanitizers`：grep 报告类型后输出固定结果 |

### 修复与预防

修复：测试构建去掉 `-DNDEBUG`；TSan 与 ASan 分两次构建分别跑；缺陷修复后开对应
消毒器回归。预防：把「测试构建不定义 NDEBUG」写进构建脚本（`run.sh`）而不是口头
约定；CI 每次全量跑用例，假绿在 PR 上就会被发现。

**反例（可执行）**

- 反例一：错误做法——用 `-DNDEBUG` 构建去跑断言测试。复现命令（实测）：

  ```bash
  docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:${TAG:-latest}" bash -c 'cd /tmp &&
    printf "#include <cassert>\n#include <cstdio>\nint main(){int n=0; assert(n==1); printf(\"alive\n\"); return 0;}" > t.cpp &&
    g++ -DNDEBUG -std=c++20 t.cpp -o t1 && ./t1 &&
    g++ -std=c++20 t.cpp -o t2 && ./t2'
  ```

  实测：第一段打印 `alive` 且退出码 0（断言被编译掉）；第二段
  `Assertion 'n == 1' failed.`，SIGABRT（退出码 134）。
  后果：断言型测试在 NDEBUG 构建下一个缺陷也抓不到，测试假绿。

- 反例二：错误做法——一把梭同开两个消毒器。复现命令（实测）：

  ```bash
  docker run --rm "ghcr.io/zeek-zhao/devbox-cpp:${TAG:-latest}" bash -c \
    'g++ -fsanitize=address,thread -std=c++20 /tmp/x.cpp -o /tmp/x'
  # 实测：cc1plus: error: '-fsanitize=thread' is incompatible with '-fsanitize=address'
  ```

  后果：编译直接失败；正确做法是分开构建（`L2-006-sanitizers` README「延伸」）。
