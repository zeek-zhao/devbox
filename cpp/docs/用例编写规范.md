# C++ 用例编写规范

本规范是后续 C++ 用例和其他语言用例的模板。示例、输出和目录契约都按自动验收方式编写；不确定的行为不能靠评审者猜。

## 1. 用例目录契约

每个用例是一个独立目录，三个文件各自承担唯一职责：

```text
<lang>/examples/<ID>/
├── run.sh          # 必须：自己负责编译与运行，只往 stdout 打业务输出
├── expected.txt    # 期望输出，逐行精确匹配（忽略行尾空白与首尾空行）
└── README.md       # 考点 / 易错点 / 延伸（各 2-5 行）
```

`run.sh` 把编译和执行封装在一起，让调用方不必知道编译器命令或项目结构；重复运行必须得到相同结果，也不能在仓库里留下可执行文件、对象文件等产物。单文件产物写到 `/tmp` 或 `${TMPDIR}`；项目级构建目录 `build/` 已在 `.gitignore`，多文件用例也必须把它放在临时目录下。输出必须确定，否则同一份 `expected.txt` 无法可靠验收。所有用例统一由 `scripts/run-example.sh <lang> <ID>` 执行，它负责容器、输出比对与状态汇总；不要为单个用例另写一套调用方式或比较脚本。

## 2. 编号规则

格式固定为 `L<级别>-<三位序号>-<短横线小写英文>`，例如：

- 正例：`L1-001-string-view`
- 正例：`L2-014-raii-resource`
- 正例：`L3-003-thread-pool`
- 反例：`l1-001-string-view`（级别前缀大小写错误）
- 反例：`L1-1-string-view`（序号不是三位）
- 反例：`L1-001-StringView`（说明部分不是短横线分隔的小写英文）

序号只在**同一语言、同一级别**内连续递增，从 `001` 开始，不跳号；换语言或级别后各自从头编号。新加用例时先确认同组最后一个序号，避免重复或留空。

## 3. run.sh 规范

1. 第一行必须是 `#!/usr/bin/env bash`，第二行必须是 `set -euo pipefail`。前两行之前不能有注释或空行。
2. 单文件产物路径统一为 `OUT="${TMPDIR:-/tmp}/devbox-<lang>-<id>"`，替换尖括号内容为实际语言和完整 ID。可执行文件、对象文件等**不许写进用例目录**。
3. 编译器使用 `${CXX:-g++}`，C++ 标准显式指定 `-std=c++20`；不要依赖容器默认编译标准。
4. stdout 只输出程序的业务结果。编译器命令、`echo "==> 编译中"` 等进度信息应走 stderr，或干脆不输出；编译器错误保留在 stderr，不能重定向后假装成功。
5. 退出码 `0` 表示编译和运行成功，任何失败都必须返回非 `0`。不许用 `|| true` 吞掉编译或运行失败。
6. L2/L3 等需要多个文件的用例，由 `run.sh` 自己驱动 `cmake -B build` 或 `make -C`，并把构建目录放到 `${TMPDIR}` 下，例如 `cmake -S . -B "${TMPDIR:-/tmp}/devbox-cpp-<id>-build"`。不要在仓库用例目录里生成 `build/`。

## 4. expected.txt 生成规则

`expected.txt` **必须从程序真实运行结果生成，不许手写**。手写容易漏换行、添空格或误判空行，导致本地和 CI 的实际比较不一致。使用统一 runner 生成：

```bash
TAG=latest scripts/run-example.sh cpp <ID> --update
```

生成后必须立刻查看 `git diff -- cpp/examples/<ID>/expected.txt`，确认每一行都是预期业务输出。`--update` 会把程序当前输出直接写入文件；程序即使输出了错误结果，也可能因此把 bug 固化成期望值。

期望输出不许包含时间、随机数、绝对路径、完整版本号、指针地址或线程 ID 等每次运行可能不同的内容。先让程序输出稳定、可读的业务值，再生成期望文件。

## 5. README.md 三段结构

README 必须按以下顺序写三段，每段各 2-5 行，写具体信息而不是口号：

```markdown
## 考点
（2-5 行：这个用例考哪个知识点，对应知识点清单的哪个 KP 编号）

## 易错点
（2-5 行：真实会踩的坑，写“会怎样 + 为什么 + 怎么避免”）

## 延伸
（2-5 行：学完这个还能往哪走，给具体方向不给空话）
```

README 里还必须有一行能手动复现的命令，使用真实 ID，例如：`TAG=latest scripts/run-example.sh cpp L1-007-string-view`。

## 6. 输出确定性黑名单

| 不许出现 | 为什么 | 替代做法 |
|---|---|---|
| 时间戳、当前时间 | 每次运行都可能不同 | 固定输入；只输出稳定的业务状态 |
| 随机数 | 即使范围相同，输出仍不相同 | 使用显式固定的测试数据；不要把随机值打印到 stdout |
| `/proc/self` 内容或绝对路径 | 与容器、机器和挂载位置有关 | 输出相对名称或固定标签，不打印环境路径 |
| `__cplusplus`、`gcc --version` 等版本号 | 镜像或工具链升级会改变结果 | 用编译期特性断言验证能力；输出固定的语义结果 |
| 指针地址（如 `%p`） | 地址受进程布局影响 | 打印对象内容、相等/不等关系或固定布尔值 |
| `std::thread::id` | 线程 ID 不可预测且实现相关 | 为任务分配固定序号，收集结果后排序再输出 |
| `unordered_map` 的迭代顺序 | 顺序不受保证，可能随实现或运行改变 | 把键值对收集到有序容器或排序后输出 |
| 未定义行为的任何结果 | 编译器优化、平台或运行都可能改变结果 | 只使用标准定义的行为；用断言验证前置条件 |
| 浮点数默认 6 位精度 | 默认格式/精度可能隐藏差异或不能匹配预期 | 用 `std::fixed` 和 `std::setprecision(n)` 明确格式，或输出可精确比较的整数 |
| 未排序的并发任务结果 | 调度顺序不固定 | 汇总结果后按稳定键排序，再打印 |

## 7. 禁止事项（会被判失败）

每项左边是错误写法，右边是正确做法：

- `cmd || true` → 直接运行 `cmd`，让 `set -e` 传播失败；如果确实要处理错误，用 `if cmd; then ...; else ...; fi` 并显式返回失败。
- `cmd 2>/dev/null` → 编译和运行命令保留 stderr；只有非编译/运行命令的错误确实可忽略时，才可重定向，并在旁边写明理由。
- `set +e` → 保持 `set -euo pipefail`；需要处理失败时用 `if` 显式分支并在失败分支返回非零。
- 用 `$?` 判空或绕过失败（包括先执行命令、再检查 `$?` 的写法）→ 直接用 `if cmd; then ...; else ...; fi` 检查命令状态，不依赖 `$?`。
- 在可能失败的分支里 `exit 0` → 返回非零，或让失败自然沿 `set -e` 退出。
- 用 `sleep` 等并发用例“差不多跑完了” → 用同步原语（如 `join`、条件变量或屏障）等待明确完成。
- 把 `expected.txt` 写成“大概长这样” → 真实运行程序，通过 `--update` 生成逐行精确的输出，再检查 diff。

## 8. L2 / L3 的补充断言

L2/L3 可以在 `run.sh` 中运行 `make test`、`ctest` 或自写 harness；这些检查失败时必须返回非零，退出码 `0` 才算通过。它们和 stdout 断言不互斥：只要程序有业务输出，仍须通过 `expected.txt` 精确比对。不要为了断言 stdout 再引入额外测试框架。并发用例必须用 `join` 收尾，并在**排序后**打印结果，不能依赖线程调度顺序。

## 9. 完整可运行示例（评审会抽出来真跑）

此例展示 `std::string_view` 不拥有字符：视图反映源字符串的修改，而独立构造的 `std::string` 保留修改前的副本。它不访问已失效的视图，输出固定。

<!-- spec:run-sh:start -->
```bash
#!/usr/bin/env bash
set -euo pipefail

CXX="${CXX:-g++}"
OUT="${TMPDIR:-/tmp}/devbox-cpp-l1-007-string-view"

"$CXX" -std=c++20 -Wall -Wextra -pedantic main.cpp -o "$OUT"
"$OUT"
```
<!-- spec:run-sh:end -->

<!-- spec:src:start -->
```cpp
#include <iostream>
#include <string>
#include <string_view>

int main() {
  std::string source{"devbox"};
  std::string_view view{source};
  std::string owned{view};

  source[0] = 'D';
  source[1] = 'E';

  std::cout << "view: " << view << '\n';
  std::cout << "owned: " << owned << '\n';
}
```
<!-- spec:src:end -->

<!-- spec:expected:start -->
```text
view: DEvbox
owned: devbox
```
<!-- spec:expected:end -->

## 10. 反例集

### 反例一：把产物写进用例目录

**错误代码：** `g++ main.cpp -o program && ./program`  
**会出什么问题：** 第一次运行在目录内留下 `program`；第二次运行可能误用旧产物，且 `git status` 会出现残留。  
**正确写法：** `OUT="${TMPDIR:-/tmp}/devbox-cpp-l1-001-example"`，编译和运行都引用 `"$OUT"`。

### 反例二：手写 expected.txt

**错误代码：** 手工写 `done` 并猜测末尾换行。  
**会出什么问题：** 程序输出多一个空行时，本地肉眼看起来一样，CI 仍可能报 `MISMATCH`。  
**正确写法：** `TAG=latest scripts/run-example.sh cpp L1-001-example --update` 后查看该文件的 diff，并核对程序输出。

### 反例三：并发任务按完成顺序打印

**错误代码：** 多个线程各自完成时立即 `std::cout << result`。  
**会出什么问题：** 调度改变打印顺序，导致本地通过、CI 失败，而且无法稳定复现。  
**正确写法：** 收集每个线程的结果，逐个 `join`，按固定键排序后由单线程统一打印。

## 11. 提交前自检清单

以下命令块可在仓库根目录直接执行；`ID` 应替换为本次用例的真实编号：

```bash
ID=L1-007-string-view
# 用例契约
test -f "cpp/examples/$ID/run.sh" && test -f "cpp/examples/$ID/expected.txt" && test -f "cpp/examples/$ID/README.md"
# shellcheck
shellcheck -S warning "cpp/examples/$ID/run.sh"
# 真跑 + 比对
TAG=latest scripts/run-example.sh cpp "$ID"
# 仓库无残留
git status --porcelain -- "cpp/examples/$ID"
# 覆盖表已同步（如果 COVERAGE.md 已启用）
if [ -f cpp/project/COVERAGE.md ]; then bash scripts/coverage-check.sh cpp; fi
```

## 12. `coverage: pending` 的语义与生命周期

用例已落地、但 `<lang>/project/` 尚未真正引用它时，在该用例的 `README.md` 中单独写一行，逐字使用：

```markdown
<!-- coverage: pending -->
```

真实示例见 [`cpp/examples/L1-001-references-pointers/README.md`](../examples/L1-001-references-pointers/README.md)。标记只从用例自己的 README 读取，不放在覆盖表或项目说明里。

依据 [`scripts/coverage-check.sh`](../../scripts/coverage-check.sh) 的四条校验规则，pending 豁免第 2 条（用例 ID 必须在 `project/` 代码里出现）和第 3 条（用例 ID 必须在 `project/COVERAGE.md` 表里声明）。它不允许表里声明不存在的用例；有非 pending 用例时，覆盖表仍须存在且非空。

**pending 不是“通过”，而是明账上的欠债**：脚本按语言及总量单独统计；非严格模式可能报告“校验通过（pending … 个）”，不代表项目已经覆盖这些用例。M4 收口用 `bash scripts/coverage-check.sh --strict`，只要仍有 pending 就返回失败；只查一门可用 `bash scripts/coverage-check.sh cpp --strict`。

只有 `project/` 真正接入对应知识点、代码中有可追溯的用例 ID，并同步 `project/COVERAGE.md` 的落点与说明之后，才摘掉 README 的标记，再运行覆盖校验。不要为清零而只写空注释或提前删标记；脚本能识别 ID，不替代对实际接入的评审。

## 13. 六语言 `run.sh` 规则表

仓库的统一 runner 与 CI 矩阵都是六门语言（`cpp go rust shell python java`），下表按同样六行列出，避免漏掉 Java。依据见 [`scripts/run-example.sh`](../../scripts/run-example.sh) 与 [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)。

各语言继续遵守前文的失败传播、临时产物及输出确定性规则。**输出归一化统一由 `scripts/run-example.sh` 完成**：实际 stdout 与 `expected.txt` 都只去行尾空白、去首尾空行，然后逐行 diff；不排序、不删除内部空行、不替换时间或路径。表中的语言专属处理是在产生输出之前固定业务结果，不是事后过滤错误。

| 语言 | 编译器/解释器怎么调 | 产物与缓存往哪重定向 | 输出怎么归一化 | 专属坑 |
|---|---|---|---|---|
| cpp | `${CXX:-g++}`，显式 `-std=c++20 -Wall -Wextra -pedantic`；见 [L1 runner](../examples/L1-001-references-pointers/run.sh)。[`images/versions.env`](../../images/versions.env) 当前 `GCC_MAJOR=14`，[安装脚本](../../images/scripts/install/cpp.sh) 将默认 `g++` 指向该主版本，不编造补丁版本。 | 单文件用 `OUT="${TMPDIR:-/tmp}/devbox-cpp-<ID>"`；多文件用临时 `…-build/` 构建目录，见 [CMake runner](../examples/L2-002-cmake-targets/run.sh) 的 `cmake -S . -B "$BUILD"`。 | 同统一归一化；CMake 构建、安装信息用 `>&2`，stdout 只留程序输出。 | “产物进 build/”不等于允许仓库内 `build/`；仍须按第 3 节放在临时目录。不得把 `g++ --version` 放进期望业务输出。 |

## 14. 两个“本地全绿但 CI 红”的坑

### 14.1. Go VCS stamping 与容器属主

[`go/examples/L2-001-local-module-replace/run.sh`](../../go/examples/L2-001-local-module-replace/run.sh) 开头记录了两个原因：Go 在模块模式下可能把 commit hash 等 VCS 信息烙进二进制，使构建结果依赖提交；容器用户与 `.git` 属主不一致时，git 可能以 `exit 128` 拒绝访问，导致 `go build` 失败。

worktree 的 `.git` 是指向主仓库 gitdir 的文件；只挂载 worktree 时，目标可能位于挂载外，Go 自动 stamping 找不到可用仓库而静默跳过，于是本地绿。CI 的真实 checkout 把 `.git` 放在挂载内，root 容器能发现它，却可能被 git 的属主安全检查拒绝，于是红。不要依赖这种“刚好看不见 `.git`”的环境差异，也不要通过修改 git 信任配置掩盖问题；修法是在所有 Go runner 中固定 `export GOFLAGS="-buildvcs=false"`。

### 14.2. 文件系统执行位不等于提交执行位

git 对普通文件只记录 `100644` / `100755`，不记录完整 Unix 权限。`chmod +x` 本身不修改已有提交；尤其 `core.filemode=false` 时，本地可执行也可能没有进入索引。判据是提交内容，而不是 `ls -l`：

```bash
git ls-tree HEAD shell/examples/L1-001-shebang-execution/demo.sh
# 直接执行的脚本应显示 100755
git update-index --chmod=+x shell/examples/L1-001-shebang-execution/demo.sh
# 随后提交，并再次用 git ls-tree HEAD 检查
```

真实坑位是 [`shell/examples/L1-001-shebang-execution/run.sh`](../../shell/examples/L1-001-shebang-execution/run.sh) 调用的 [`demo.sh`](../../shell/examples/L1-001-shebang-execution/demo.sh)。runner 已有 `[ -x ./demo.sh ] || chmod +x ./demo.sh` 兜底，修复挂载文件系统丢执行位后的直接执行；这是显式修复前置条件，不是吞掉运行失败。优先把执行位提交为 `100755`，需要兼容权限传播异常时再保留该兜底。CI 的静态步骤给 `run.sh` 加执行位，以及统一 runner 用 `bash run.sh` 启动，都不能保证它调用的 `./demo.sh` 可执行；依据见 [CI 配置](../../.github/workflows/ci.yml) 和 [统一 runner](../../scripts/run-example.sh)。

### 14.3. 复现与修复验证：真 clone + root 容器

在**非 root 宿主用户**下，从仓库根目录执行；需要 Docker 和已可用的语言镜像。真 clone 的 `.git` 在挂载内且归宿主用户所有，容器显式以 root 跑。仅在 worktree 里跑无法可靠暴露上述差异。下列 clone 只取已提交内容；验证待提交的 runner 前先提交修复。

```bash
REPRO="$(mktemp -d "${TMPDIR:-/tmp}/devbox-ci-repro.XXXXXX")"
BRANCH="$(git branch --show-current)"
git clone --no-local --branch "$BRANCH" . "$REPRO/repo"
REGISTRY="$(sed -n 's/^REGISTRY=//p' images/versions.env)"
TAG="${TAG:-latest}"

# 反例：仅在复现容器中关闭修复，模块构建应暴露 VCS 属主错误。
# 预期失败，诊断须保留；不要用 || true、set +e 或隐藏 stderr。
docker run --rm --user 0:0 --network none \
  -v "$REPRO/repo:/work" -w /work/go/examples/L2-001-local-module-replace \
  -e GOFLAGS= "$REGISTRY/devbox-go:$TAG" \
  go build -o /tmp/devbox-go-vcs-repro .
```

反例命令预期返回非零（git `exit 128` 引发 Go 构建失败）；若未触发，检查宿主是否 root、镜像是否已配置 `safe.directory`，以及挂载内是否确有真实 `.git`，不能把一次绿当成 stamping 安全。另行执行修复验证：

```bash
docker run --rm --user 0:0 --network none \
  -v "$REPRO/repo:/work" -w /work/go/examples/L2-001-local-module-replace \
  -e GOFLAGS=-buildvcs=false -e GOCACHE=/tmp/devbox-go-repro-cache \
  "$REGISTRY/devbox-go:$TAG" bash run.sh

# 查真 clone 的提交模式，而非宿主工作区权限。
git -C "$REPRO/repo" ls-tree HEAD shell/examples/L1-001-shebang-execution/demo.sh
# 只在临时 clone 中模拟挂载丢执行位；当前 runner 的兜底应修复并成功运行。
docker run --rm --user 0:0 --network none \
  -v "$REPRO/repo:/work" -w /work/shell/examples/L1-001-shebang-execution \
  "$REGISTRY/devbox-shell:$TAG" \
  bash -euo pipefail -c 'chmod -x ./demo.sh; bash run.sh'
```

若要观察历史执行位反例，在同一临时 clone 中另跑 `chmod -x ./demo.sh; ./demo.sh`（使用同样的 root 容器和严格 Bash），应报 `Permission denied` 并返回非零；不要移除真实 runner 的兜底来制造失败。上述手动容器命令用于诊断，正常用例验收仍走 `scripts/run-example.sh` 与 `expected.txt` 比对。复现只污染临时 clone；检查后清理本次明确创建的目录，勿对仓库根目录或通配路径做递归删除。
