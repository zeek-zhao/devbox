## 1. 怎么用这份清单

这份清单是写用例的依据，也是验收的依据；先评审通过清单，再按清单写用例。每个 KP 编号必须对应一个用例 ID，一个 KP 对应一个用例，不合并、不拆分。级别按解决问题所需的能力划分：L1 是单文件 50 行内能讲清、且不依赖构建系统的语言特性；L2 需要构建系统、多文件、外部依赖或测试框架，属于工程能力；L3 有明确技术难点，如并发、FFI、网络、序列化或性能，属于专题。

| KP-L1-21 | 强类型枚举（scoped enumerations） | 用 `enum class` 表达有限状态，并显式处理到整数的转换。 | 不同枚举类型不能意外混用，序列化值有明确转换。 | L1-021-enum-class | `enum class` 不会隐式转换为整数。 | 索引状态 |
| KP-L1-22 | 继承与多态（inheritance and polymorphism） | 通过虚函数实现运行时多态，并区分静态类型与动态类型。 | 基类引用调用派生类重写函数并产生预期结果。 | L1-022-inheritance-polymorphism | 函数签名不匹配时可能只是隐藏基类函数而非重写。 | — |
| KP-L1-23 | 虚析构函数（virtual destructors） | 通过基类指针销毁派生对象时保证派生析构函数被调用。 | 删除基类指针后派生资源的析构记录确实出现。 | L1-023-virtual-destructor | 通过无虚析构函数的基类指针删除派生对象会产生未定义行为。 | — |
| KP-L1-24 | 异常安全（exception safety） | 区分基本、强和不抛异常保证，并确保失败时对象状态有效。 | 人为触发操作失败后对象不泄漏资源且保持有效状态。 | L1-024-exception-safety | 修改状态后才执行可能抛异常的操作，可能破坏强保证。 | 索引构建失败回滚 |

| KP-L1-26 | 显式类型转换（explicit casts） | 按转换目的选 cast 并识别运行时检查边界。 | 合法转换使用对应 cast，运行时类型检查失败可被检测。 | L1-026-explicit-casts | `reinterpret_cast` 不会令不兼容对象布局或别名访问变安全。 | mmap 字节视图边界 |
| KP-L1-27 | 作用域与命名空间（scope and namespaces） | 用作用域和命名空间隔离名称，并判断局部遮蔽与查找结果。 | 相同短名称在不同命名空间中可无歧义引用。 | L1-027-namespaces | 头文件中滥用 `using namespace` 会污染包含者名称空间。 | 索引器模块命名 |

| KP-L1-29 | Pair 与 Tuple（`std::pair` and `std::tuple`） | 用标准复合类型返回多个关联值，并明确各元素类型和访问方式。 | 能通过结构化绑定或 `get` 读出返回的键和值。 | L1-029-pair-tuple | `std::get` 使用的 tuple 下标越界会在编译期失败。 | 词项与统计值 |
| KP-L1-30 | 编译期断言（`static_assert`） | 用静态断言将类型约束和常量条件转成编译期检查。 | 修改不满足条件的常量或类型后编译在断言处失败。 | L1-030-static-assert | 断言条件依赖的表达式必须满足常量表达式要求。 | — |

## 5. L4 设计模式专题

L4 是**专题层**：不再引入新语法，而是把 L1–L3 的能力组合成可复用的结构。
本层素材整理自外部 `cpp-sample` 仓库的既有实现（cpp/python 有现成单文件，go 需拆分，
java 按本表判据实现），一个模式一个用例，共 23 例。

**与 L1–L3 的三点不同**：

1. 用例一律标 `coverage: pending` —— 设计模式是**可复用结构**的练习，不强制接入毕业项目；
   是否纳入 `--strict` 收口见 `devbox-待办清单.md` 的待定项。
2. 判据只允许「stdout 固定文本 / 退出码 / 编译结果」，**不许出现耗时、随机、并发调度顺序**。
3. 同一模式在四门语言里 ID 相同（`L4-0NN-<slug>`），便于横向对照。

### 为什么 L4 不计入 R-E-01 的每语言 55 软目标

R-E-01 的软目标衡量的是「语言能力覆盖」，L4 是**结构复用**专题，与 L1–L3 的知识点不重叠。把 23 例计入后每语言 76 例，已超出 47–59 区间，这是**有意的范围扩展**，不是漏算。

## 6. 明确不覆盖的（及理由）

| 内容 | 为什么不覆盖 |
|---|---|
| C++20 modules | GCC 14 对 modules 的支持仍有工具链和生态差异，不适合作为六语言共用模板的基础验收项。 |
| 协程（coroutines） | 需要额外理解 promise、调度器和执行模型，概念门槛高，且六语言之间缺少可直接对齐的基础用例。 |
| Boost 生态 | 组件覆盖面和依赖体积超出当前轻量用例预算，标准库与少量专题足以支撑本清单。 |
| GUI 与图形 | 与高性能文本索引器目标无关，也不属于跨语言基础能力的共同核心。 |
| 异常规格说明（dynamic exception specifications） | 旧式动态异常规格已废弃并从现代标准中移除，学习资源应聚焦 noexcept 与异常安全。 |
| 自定义内存分配器 | 与 allocator traits、对齐和容器兼容性耦合较深，当前索引器可先使用标准分配策略。 |
| C++20 ranges | 标准库实现和项目工具链支持仍需额外约束，迭代器与 `<algorithm>` 已覆盖本轮共同基础。 |
| 编译器扩展与平台专属汇编 | 可移植性差且超出六语言模板范围，平台优化应在基准证明必要后另行评审。 |
