## 虚拟环境与依赖环境（串味 / 装错环境）

> 来源：类型 ②——可复现实验（下文三组输出均为容器实测）；类型 ①——素材池
> `S-05`（runtime 层模块集合与文档口径漂移：注释写 `python3-minimal`、实际
> `apt install python3`，环境「有什么」要以容器实测为准，`Q-S-08`）。

### 典型现象

- 对系统解释器直接装包报错退出（实测）：
  `error: externally-managed-environment`，退出码 1（PEP 668 保护）；
- 「我明明装过了」，import 却报 `ModuleNotFoundError: No module named 'xxx'`——
  包装进了 venvA，用 venvB 或系统解释器去 import（实测 venvB 与系统解释器
  均报 `ModuleNotFoundError: No module named 'myproj'`）；
- 环境明明隔离了，还是 import 到了别的环境的包——常见于 `PYTHONPATH` 残留：
  实测给 venvB 设 `PYTHONPATH=/tmp/venvA/lib/python3.12/site-packages` 后，
  venvB 成功 import 了 venvA 里的 `straylib`（串味）。

### 先做的三个检查

1. 你在用哪个解释器：`python3 -c 'import sys; print(sys.executable)'`——
   是 `/tmp/venvA/bin/python3` 还是 `/usr/bin/python3`，逐字看；
2. 这个解释器看得见哪些路径：`python3 -c 'import sys; print("\n".join(sys.path))'`，
   重点看有没有 `PYTHONPATH` 混进来（`echo $PYTHONPATH`）；
3. 包到底装进了哪个 site-packages：`python3 -m pip -V` 输出末尾就是 pip 所属的
   site-packages 路径；venv 内用 `uv pip list` 或
   `<venv>/bin/python3 -m pip list` 核对。

### 定位命令 / 工具

```bash
python3 -c 'import sys; print(sys.executable, sys.version.split()[0])'   # 哪个解释器、什么版本（版本真本 images/versions.env 的 ${PYTHON_VERSION}）
python3 -c 'import sys; print("\n".join(sys.path))'                      # 解释器找包的路径表
python3 -m pip -V                                                        # pip 自己属于哪个 site-packages
uv pip list --python /tmp/venvA/bin/python3                              # 指定环境的包清单（工具细节见 工具指南.md）
TAG=latest scripts/run-example.sh python L2-001-package-imports          # 导入机制的健康对照用例
```

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| `externally-managed-environment` | 对 PEP 668 保护的系统解释器直接装包 | 实测复现见下反例；`ls /usr/lib/python3.12/EXTERNALLY-MANAGED` 存在即受保护 |
| 装了却 `ModuleNotFoundError` | 装进环境 A、运行用环境 B | `sys.executable` 对比安装时用的解释器；实测装进 venvA 的包 venvB/系统都看不见 |
| 隔离失效、跨环境 import | `PYTHONPATH` 指向另一环境的 site-packages | `echo $PYTHONPATH` + `sys.path`；实测 PYTHONPATH 指向 venvA 时 venvB 能 import venvA 的包 |
| 语言层有、runtime 层没有 | 模块集合差异是镜像层的真实约束（素材池 `S-05`） | `docker run --rm ghcr.io/zeek-zhao/devbox-runtime:latest python3 -c 'import json'`（实测报 `ModuleNotFoundError: No module named 'json'`） |

### 修复与预防

修复：先 `sys.executable` 定锚，再决定在哪修——要装包就切到目标 venv
（`<venv>/bin/python3 -m pip install ...` 或 `uv pip install --python <venv>/bin/python3 ...`）；
串味就清掉 `PYTHONPATH`（或在 runner 的干净环境里复跑）；runtime 层缺模块不是
bug，是约束——按毕业项目的做法把依赖收进 `src/` 可用的标准库子集，或改镜像
安装脚本走重建。

预防：装包命令永远显式带目标解释器（uv 的 `--python` 参数把「装进哪个环境」
变成显式参数）；不要在 shell 配置里导出 `PYTHONPATH` 指向任何 site-packages；
新依赖先查 runtime 模块集合再写代码；离线容器内装不了新包，加依赖走
`images/scripts/install/python.sh` 镜像重建（见 [工具指南.md](工具指南.md)）。

**反例（可执行）**

- 错误做法：绕过虚拟环境，直接对系统解释器装包。
- 复现命令（实测）：

  ```bash
  docker run --rm "ghcr.io/zeek-zhao/devbox-python:${TAG:-latest}" \
    python3 -m pip install requests
  # 实测 stderr 关键行：error: externally-managed-environment
  # 实测退出码：1
  ```

- 后果：装包失败（ rc=1 ）；即便按提示加 `--break-system-packages` 硬闯成功，
  也会把系统 site-packages 搅乱——ruff/mypy/pytest 这些验收工具就装在那里，
  排查问题时你将分不清「哪个包是谁装的」。

## 可变默认参数与运行时状态累积

> 来源：类型 ②——可复现实验（`devbox-python:latest` 容器实测，输出原样记录，
> 见下）；对应知识点 `KP-PY-L1-07`（用例 `L1-007-mutable-default`）与
> `KP-PY-L1-10`（闭包 late binding，用例 `L1-010-closure-late-binding`），
> 同属「表达式求值时机」一族。

### 典型现象

- 函数的「每次调用都从空列表开始」假设被打破：连续调用结果累积——实测
  `print(add_tag("a")); print(add_tag("b"))` 输出 `['a']`、`['a', 'b']`；
- 数据里混进了上一次调用的记录，像「脏数据」又查不到写入点；
- 用 `inspect` 或 `__defaults__` 一看，默认值对象本身就是被污染的那个
  （实测 `add_tag.__defaults__` 为 `(['a', 'b'],)`）；
- 同族现象：循环里创建的 `lambda: i` 全部返回最后一个循环值（闭包 late binding，
  用例 `L1-010-closure-late-binding` 的验收点）。

### 先做的三个检查

1. 函数签名里有没有可变默认值：
   `grep -nE 'def .*=\s*(\[\]|\{\}|set\(\))' your_file.py`——`[]`/`{}`/`set()`
   出现在默认值位置就是嫌疑人；
2. 被怀疑的默认对象到底是不是同一个：
   打印 `func.__defaults__`（或 `id()`），连续调用两次看是否同一个对象；
3. 现象是否只在第二次及以后的调用出现——是，几乎可以锁定「跨调用共享状态」，
   而不是输入数据问题。

### 定位命令 / 工具

```bash
grep -rnE 'def .*=\s*(\[\]|\{\}|set\(\))' python/project/src/            # 在毕业项目里扫可变默认值
docker run --rm "ghcr.io/zeek-zhao/devbox-python:${TAG:-latest}" python3 - <<'PY'   # 最小复现（见反例）
TAG=latest scripts/run-example.sh python L1-007-mutable-default          # 对照用例：两种写法同框验收
TAG=latest scripts/run-example.sh python L1-010-closure-late-binding     # 同族：闭包 late binding
```

工具细节见 [工具指南.md](工具指南.md)；静态侧可用 ruff/mypy 扫
（[清单自检.md](清单自检.md) 有本轨道的检查口径）。

### 根因分类表

| 现象 | 可能根因 | 验证方法 |
|---|---|---|
| 结果跨调用累积 | 默认表达式只在函数定义时求值一次，所有调用共享同一可变对象 | 实测复现见反例；`__defaults__` 打印默认对象 |
| 只在第二次调用出问题 | 第一次调用已经 mutate 了共享默认值 | 把调用顺序反过来跑，污染跟随调用而不是数据 |
| 函数「有时对有时错」 | 共享默认对象被有条件地 mutate | 在函数入口打印 `id(tags)` |
| 循环里的 lambda 全取最后值 | 闭包 late binding（捕获绑定不捕获值） | 用例 `L1-010-closure-late-binding`；修法同族：默认参数固定 `i=i` |

### 修复与预防

修复：默认值改成 `None` 哨兵，函数体内新建容器——
`def add_tag(tag, tags=None): tags = [] if tags is None else tags`。
实测修复后两次独立调用分别输出 `['a']`、`['b']`，`__defaults__` 变为 `(None,)`。

预防：把「默认值禁止可变字面量」落进 review 与静态检查——签名扫描命令放
进 CI 前置脚本；需要跨调用共享容器时显式传参，别借默认值；教学侧跑
`L1-007-mutable-default`，两种写法在同一份 `expected.txt` 里对照验收，
`expected.txt` 的差异就是考点的可观察判据。

**反例（可执行）**

- 错误做法：`def f(x, acc=[])` 直接累积。
- 复现命令（实测，`devbox-python:latest` 容器内原样输出）：

  ```bash
  docker run --rm "ghcr.io/zeek-zhao/devbox-python:${TAG:-latest}" python3 - <<'PY'
  def add_tag(tag, tags=[]):
      tags.append(tag)
      return tags
  print(add_tag("a"))
  print(add_tag("b"))
  print(add_tag.__defaults__)
  PY
  # 实测输出：
  # ['a']
  # ['a', 'b']
  # (['a', 'b'],)
  ```

- 后果：两次「独立」调用共享同一个列表，状态像全局变量一样跨调用泄漏；
  在请求处理、批处理脚本里表现为「上一条请求的数据出现在下一条结果里」，
  且因为写入点藏在函数签名里，普通日志定位不到。
