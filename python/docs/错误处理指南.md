# Python 错误处理指南（G1 · 操作指南）

> 本文只有一个主要承诺：**按本仓库口径，把一段 Python 的错误处理写对**的操作步骤。
> 每一步落到具体用例 ID，命令契约统一为 `TAG=latest scripts/run-example.sh python <ID>`
> （见 [工程参考](工程参考.md) §5）。症状 → 命令 → 判据 → 修复的排查动作在
> [排查手册](排查手册.md)，本文不复述。语法基础归 [知识点清单](知识点清单.md) §2。

## 1. 适用边界（什么时候用 / 什么时候别用）

**用**：你在 `python/examples/` 下写用例、或写带失败路径的业务代码，需要决定
「失败怎么表达、怎么传播、怎么报告」。本仓库只用标准库（异常层次 / `raise from` /
`contextlib` / `logging` / `concurrent.futures`），无第三方错误处理框架；
lint/mypy 门禁见 [工程参考](工程参考.md) §3。

**别用**：异常语法学习（try/except/finally 基础归 [知识点清单](知识点清单.md) §2，
用例 `L1-016-exceptions-chain`、`L1-015-context-managers`）；正在排查一个已发生的
故障时直接去 [排查手册](排查手册.md) 按症状查。

## 2. 最小动线：分类 → 捕获 → 链与惯用 → 系统边界 → 容错 → 退出 → 报告

### 2.1 先建领域异常层次，类别决定动作

操作：为业务定义一个小异常层次（如 `ValidationError` / `TransientError` /
`InternalError`），每个类别映射唯一动作（reject-input / retry / fail-fast）；
失败在抛出点就归类，不在调用点猜。演练：`E-001-exception-hierarchy`
（判据 `taxonomy types=3 VALIDATION=1 TRANSIENT=1 INTERNAL=1`）。决策表在
[排查手册](排查手册.md) §2.1。

### 2.2 捕获顺序：具体在前、宽在后

操作：except 子句自上而下排列——具体类型在前，同级类型用元组一次捕获，
`except Exception` 兜底放最后；禁止把宽子句写在前头（后面的分支永远死代码）。
演练：`E-002-except-order`（判据 `order-rule: except clauses are tried top-down,
subclass handlers go first`）。规则见 [排查手册](排查手册.md) §2.2。

### 2.3 链与惯用：`raise from` 保根因，EAFP 消除检查窗口

操作两件套：

1. 跨层转换异常时用 `raise NewError(...) from e` 显式保留根因；
   纯重抛用裸 `raise`（传播同一对象、不造新链）；禁止 `raise NewError(...) from None`
   抹掉现场。演练：`E-003-exception-chaining`
   （判据 `explicit: type=RuntimeError cause=ValueError context=ValueError`）。
2. 存在性检查用 EAFP（try/except）而不是 LBYL（先 if 后用）：检查与使用并成
   一个原子步骤，关闭 check-then-use 窗口。演练：`E-004-eafp-lbyl`
   （判据 `verdict: EAFP collapses check and use into one step, ...`）。
   链形态对照见 [排查手册](排查手册.md) §2.3/§2.4。

### 2.4 系统边界：errno 映射 + 清理顺序

操作两件套：

1. 文件/网络失败按 errno 分流（EACCES→DENIED、EAGAIN→TRANSIENT、EIO→UNKNOWN），
   优先捕获内建 OSError 子类（`FileNotFoundError`/`PermissionError`/`BlockingIOError`）；
   errno 值才是稳定接口。演练：`E-005-errno-mapping`
   （判据 `denied: errno=13 type=PermissionError category=DENIED action=stop-and-report`）。
2. 多资源按后开先关逆序清理（嵌套 `with` / `ExitStack`）；可选资源的清理失败用
   `contextlib.suppress` 显式吞掉并继续，主流程异常不被清理动作覆盖。
   演练：`E-006-cleanup-order`（判据 `close: b` 先于 `close: a`，随后 `caught: boom`）。
   口径见 [排查手册](排查手册.md) §2.5/§2.6。

### 2.5 容错：重试 / 聚合 / 截止

操作：

1. 重试：只重试 TRANSIENT 类别，指数退避（10ms、20ms…）加次数上限；
   VALIDATION 一进重试器就拒绝。演练：`E-007-retry-backoff`
   （判据 `backoff: retries=2 delays=10,20ms`）。
2. 批量校验聚合：每条坏记录列出全部错误，全部报告后再拒绝；不做逐字段短路。
   演练：`E-009-error-aggregation`（判据 `aggregate: bad=3 errors=5 -> report all, then reject`）。
3. 等待设截止：每个阻塞调用有 deadline，超时抛 `TimeoutError`、归类 TIMEOUT、
   取消善后。演练：`E-011-timeout-deadline`
   （判据 `deadline-hit: TimeoutError after 0.05s`）。

参数与场景对照见 [排查手册](排查手册.md) §2.7/§2.9/§2.11。

### 2.6 退出协议与兜底边界

操作：CLI/服务在边界声明退出码协议（usage=2 / data=1 / success=0），非法输入
在入口即拒，错误详情进 stderr、stdout 只留可断言行；工作线程漏抛的异常装
`threading.excepthook` 兜底——记一行类型+消息、进程按约定续跑。
演练：`E-008-fail-fast-exit`（判据 `protocol: usage=2 data=1 success=0`）、
`E-013-excepthook-boundary`（判据 `boundary: unexpected errors are logged once,
process keeps running`）。协议见 [排查手册](排查手册.md) §2.8/§2.13。

### 2.7 报告：结构化日志、消息契约、降级留痕、反模式自查

操作：错误日志输出 JSON 行（code/level/message 三键固定、键序字典序），
错误类别是字段不是消息前缀；异常消息带字段名+实际值+期望（+行动建议），
凭证不进消息；降级逐源留痕（来源标签 + failed-sources 计数），全部路径失败才
RuntimeError 且携带每个源的原因。提交前对照三大反模式自查：静默吞错、
按消息文本分流、裸 except 吞 Ctrl-C。演练：`E-010-structured-logging`
（判据 `{"code": "TRANSIENT", "level": "ERROR", "message": "database unavailable"}`）、
`E-012-message-contract`（判据 `contract: good: field=True value=True action=True`）、
`E-014-graceful-degradation`（判据 `degradation: failed-sources=1`）、
`E-015-antipattern-compare`（判据 `rule: never swallow silently; classify by type;
let BaseException escape`）。口径见 [排查手册](排查手册.md) §2.10/§2.12/§2.14/§2.15。

## 3. 惯用法与反模式对照表

| 场景 | 惯用法（本仓库口径） | 反模式（可复现后果） |
|---|---|---|
| 异常设计 | 领域异常层次 + 类别→动作映射 | 一把 `Exception` 走天下，动作靠猜（`E-001`） |
| 捕获 | 具体在前、元组同级、宽兜底在后 | 宽子句在前，具体分支死代码（`E-002`） |
| 重抛 | 裸 `raise` 或 `raise ... from e` | `raise ... from None` 抹根因；换类型丢链 |
| 存在性 | EAFP 原子化检查+使用 | LBYL 的 check-then-use 窗口（`E-004`） |
| 清理 | 后开先关 + `suppress` 显式化 | 清理失败覆盖主异常 / 资源泄漏（`E-006`） |
| 分类 | 按 errno/类型分流 | 按消息文本 `startswith` 分流（`E-015` anti-2） |
| 兜底 | `except Exception` 后 `raise` 或记录+分类退出 | 裸 `except:` 连 `KeyboardInterrupt` 一起吞（`E-015` anti-3） |

## 4. 真实工作中的变体

- **异常层次随业务长**：教学版三层（VALIDATION/TRANSIENT/INTERNAL）；真实服务
  按域细分（如订单/库存各自的 Validation 子类），「类别→唯一动作」映射不变。
- **日志后端**：`E-010` 用 `json.dumps` 打 JSON 行；真实工程接日志平台时字段
  契约（code/level/message）不变，本仓库环境变量口径见 [工程参考](工程参考.md) §5。
- **异步超时**：`E-011` 用线程池 deadline 演示；asyncio 场景对应
  `L3-001-asyncio-timeout`，截止纪律一致。

## 5. 评审清单（review 时逐条问）

1. 每个抛出点异常归好类了吗？类别→动作映射唯一吗？
2. except 顺序具体在前吗？有没有宽子句吃掉具体分支？
3. 跨层转换用 `raise from` 了吗？重抛是裸 `raise` 吗？
4. 等待有截止吗？超时被归类了吗？
5. 退出码协议声明了吗？错误详情走 stderr 吗？
6. 错误日志是结构化字段吗？消息带字段名/实际值/期望吗？
7. 有没有裸 `except:`、静默吞错、按消息文本分流？
8. `ruff` + `mypy --strict` 门禁过了吗（`bash python/project/build.sh`）？
